## Build a prefix big enough to cache

The minimum cacheable prefix is model-dependent: 512 tokens on Sonnet 5.5 and
Opus 5.5, 1,024 on Sonnet 5 and Opus 5, and 4,096 on Haiku 4.5 (prompt caching
docs, checked 2026-10-06). Below the minimum nothing errors; the request just
runs uncached with `cache_creation_input_tokens: 0`. Note that the cheapest
model needs the largest prefix, so a short system prompt that caches on Sonnet
can silently never cache on Haiku.

The corpus below is sized to clear every current minimum.

```python
DOC = ("Section %d. The widget subsystem handles inventory reconciliation "
       "across regional warehouses, applying tier rules and audit logging.\n")
CORPUS = "".join(DOC % i for i in range(1, 201))
print("approx tokens:",
      client.messages.count_tokens(model=MODEL,
          messages=[{"role":"user","content":CORPUS}]).input_tokens)
```

<Output kind="illustrative" label="Out [2]">

```text
approx tokens: 6012
```

</Output>

**What to notice**

- About 6,000 tokens clears every current minimum, including Haiku 4.5's 4,096. Your count will differ slightly by model, because current models use a newer tokenizer.
- Below the model's minimum, caching fails silently: no error, just cache_creation_input_tokens of 0. Measuring the prefix is the only way to know.

## Run 1 · cache write

The first call pays a write premium: 1.25x base input at the default 5-minute
TTL (2x if you ask for the 1-hour TTL).

```python
def ask(question, prefix):
    r = client.messages.create(
        model=MODEL, max_tokens=1024,
        system=[
            {"type":"text","text":"You answer from the provided corpus only."},
            {"type":"text","text":prefix,"cache_control":{"type":"ephemeral"}},
        ],
        messages=[{"role":"user","content":question}],
    )
    u = r.usage
    print(f"  write={u.cache_creation_input_tokens:<7} read={u.cache_read_input_tokens:<7} "
          f"uncached_in={u.input_tokens}")
    return r

print("run 1"); ask("What does the widget subsystem do?", CORPUS);
```

<Output kind="illustrative" label="Out [3]">

```text
run 1
  write=6031    read=0       uncached_in=14
```

</Output>

**What to notice**

- write is the whole prefix up to and including the block that carries cache_control: both system blocks. You paid 1.25x base input on those tokens.
- uncached_in is only the question after the breakpoint. That split is what makes caching cheap when the prefix is large and the suffix is small.

## Run 2 · cache read

Same prefix. `write` should drop to 0 and `read` should jump. Only the
question after the breakpoint is billed as uncached input.

```python
print("run 2"); ask("Which rules does it apply?", CORPUS);
print("run 3"); ask("Does it log?", CORPUS);
```

**What to notice**

- write drops to 0 and read equals the earlier write: the second and third calls reused the stored prefix at 0.1x input price.
- The questions changed but sit after the breakpoint, so they do not affect the cache key. Only content before the breakpoint has to match byte for byte.
- Each read also refreshes the 5-minute TTL, so steady traffic keeps the entry warm without a longer TTL.

## Now break it

One timestamp at the top of the prefix. Nothing else changes.

This is a typical failure scenario: *a release adds a current timestamp to the
cached system prompt, and `cache_read_input_tokens` drops to near zero while
nothing errors.*

```python
from datetime import datetime
print("poisoned run 1"); ask("What does it do?", f"Generated: {datetime.now()}\n" + CORPUS);
print("poisoned run 2"); ask("Which rules?",     f"Generated: {datetime.now()}\n" + CORPUS);
print()
print("read stays at 0. Every call is now a fresh write at 1.25x input price.")
print("The fix is PLACEMENT, not TTL: move volatile values out of the cached prefix.")
```

**What to notice**

- Nothing errored. The only signal is cache_read_input_tokens falling to 0 while cache_creation_input_tokens stays high on every call.
- A longer TTL would not help, because the prefix never repeats. The fix is to move the timestamp after the breakpoint (for example, into the user message).
- In a typical failure scenario like this one, the deciding clue is a value that changes per request inside the cached prefix.

## Do the arithmetic

Cache reads cost 0.1x base input on most models (0.05x on Opus 5.5, 0.025x on
Fable 5.1). The numbers below use Sonnet 5.5 list prices ($2 per million input
tokens, pricing page checked 2026-10-06). Work out what the mistake costs at
your real traffic volume, then notice the third line: a poisoned cache is
worse than no cache at all.

```python
IN_PER_MTOK, CACHE_READ_MULT, CACHE_WRITE_MULT = 2.00, 0.10, 1.25
tokens, calls = 5000, 100_000

full     = tokens/1e6 * IN_PER_MTOK * calls
cached   = (tokens/1e6*IN_PER_MTOK*CACHE_WRITE_MULT) + (tokens/1e6*IN_PER_MTOK*CACHE_READ_MULT*(calls-1))
poisoned = tokens/1e6 * IN_PER_MTOK * CACHE_WRITE_MULT * calls
print(f"no cache      ${full:,.2f}")
print(f"cached        ${cached:,.2f}")
print(f"poisoned      ${poisoned:,.2f}  (every call a write)")
print(f"saved         ${full-cached:,.2f}  ({(1-cached/full)*100:.1f}%)")
```

<Output kind="illustrative" label="Out [6]">

```text
no cache      $1,000.00
cached        $100.01
poisoned      $1,250.00  (every call a write)
saved         $899.99  (90.0%)
```

</Output>

**What to notice**

- These numbers are arithmetic from list prices, not a measurement: 5,000-token prefix, 100,000 calls, Sonnet 5.5 at $2 per million input tokens.
- A poisoned cache costs 25% more than not caching at all, because every call pays the write premium and none gets the read discount.
- The multipliers depend on the model: reads are 0.05x on Opus 5.5 and 0.025x on Fable 5.1, so rerun the cell with your model's numbers.

## Checkpoint

<Recall q="What is the prefix order? (three things, in order)">

tools, then system, then messages. The cache key is built over that rendered order, so a change at any level invalidates that level and everything after it. That is why changing a tool definition breaks the system and message caches too.

</Recall>

<Recall q="Name three ways to invalidate a cache.">

Any byte change before the breakpoint does it: a timestamp or request ID interpolated into the system prompt, adding, removing or reordering tool definitions, or non-deterministic JSON key order in serialized content. Switching models also misses, because caches are model-scoped, and changing thinking, effort or tool_choice invalidates the message-level cache. Finally, an entry simply expires if nothing reads it within its TTL.

</Recall>

<Recall q="Where do you place breakpoints, and why does content order matter?">

Put a breakpoint at the end of the stable content, typically the last block of the static system prompt or the last tool, and keep everything volatile after it; you get at most four breakpoints per request. Order matters because the match is an exact prefix: stable content placed after a volatile value can never be reused, however many markers you add.

</Recall>
