## A tool, and a real implementation behind it

```python
ORDERS = {"CUST-10041": "shipped", "CUST-10042": "processing"}

TOOLS = [{
    "name": "lookup_order",
    "description": ("Look up the status of a customer order by ID. "
                    "Use when the user asks about an order's status or delivery. "
                    "Do NOT use for refunds or cancellations."),
    "input_schema": {
        "type":"object",
        "properties":{"customer_id":{"type":"string",
                      "description":"Customer ID in the form CUST-XXXXX"}},
        "required":["customer_id"],
    },
}]

def run_tool(name, args):
    if name != "lookup_order":
        raise ValueError(f"unknown tool {name}; available: lookup_order")
    cid = args["customer_id"]
    if cid not in ORDERS:
        raise LookupError(f"customer_id {cid} not found; expected format CUST-XXXXX")
    return ORDERS[cid]
```

**What to notice**

- The tool definition is just data: a name, a description and a JSON Schema. Nothing here gives the model the ability to run code.
- run_tool raises on bad input with a message that says what was wrong and what the expected format is. The loop turns that into an actionable tool_result.

## The loop, bounded

Note `max_turns`. An unbounded loop is a harness design failure, not a model
failure.

Two details that matter on current models: append `r.content` back **whole
and unchanged** (it can contain `thinking` blocks that must round-trip), and
branch on `stop_reason` rather than on whether text exists.

```python
def agent(question, tools=TOOLS, max_turns=6, verbose=True):
    msgs = [{"role":"user","content":question}]
    for turn in range(max_turns):
        r = client.messages.create(model=MODEL, max_tokens=2048, tools=tools, messages=msgs)
        if verbose: print(f"turn {turn}: stop_reason={r.stop_reason}")
        if r.stop_reason != "tool_use":
            return text_of(r)
        msgs.append({"role":"assistant","content":r.content})
        results = []
        for b in r.content:
            if b.type == "tool_use":
                if verbose: print("   model asked for", b.name, b.input)
                try:
                    results.append({"type":"tool_result","tool_use_id":b.id,
                                    "content":run_tool(b.name, b.input)})
                except Exception as e:
                    if verbose: print("   TOOL FAILED ->", e)
                    results.append({"type":"tool_result","tool_use_id":b.id,
                                    "content":str(e),"is_error":True})
        msgs.append({"role":"user","content":results})
    return "HIT THE TURN LIMIT"

print(agent("What is the status of order CUST-10041?"))
```

**What to notice**

- The model only asked for lookup_order. Your code ran it and sent the result back; the model never executed anything.
- Two API calls for one answer: every tool round trip resends the full history, so input tokens grow with each turn.
- The loop exits on stop_reason, not on whether text exists, and max_turns caps it. A harness without that cap can loop until it hits a cost limit.

## The important half: a deliberate failure

Watch the model receive `is_error: True`, read the message, and
**self-correct**. This is why you return actionable errors instead of
throwing.

A good schema description usually prevents the mistake entirely, so this cell
uses a copy of the tool with the ID format removed from the schema. The only
place the model can learn the format is the error message.

```python
import copy
NO_FORMAT_HINT = copy.deepcopy(TOOLS)
NO_FORMAT_HINT[0]["input_schema"]["properties"]["customer_id"]["description"] = "The order's ID"

print(agent("Check order 10042 for me.", tools=NO_FORMAT_HINT))
```

**What to notice**

- The first call failed, the loop returned is_error: true with the reason, and the model retried with the corrected ID. Raising instead would have ended the conversation.
- The error message did the work a good schema description normally does. Actionable errors are a second line of defence, not a substitute for clear descriptions.
- Your run may succeed on the first call if the model infers the format anyway; the illustrative output shows the failure path this cell is built to provoke.

## Now make tool selection worse

Add an overlapping tool with a vague description. The model has to guess, and
can guess badly. Every tool definition is also input tokens on **every**
request, on top of a fixed tool-use system prompt the API adds whenever any
tool is present (286 tokens on Sonnet 5.5, per the pricing page).

```python
TOOLS.append({
    "name":"get_customer_info",
    "description":"Gets information about a customer.",      # vague on purpose
    "input_schema":{"type":"object",
        "properties":{"id":{"type":"string"}},"required":["id"]},
})

base = client.messages.count_tokens(model=MODEL, tools=TOOLS[:1],
        messages=[{"role":"user","content":"status of CUST-10041?"}]).input_tokens
both = client.messages.count_tokens(model=MODEL, tools=TOOLS,
        messages=[{"role":"user","content":"status of CUST-10041?"}]).input_tokens
print(f"1 tool: {base} tokens | 2 tools: {both} tokens | overhead every request: +{both-base}")
print()
print(agent("Tell me about CUST-10041."))
```

**What to notice**

- Even one tool costs a few hundred tokens because the API adds a fixed tool-use system prompt whenever tools are present. Each additional definition adds its own tokens on every request.
- The vague tool matched "tell me about" better than the precise one, so the model picked it. Overlapping, vague descriptions cause selection errors that look like model mistakes but are tool design mistakes.
- Which tool the model picks first will vary between runs; the token overhead will not.

## Checkpoint

<Recall q="Who executes a tool?">

Your application does. The model returns a tool_use block naming a tool and its input, and your harness decides whether to run it, runs it, and sends back a tool_result. That is why validation, permissions and side-effect controls belong in harness code, not in the prompt.

</Recall>

<Recall q="Why is a tool description a prompt?">

The API renders tool names, descriptions and schemas into the model's context, and the model chooses which tool to call and with what arguments by reading them. A vague description therefore produces wrong selections and badly formed inputs, exactly like a vague instruction. The docs call detailed descriptions the most important factor in tool performance.

</Recall>

<Recall q="What do you return when a tool throws, and why not just raise?">

Return a tool_result for that tool_use_id with is_error: true and a message that says what went wrong and how to fix it. Raising ends the loop and leaves the tool_use unanswered, while an actionable error lets the model correct itself on the next turn, as the failure cell showed.

</Recall>

<Recall q="Why do 40 tools make selection worse rather than better?">

More tools means more overlapping descriptions for the model to choose between, so ambiguity and wrong picks increase, and every definition is paid for in input tokens on every request. Consolidating related operations, namespacing names, and loading rarely used tools on demand (for example with tool search) keep the choice small and clear.

</Recall>
