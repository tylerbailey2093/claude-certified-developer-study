**~15 minutes of work, then a wait · costs about $0.01 · Domain 2 API Mechanics**

50% off, no streaming, up to 24 hours to finish (most batches end within an
hour), and **results come back in any order**. That last one is the trap, and
it is a silent data-corruption bug: the batch succeeds, every row returns, and
the labels are attached to the wrong records.

```python
import os, anthropic
client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY
MODEL  = "claude-sonnet-5-5"            # everyday model (src/data/facts.json); verify against lab 00
CHEAP  = "claude-haiku-4-5"             # for high-volume steps

def text_of(resp):
    """Join every text block. Never index content[0]: the first block can be thinking or tool_use."""
    return "".join(b.text for b in resp.content if b.type == "text")
```

## Submit with custom_id

Each request carries a `custom_id` (1 to 64 characters: letters, digits,
hyphens, underscores). `max_tokens=256` is generous for a one-word label;
Haiku 4.5 does not think unless you enable it, but a model that does would
spend part of a tiny budget before any text appears.

```python
REVIEWS = [
    "Arrived broken and support never replied.",
    "Exactly what I needed, shipped fast.",
    "Fine, nothing special.",
    "Second time this has failed. Done with this brand.",
    "Better than the previous model by a mile.",
]

batch = client.messages.batches.create(requests=[
    {"custom_id": f"review-{i}",
     "params": {"model": CHEAP, "max_tokens": 256,
                "messages": [{"role":"user",
                    "content": f"Reply with one word, positive or negative:\n{t}"}]}}
    for i, t in enumerate(REVIEWS)
])
print("batch:", batch.id, "|", batch.processing_status)
```

**What to notice**

- Creation returns immediately with a batch ID and in_progress. No results exist yet; batch is asynchronous by design.
- Each request carries its own params, including max_tokens, exactly as a normal Messages call would. Batch changes price and timing, not the request shape.

## Poll

Can take a few minutes. Batch is for work nobody is waiting on.

## The bug, demonstrated

`positional` is what a reasonable engineer writes on a Friday. Compare it with
the `custom_id` join and see whether they agree.

```python
raw = list(client.messages.batches.results(batch.id))

positional = {REVIEWS[i]: text_of(r.result.message).strip()
              for i, r in enumerate(raw) if r.result.type == "succeeded"}

by_id = {}
for r in raw:
    if r.result.type == "succeeded":
        idx = int(r.custom_id.split("-")[1])
        by_id[REVIEWS[idx]] = text_of(r.result.message).strip()

print("returned order:", [r.custom_id for r in raw])
print()
for text in REVIEWS:
    p, c = positional.get(text), by_id.get(text)
    flag = "  <-- MISMATCH" if p != c else ""
    print(f"{text[:44]:<46} positional={str(p):<10} custom_id={c}{flag}")
```

**What to notice**

- The returned order shown is illustrative. On your run it may match the input order by luck, and that is the danger: the positional join passes every test until it silently mislabels production data.
- The custom_id join is correct regardless of order. It is the only safe key, which is why each request needs a unique, meaningful custom_id.
- Every row succeeded and nothing errored. Corruption here is a join bug in your code, not an API failure.

If the returned order happened to match this time, run it again with more
requests. **The API makes no ordering guarantee**, so code that relies on order
is broken whether or not it has failed yet. That is the worst kind of bug.

## Checkpoint

<Recall q="Four properties of the Batch API">

It costs 50% of standard prices on input and output. It is asynchronous: most batches finish within an hour, and requests still unprocessed after 24 hours expire. It does not stream (stream: true is rejected), and results come back in any order, available for 29 days.

</Recall>

<Recall q="What is the only safe join key?">

custom_id. The docs state that results can be returned in any order, so joining by position can attach answers to the wrong inputs without any error. Give every request a unique custom_id that maps back to your source record.

</Recall>

<Recall q="Does batch stack with caching? At what discount?">

Yes. The pricing page says caching multipliers stack with the Batch API discount, so a cache read inside a batch costs 0.1 x 0.5 = 0.05x the standard input price, and a 5-minute cache write costs 1.25 x 0.5 = 0.625x. Because a batch can take longer than five minutes, the docs suggest the 1-hour cache TTL for shared context in batches.

</Recall>
