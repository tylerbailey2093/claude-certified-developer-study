Four API facts, proven by running them:

1. The system prompt goes in the top-level `system` parameter; a `system` role as the first message is a 400
2. `content` is a **list of blocks**, not a string
3. `stop_reason` arrives on a **successful 200** and is not an error
4. `usage` has more fields than you think

```python
import os, anthropic
client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY
MODEL  = "claude-sonnet-5-5"            # everyday model (src/data/facts.json); verify against lab 00
CHEAP  = "claude-haiku-4-5"             # for high-volume steps

def text_of(resp):
    """Join every text block. Never index content[0]: the first block can be thinking or tool_use."""
    return "".join(b.text for b in resp.content if b.type == "text")

print("sdk", anthropic.__version__)
```

## 2 · Iterate blocks by type

`r.content[0].text` works right up until a `thinking` or `tool_use` block lands
in position zero. Then it throws `AttributeError` in production at 2am.

On Sonnet 5.5 that is the normal case, not the edge case: adaptive thinking is
on by default, so the first block is often `thinking` (with an empty
`thinking` field, because the display default is `omitted`). Iterate by type,
or use `text_of`.

```python
def render(resp):
    for i, b in enumerate(resp.content):
        print(f"[{i}] type={b.type}")
        if b.type == "text":
            print("    ", b.text[:120].replace("\n"," "))
    return resp

render(r)
print("text_of ->", repr(text_of(r)))
```


**What to notice**

- Position zero is a thinking block. Code that assumes content[0] is text fails here, on an ordinary request with no tools.
- Filtering by block type is the general pattern; it also handles tool_use blocks and multiple text blocks (for example, with citations).

## 3 · Force a truncation and read stop_reason

This returns **HTTP 200**. It is not an error. Your code must branch on it.

`max_tokens=256` is deliberately far too small for a 1,500-word request. It
caps thinking and text together, so on a thinking model the cut can land
before any text block exists; then `text_of` returns an empty string. Both
outcomes teach the same thing: the response is truncated, not malformed.

```python
t = client.messages.create(
    model=MODEL, max_tokens=256,                      # deliberately too small
    messages=[{"role":"user","content":"Explain the TCP handshake in exhaustive detail, at least 1,500 words."}],
)
print("stop_reason:", t.stop_reason)
print("block types:", [b.type for b in t.content])
print("visible text:", len(text_of(t)), "chars, ending", repr(text_of(t)[-60:]))
print()
print("TRUNCATED, NOT MALFORMED. The rest was never generated.")
print("Sending this back to the model for 'repair' asks it to invent the missing part.")
```

<Output kind="illustrative" label="Out [4]">

```text
stop_reason: max_tokens
block types: ['thinking', 'text']
visible text: 583 chars, ending 'h a segment that has both the SYN and ACK flags set, and its'

TRUNCATED, NOT MALFORMED. The rest was never generated.
Sending this back to the model for 'repair' asks it to invent the missing part.
```

</Output>

**What to notice**

- The call succeeded with HTTP 200 and still delivered an unusable answer. Only stop_reason tells you; no exception is raised.
- max_tokens caps thinking and text together. On some runs thinking consumes the whole budget and block types shows only thinking, with zero visible text.
- The correct response to max_tokens is a code decision (raise the limit, stream, or split the task), not a follow-up prompt asking the model to fix the fragment.

## 4 · Where the system prompt goes

The system prompt belongs in the top-level `system` parameter. Putting
`{"role": "system"}` first in `messages` returns a **400 invalid_request_error**
on every current model, but for two different reasons:

- On models without mid-conversation system messages (Haiku 4.5 here), the
  `system` role itself is rejected.
- Newer models (Sonnet 5.5, Opus 5.5 and others) accept a `system` role
  **mid-conversation**, after a user turn, as an operator channel that leaves
  the cached prefix intact. It still cannot be `messages[0]`.

Run it against both and compare the messages. The mid-conversation feature is
recent engineering knowledge [Likely]; for exam purposes the stable fact is
"system prompt = top-level parameter".

```python
import anthropic
for model in (CHEAP, MODEL):
    try:
        client.messages.create(model=model, max_tokens=256, messages=[
            {"role":"system","content":"You are terse."},
            {"role":"user","content":"hi"},
        ])
        print(model, "-> no error (unexpected)")
    except anthropic.BadRequestError as e:
        print(model, "-> status", e.status_code)
        print("   ", e.message[:240])
```

<Output kind="illustrative" label="Out [5]">

```text
claude-haiku-4-5 -> status 400
    Error code: 400 - {'type': 'error', 'error': {'type': 'invalid_request_error', 'message': "role 'system' is not supported on this model"}, ...
claude-sonnet-5-5 -> status 400
    Error code: 400 - {'type': 'error', 'error': {'type': 'invalid_request_error', 'message': 'messages.0: a system message cannot be the first message', ...
```

**What to notice**

- Both calls fail with 400 invalid_request_error, which is a request-shape problem: retrying will never fix it.
- The two messages differ. Haiku 4.5 rejects the role outright; Sonnet 5.5 supports mid-conversation system messages but not as messages[0]. The exact wording shown is illustrative.
- The stable rule for exam purposes: the system prompt goes in the top-level system parameter.

## 5 · Every field of usage

Log these separately in production or your cost model is quietly wrong. On a
thinking model, `output_tokens` includes thinking tokens you never see as text.

```python
u = r.usage
for f in ["input_tokens","output_tokens","cache_creation_input_tokens",
          "cache_read_input_tokens","cache_creation","service_tier"]:
    print(f"{f:<30}", getattr(u, f, None))
```

```text
cache_creation                 CacheCreation(ephemeral_1h_input_tokens=0, ephemeral_5m_input_tokens=0)

```

**What to notice**

- input_tokens counts only uncached input. Total input is input_tokens plus cache_creation_input_tokens plus cache_read_input_tokens, and each is priced differently.
- output_tokens includes thinking. A cost model that estimates output from visible text length will under-count on thinking models.
- The cache fields are zero here because nothing was marked for caching. Lab 02 makes them move.

## Checkpoint

<Recall q="Name the stop_reason values and say why none of them is an error.">

end_turn, max_tokens, stop_sequence, tool_use, pause_turn and refusal, plus model_context_window_exceeded on current API versions. All arrive on an HTTP 200 with valid content and explain why generation stopped; errors are non-2xx responses or error events in a stream. Each value still needs its own branch: run tools on tool_use, resend on pause_turn, handle refusal, and treat max_tokens as truncation.

</Recall>

<Recall q="Why is content[0].text a latent bug?">

content is a list of typed blocks, and the first one is not guaranteed to be text. On thinking models such as Sonnet 5.5 the first block is often a thinking block, which has no text attribute, and with tools it can be tool_use. Filter blocks by type and join the text ones.

</Recall>

<Recall q="What do you do when stop_reason is max_tokens and the JSON is broken?">

Treat it as truncation, not as malformed output: the rest of the JSON was never generated. Raise max_tokens (stream if the output is long) or reduce what you ask for, and retry; do not ask the model to repair the fragment, because that invites it to invent the missing part. Check stop_reason before parsing, and use structured outputs when you need the shape guaranteed once the response is complete.

</Recall>
