Two facts: final `usage` and `stop_reason` arrive in **`message_delta`**, not
`message_start`; and because the HTTP status commits before generation
finishes, **an error can arrive after a 200**.

## Print every event in order

Do this once and the sequence sticks. Two SDK details: the Python
`messages.stream()` helper also yields convenience events (`text`, `thinking`,
`signature`, `input_json`) next to the raw server-sent events, and it silently
drops `ping` events. The wire order is `message_start`, then per block
`content_block_start` / `content_block_delta`... / `content_block_stop`, then
`message_delta`, then `message_stop`.

```python
from collections import Counter
seen = Counter()

with client.messages.stream(model=MODEL, max_tokens=1024,
        messages=[{"role":"user","content":"List three uses for prompt caching."}]) as s:
    for ev in s:
        seen[ev.type] += 1
        if ev.type == "content_block_start":
            print(ev.type, "->", ev.content_block.type)
        elif ev.type in ("message_start","content_block_stop","message_delta","message_stop"):
            print(ev.type)
        if ev.type == "message_delta":
            print("   stop_reason:", ev.delta.stop_reason)
            print("   usage:", ev.usage)

print()
print(dict(seen))
```

**What to notice**

- The order is fixed: message_start, then each block as start, deltas, stop, then message_delta, then message_stop. stop_reason first appears in message_delta.
- Block 0 is a thinking block whose only delta is a signature, because thinking display defaults to omitted. Streaming UIs see a pause before text starts.
- text and signature are SDK convenience events, not wire events, and the SDK drops ping events. Counts are illustrative.

## Confirm where usage lives

`message_start` carries the input count and a placeholder output count; the
**final** output count only shows up in `message_delta`, whose usage figures
are cumulative. Code that reads usage at the start under-reports cost.

```python
with client.messages.stream(model=MODEL, max_tokens=1024,
        messages=[{"role":"user","content":"Say four sentences about tokens."}]) as s:
    for ev in s:
        if ev.type == "message_start":
            print("at message_start :", ev.message.usage)
        if ev.type == "message_delta":
            print("at message_delta :", ev.usage)
    final = s.get_final_message()
print("final object     :", final.usage, "| stop:", final.stop_reason)
```

```text

at message_delta : MessageDeltaUsage(cache_creation_input_tokens=0, cache_read_input_tokens=0, input_tokens=15, output_tokens=142, server_tool_use=None)
final object     : Usage(cache_creation_input_tokens=0, cache_read_input_tokens=0, input_tokens=15, output_tokens=142, service_tier='standard', ...) | stop: end_turn
```

</Output>

**What to notice**

- output_tokens at message_start is a placeholder (single digits). The real figure arrives in message_delta, and those counts are cumulative, so do not add them up.
- get_final_message() returns the same totals as the last message_delta. Use it when you only need the finished response but still want streaming's timeout protection.

## Partial output is a product decision

If the stream dies at token 300 of 800, the user has already read 300 tokens.
Deleting them is jarring; leaving them is misleading. Decide deliberately.

Mid-stream errors arrive as an `error` event (for example `overloaded_error`)
after the 200 has already been sent. If you resume, note that on current
models you cannot prefill the partial answer as an assistant turn; the
streaming docs say to send a user message containing the partial response and
an instruction to continue.

```python
import anthropic
buf = []
try:
    with client.messages.stream(model=MODEL, max_tokens=1024,
            messages=[{"role":"user","content":"Explain HTTP caching."}]) as s:
        for ev in s:
            if ev.type == "content_block_delta" and ev.delta.type == "text_delta":
                buf.append(ev.delta.text)
except anthropic.APIError as e:
    print("mid-stream failure after a 200:", type(e).__name__)
    print("partial chars already shown to the user:", len("".join(buf)))
    # policy options: mark it truncated, retry silently, or keep and flag
print("ok, chars:", len("".join(buf)))
```

<Output kind="illustrative" label="Out [4]">

```text
ok, chars: 3184
```

</Output>

**What to notice**

- Most runs print only the success line. The except branch is there for the run where an overloaded_error or a dropped connection arrives after the 200, with partial text already shown.
- A mid-stream error cannot change the HTTP status, which was sent before generation began. Error handling that only checks the status code misses it.
- Deciding what to do with partial output (keep and flag, retract, or retry) is a product decision you make in code ahead of time.

## Checkpoint

<Recall q="Name the six event types in order">

message_start, content_block_start, content_block_delta, content_block_stop, message_delta, message_stop. The middle three repeat once per content block, and ping events can appear anywhere. An error event can also arrive mid-stream, after the HTTP 200.

</Recall>

<Recall q="Where does final usage arrive?">

In message_delta, whose usage counts are cumulative. message_start carries input tokens and only a placeholder output count, so code that logs usage there under-reports cost. The SDK's get_final_message() exposes the same final totals.

</Recall>

<Recall q="What transport does Claude streaming use? (Not WebSocket.)">

Server-sent events: a one-way text/event-stream over an ordinary HTTP response, where each event has a name and a JSON payload. A WebSocket is a persistent, bidirectional connection, which the Messages API does not need because the client sends one request and only reads the stream back.

</Recall>
