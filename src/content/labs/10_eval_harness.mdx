## Code-based grading

One right answer per case, so exact match is the correct grader: fastest, most
reliable, no drift. Reach for an LLM judge only when exact match cannot apply.

```python
def classify(text, prompt):
    r = client.messages.create(model=CHEAP, max_tokens=256, system=prompt,
            messages=[{"role": "user", "content": text}])
    return text_of(r).strip().lower().strip(".")

def evaluate(prompt, label):
    results, correct = [], 0
    for text, expected in GOLDEN:
        got = classify(text, prompt)
        ok = got == expected
        correct += ok
        results.append((text, expected, got, ok))
    print(f"{label:<12} {correct}/{len(GOLDEN)}  ({correct/len(GOLDEN):.0%})")
    return results, correct
```

**What to notice**

- Exact match is the right grader when there is one right answer: fastest, most reliable, no drift. The docs order the choice as code-based first, then LLM-based, with human grading as the slow, expensive fallback.
- The classifier runs on CHEAP (Haiku 4.5) with max_tokens 256: one word out, high volume. Model choice follows the task, and the eval is what proves the cheap model is good enough.

## Did the patch trade one failure for another?

```python
before = {t: ok for t, _, _, ok in r1}
```

## When exact match will not do

For open-ended output you need a judge, and **the judge itself must be
calibrated against human labels.** A judge produces consistent scores whether or
not it measures the thing you care about. Consistency is not accuracy. Prefer a
judge model different from the one that produced the answer, give it a clear
rubric, and let it reason before it scores.

```python
def judge(answer, criterion):
    # The judge thinks before answering; thinking counts toward max_tokens.
    r = client.messages.create(model=MODEL, max_tokens=2048,
        system=("You are grading one dimension only. Reply with a score 1-5 and one "
                "short reason. If you cannot tell from what you were given, reply UNKNOWN."),
        messages=[{"role": "user", "content": f"CRITERION: {criterion}\n\nANSWER:\n{answer}"}])
    return text_of(r).strip()

print(judge("Your refund was processed on Tuesday and should appear in 3-5 days.",
            "Does the answer give the customer a concrete next step and timeframe?"))
print()
print("Grade ONE dimension per judge. Give it an UNKNOWN escape hatch.")
print("Then validate it: run it over human-labelled cases and measure agreement.")
```

## Checkpoint

<Recall q="Rank the grading methods from cheapest to most expensive">

Code-based grading (exact or string match) is cheapest, fastest and most reliable. LLM-based grading is next: scalable and flexible but it costs tokens and must be validated. Human grading is the most flexible and the most expensive and slowest, so the docs say to avoid it where possible and use it to calibrate the others.

</Recall>

<Recall q="Why must an LLM judge be validated, and against what?">

A judge is itself a model whose scores can be consistent and still wrong, rewarding length, tone or its own biases instead of the criterion. Validate it against human-labelled examples of the same task and measure agreement before relying on it. Only then is the judge's score evidence about quality.

</Recall>

<Recall q="Which production signal reveals a silent regression that no error dashboard catches?">

Quality signals on real traffic: online eval scores, user feedback such as thumbs-down or escalations, and shifts in output distributions such as category mix. A regression in answer quality returns HTTP 200, so error rates and latency stay green. Sampling production outputs back into the eval set closes the loop.
