## Concept

The Model Context Protocol lets one server expose capabilities to any MCP host: Claude Code, Claude Desktop, the Messages API connector, or your own application. This objective tests the mechanics: which role each component plays, which primitive a capability should be, which transport a deployment implies, and how each Claude surface attaches a server. At 2.1% it is about one item; aim for fast, certain recognition.

**Scope boundary.** Whether to build an MCP server at all, rather than a tool or a Skill: <ObjLink id="agentic-customization" />. Descriptions, errors and approval for its tools: <ObjLink id="tool-implementation" />. Sharing `.mcp.json` and plugin packaging: <ObjLink id="configuration-management" />.

Not this:

- Prompt injection through tool results and vetting third-party servers as a security programme: <ObjLink id="ai-application-security" />.
- WebSockets versus SSE for your own app: <ObjLink id="technical-fundamentals" />.

<Callout type="key" title="The one idea">
Two lookups answer most MCP items. Who decides to use it names the primitive: the model (tool), the application (resource), the user (prompt). How the client reaches it names the transport: a command to run is stdio, a URL is Streamable HTTP. Everything else is detail around those two.
</Callout>

## Mechanism

### Server authoring

<SubskillAnchor id="mcp.authoring" />

The official SDKs turn functions into primitives so you never hand-write JSON-RPC.

- **Python** (`mcp` 2.x): `MCPServer` with `@mcp.tool()`, `@mcp.resource("scheme://{param}")` and `@mcp.prompt()`. Type hints become the input schema and the docstring becomes the description [Certain, executed]. In 2.x `FastMCP` was renamed `MCPServer`; `from mcp.server.fastmcp import FastMCP` raises `ModuleNotFoundError`, so pin `mcp>=2.3,<3` or `mcp<2` deliberately [Certain, executed 2026-10-06].
- **TypeScript**: v2 splits into `@modelcontextprotocol/server` and `/client`; `McpServer.registerTool`, `registerResource` and `registerPrompt` take Zod v4 or other Standard Schema validators. v1 (`@modelcontextprotocol/sdk`) still gets fixes [Certain, drifting].

Rules that transfer to stems: the docstring is a prompt; raise `ToolError` (Python) or return `isError: true` (TypeScript) for failures the model can fix; never write to stdout from a stdio server; give the server `instructions`, which Claude Code uses to decide when to search for its tools [Certain].

**Exam angle:** cue words "FastMCP import fails", "decorator", "registerTool". The distractor confuses an MCP server with a Skill file or hand-builds the protocol.

### Deployment

<SubskillAnchor id="mcp.deployment" />

| | Local server | Remote server |
|---|---|---|
| Transport | stdio, spawned by the host | Streamable HTTP at an `https://` URL |
| Runs as | The user, on their machine | A service you operate |
| Credentials | From the environment (the auth spec says stdio SHOULD NOT use it) | Authorization is OPTIONAL in the spec; when used, an OAuth 2.1-based flow with the server as resource server |
| Distribution | A package plus a command (`npx`, `uvx`, a path); Claude Desktop `.mcpb` extensions | A URL, often behind your gateway |
| Main risk | Supply chain: the server runs arbitrary code with your privileges | Network exposure: DNS rebinding, unauthenticated callers |

[Certain on the authorization and transport pages.] Streamable HTTP servers MUST validate the `Origin` header (403 if invalid), SHOULD bind to 127.0.0.1 when local, and SHOULD authenticate every connection; all servers MUST validate tool inputs, enforce access control, rate limit and sanitize outputs [Certain]. For local servers, pin versions and install only from trusted sources.

**Exam angle:** cue words "OAuth", "localhost", "0.0.0.0", "third-party server". The usual distractor claims OAuth is mandatory, or exposes a local HTTP server on all interfaces.

### Integration with Claude applications

<SubskillAnchor id="mcp.integration" />

| Surface | How a server is attached | Notes |
|---|---|---|
| Claude Code | `claude mcp add name -- command args` (stdio); `claude mcp add --transport http name url` | Scopes: local (default) and user in `~/.claude.json`, project in a committed `.mcp.json` that prompts for approval in interactive sessions; precedence local, project, user. `/mcp` for OAuth login. Tools appear as `mcp__server__tool` [Certain] |
| Claude Desktop | Desktop extensions (`.mcpb`) from Settings, Extensions, or `mcpServers` in `claude_desktop_config.json` | Sensitive manifest fields stored in the OS keychain; Team and Enterprise owners can allowlist extensions [Certain] |
| Messages API | MCP connector (beta `mcp-client-2025-11-20`): `mcp_servers` entry with `type: "url"` plus an `mcp_toolset` in `tools` | Remote HTTPS only, tools only; you obtain and refresh the OAuth token; allowlist or denylist per tool; not on Bedrock or Google Cloud [Certain] |
| Your own app | An MCP client from the SDK; convert listed tools into client tools | Full control, including local stdio servers |

In Claude Code all three primitives surface: Claude calls tools under permission rules, resources attach with `@server:scheme://path`, prompts run as `/mcp__server__prompt` [Certain]. MCP tool search is on by default [Certain].

<PostGuide since="2026-09">
The connector's `mcp-client-2026-09-15` beta records each server's tool list in an `mcp_tool_listing` block and lets you pin it in the toolset, so a server that changes its tools mid-conversation does not change what Claude sees.
</PostGuide>

**Exam angle:** cue words "share with the team", "Messages API", "local server", ".mcp.json". Distractors attach a stdio server to the API connector, or omit the `mcp_toolset` entry.

### Resources, tools and prompts

<SubskillAnchor id="mcp.primitives" />

| Primitive | Controlled by | What it is | Spec examples |
|---|---|---|---|
| Tools | Model | Functions the LLM calls to act or fetch | API POST requests, file writing |
| Resources | Application | Context data the client attaches and manages, addressed by URI | File contents, git history |
| Prompts | User | Templates invoked by explicit user choice | Slash commands, menu options |

[Certain, server overview.] The control column is the exam's favourite question: context the app attaches without the model asking is a resource; a workflow the user picks is a prompt; anything with side effects, or that the model decides to call, is a tool. Sampling, elicitation and roots are client features, not server primitives. Clients MUST treat tool annotations such as "read-only" as untrusted unless the server is trusted [Certain].

**Exam angle:** cue words "user selects", "attached automatically", "model decides". The distractor calls a resource "model-invoked" because the model reads it.

### Communication: stdio, sockets and HTTP

<SubskillAnchor id="mcp.transports" />

MCP messages are UTF-8 JSON-RPC 2.0 on every transport; a transport only defines framing and delivery [Certain].

- **stdio.** The client launches the server as a subprocess. One JSON-RPC message per line on stdin and stdout; stdout carries only MCP messages; stderr is for logs [Certain].
- **Streamable HTTP.** Each client message is an HTTP POST to a single MCP endpoint; the reply is a JSON object or a request-scoped SSE stream [Certain]. This is the remote transport.
- **HTTP+SSE** (separate SSE and POST endpoints) is deprecated since 2025-03-26 [Certain]. Claude Code still accepts `--transport sse` and labels it deprecated.

The guide's word **"sockets"** is not a third standard transport. Custom transports are allowed, and those over Unix domain sockets or TCP SHOULD reuse the stdio framing [Certain]; there is no standard WebSocket transport. Read "sockets" as the channel question: local process or byte stream versus networked HTTP endpoint [Likely interpretation].

**Exam angle:** cue words "spawned by the client", "reachable by URL", "SSE endpoint", "socket". Distractors offer HTTP+SSE as current or invent a WebSocket transport.

### Client versus server roles

<SubskillAnchor id="mcp.client-server" />

- **Host**: the application the user runs (Claude Desktop, Claude Code, your agent). It creates clients, enforces consent and security policy, holds the conversation, and coordinates the LLM [Certain].
- **Client**: created by the host, one per server, 1:1 [Certain].
- **Server**: exposes primitives, local or remote, and should not be able to read the whole conversation or see into other servers [Certain].

Roles are positions, not products: `claude mcp serve` runs Claude Code as an MCP server for another host, which must then supply its own approval prompts [Certain].

Under revision 2025-11-25 (current when the guide was written) every connection starts with a handshake: the client sends `initialize` with `protocolVersion`, its capabilities (sampling, elicitation, roots) and `clientInfo`; the server answers with its capabilities (tools, resources, prompts, `listChanged`) and `serverInfo`; the client sends `notifications/initialized`. Both sides then use only negotiated capabilities [Certain].

<PostGuide since="2026-07">
Revision 2026-07-28 makes MCP stateless: no `initialize` handshake or `Mcp-Session-Id`; each request carries version and capabilities in `_meta`; servers implement `server/discover`; Roots, Sampling and Logging are deprecated. Lab 08 negotiated this revision. Primitives and transports are unchanged; answer exam items with the handshake model.
</PostGuide>

**Exam angle:** cue words "host", "one client per server", "capability negotiation", "initialize". Distractors let one client talk to many servers, or let a server read the full conversation.

## Decision table

| If the stem says... | Choose | Why the runner-up loses |
|---|---|---|
| The user picks a saved "incident triage" workflow from a menu | A prompt | A tool is invoked by the model, not chosen by the user |
| The app should attach the on-call runbook as context automatically | A resource | Making it a tool hands the decision to the model |
| Claude should decide when to re-run a failed job | A tool | Resources are read-only context, not actions |
| The server ships as `npx` or `uvx` and is launched by the host | stdio | Streamable HTTP needs a URL and a listening service |
| A shared service the whole company reaches at an https URL | Streamable HTTP with authentication | HTTP+SSE is deprecated; stdio cannot cross the network |
| Backend on the Messages API must use the team's local stdio server | Host it as a remote Streamable HTTP server for the connector, or run an MCP client in the backend | The connector reaches only public HTTPS servers |
| Connector request rejected with only `mcp_servers` set | Add an `mcp_toolset` entry naming that server | Each server must be referenced by exactly one toolset |
| A local stdio server connects, then fails on the first call | Move logging from stdout to stderr | Restarting or switching transport does not stop stdout pollution |
| The team wants a server config committed for everyone | `claude mcp add --scope project` (writes `.mcp.json`) | Local and user scopes live in `~/.claude.json` and are not shared |
| "Does MCP require OAuth 2.1?" | No: authorization is optional; HTTP servers should authenticate, stdio uses the environment | "Always OAuth" misreads an optional, HTTP-only specification |

## Worked walkthrough

<Walkthrough title="Scenario: a laptop MCP server and a backend service">

<Step title="Read the scenario">
An analytics team built `lineage-mcp`, a Python server answering "what feeds this table?". Engineers run it in Claude Code via `claude mcp add lineage -- uvx lineage-mcp`. A product team wants their backend, which calls the Messages API, to use the same tools; their request with `mcp_servers` pointing at `stdio://lineage-mcp` is rejected. What should they do?
</Step>

<Step title="Find the constraint">
"Messages API" plus a server launched by command. With the connector, Anthropic connects to your server over the network: `https://` URLs only, tools only. A stdio subprocess on a laptop has no reachable address.
</Step>

<Step title="Eliminate the distractors">
- "Add the missing `mcp_toolset` entry." Necessary for any connector call, but the URL still is not reachable.
- "Switch the server to HTTP+SSE." The connector would accept it, but it is the deprecated transport and still needs public hosting, which is the real change.
- "Paste the server's Python functions into the backend's system prompt." A prompt cannot execute code; tools need a definition and an executor.
</Step>

<Step title="Choose">
Run `lineage-mcp` as a remote Streamable HTTP service at an `https://` URL that validates `Origin` and authenticates callers. Point `mcp_servers` at it with an `authorization_token`, add the matching `mcp_toolset`, and allowlist the read tools. If it cannot be exposed, the backend runs its own MCP client and passes the tools to Claude as client tools.
</Step>

<Step title="The deciding cue">
"Messages API" next to "launched by a command". A connector needs a reachable HTTPS URL; a command implies stdio and a local host process.
</Step>

</Walkthrough>

## Code

**One server, three primitives, three controllers.** Python executed with `mcp` 2.3.0 (Lab 08's API); `ToolError` becomes an `isError` result.

```python
# pip install "mcp>=2.3,<3"   (2.x renamed FastMCP to MCPServer)
from mcp.server.mcpserver import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp = MCPServer("pipeline-ops", instructions="Look up nightly ELT job runs and their runbooks.")

RUNS = {"run-8812": ("orders_daily", "FAILED", "schema drift on column order_ts"),
        "run-8813": ("customers_scd2", "SUCCEEDED", None)}
RUNBOOKS = {"orders_daily": "1. Check upstream schema registry. 2. Re-run from bronze."}

@mcp.tool()                                # MODEL decides when to call it
def jobs_get_run(run_id: str) -> str:
    """Return status and failure reason for ONE job run. Use when the user
    names a run ID (format run-NNNN) or asks why a specific run failed.
    Do NOT use to list runs or to re-run anything; this tool is read-only."""
    if run_id not in RUNS:
        raise ToolError(f"Unknown run_id {run_id!r}. Expected format run-NNNN, "
                        f"for example {next(iter(RUNS))}.")
    job, status, reason = RUNS[run_id]
    return f"{run_id} job={job} status={status} reason={reason or 'n/a'}"

@mcp.resource("runbook://{job}")           # APPLICATION decides when to attach it
def runbook(job: str) -> str:
    """On-call runbook for a job, as read-only reference text."""
    return RUNBOOKS.get(job, "No runbook on file.")

@mcp.prompt()                              # USER picks it, e.g. as a slash command
def triage_failed_run(run_id: str) -> str:
    """Template: triage a failed run end to end."""
    return f"Triage {run_id}: get the run, read its job's runbook, propose a fix."

if __name__ == "__main__":
    mcp.run()                              # stdio: the host spawns this process
    # mcp.run(transport="streamable-http")  # remote: serves /mcp on 127.0.0.1:8000
```

```typescript
// npm install @modelcontextprotocol/server zod   (SDK v2; v1 was @modelcontextprotocol/sdk)
import { McpServer, ResourceTemplate } from "@modelcontextprotocol/server";
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import * as z from "zod/v4";

const server = new McpServer({ name: "pipeline-ops", version: "1.0.0" });

const RUNS: Record<string, [string, string, string | null]> = {
  "run-8812": ["orders_daily", "FAILED", "schema drift on column order_ts"],
  "run-8813": ["customers_scd2", "SUCCEEDED", null],
};
const RUNBOOKS: Record<string, string> = {
  orders_daily: "1. Check upstream schema registry. 2. Re-run from bronze.",
};

server.registerTool( // MODEL decides when to call it
  "jobs_get_run",
  {
    description:
      "Return status and failure reason for ONE job run. Use when the user names a run ID " +
      "(format run-NNNN) or asks why a specific run failed. Do NOT use to list runs or to " +
      "re-run anything; this tool is read-only.",
    inputSchema: z.object({ run_id: z.string() }),
  },
  async ({ run_id }) => {
    const run = RUNS[run_id];
    if (!run) {
      return { isError: true, content: [{ type: "text", text: `Unknown run_id '${run_id}'. Expected format run-NNNN, for example run-8812.` }] };
    }
    const [job, status, reason] = run;
    return { content: [{ type: "text", text: `${run_id} job=${job} status=${status} reason=${reason ?? "n/a"}` }] };
  },
);

server.registerResource( // APPLICATION decides when to attach it
  "runbook",
  new ResourceTemplate("runbook://{job}", { list: undefined }),
  { description: "On-call runbook for a job, as read-only reference text.", mimeType: "text/plain" },
  async (uri, { job }) => ({
    contents: [{ uri: uri.href, text: RUNBOOKS[String(job)] ?? "No runbook on file." }],
  }),
);

server.registerPrompt( // USER picks it, e.g. as a slash command
  "triage_failed_run",
  { description: "Template: triage a failed run end to end.", argsSchema: z.object({ run_id: z.string() }) },
  ({ run_id }) => ({
    messages: [{ role: "user", content: { type: "text", text: `Triage ${run_id}: get the run, read its job's runbook, propose a fix.` } }],
  }),
);

await server.connect(new StdioServerTransport()); // stdio: the host spawns this process
```

```python
import os
import anthropic

client = anthropic.Anthropic()
resp = client.beta.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=2048,
    betas=["mcp-client-2025-11-20"],
    mcp_servers=[{"type": "url", "url": "https://mcp.example.internal/mcp", "name": "pipeline-ops",
                  "authorization_token": os.environ["PIPELINE_OPS_TOKEN"]}],
    tools=[{"type": "mcp_toolset", "mcp_server_name": "pipeline-ops",
            "default_config": {"enabled": False},                  # allowlist mode
            "configs": {"jobs_get_run": {"enabled": True}}}],
    messages=[{"role": "user", "content": "Why did run-8812 fail?"}],
)
for block in resp.content:  # mcp_tool_use / mcp_tool_result blocks precede the answer
    if block.type == "text":
        print(block.text)
```

## Recall checks

<Recall q="Name the three MCP server primitives and who controls each.">
Tools are model-controlled: Claude decides when to call them. Resources are application-controlled: the host decides what context to attach. Prompts are user-controlled: templates the user picks, often as slash commands.
</Recall>

<Recall q="A server's docs give you a URL, another gives you an npx command. Which transport is each, and which one is deprecated?">
The URL is Streamable HTTP (POSTs to one endpoint, JSON or request-scoped SSE replies); the command is stdio (the host spawns a subprocess). The older two-endpoint HTTP+SSE transport is the deprecated one.
</Recall>

<Recall q="Is authorization required by the MCP specification?">
No, it is optional. HTTP servers that use it follow an OAuth 2.1-based flow as a resource server; stdio servers should take credentials from the environment instead. Remote servers should still authenticate callers and validate the Origin header.
</Recall>

<Recall q="What two things does a Messages API request need to use an MCP server, and what kind of server can it reach?">
An mcp_servers entry (type url, https URL, name, optional authorization_token) plus an mcp_toolset in tools naming it, with the beta header. It reaches only remote HTTPS servers, and only their tools.
</Recall>

<Recall q="What do the host, the client and the server each do, and what happens in the 2025-11-25 initialize handshake?">
The host runs the conversation, creates one client per server and enforces consent; each client talks to one server; the server exposes primitives without seeing the conversation. The client sends initialize with version and capabilities, the server replies with its own, the client sends notifications/initialized.
</Recall>
