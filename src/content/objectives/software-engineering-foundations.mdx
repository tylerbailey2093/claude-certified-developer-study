## Concept

This objective is ordinary production engineering. The guide lists REST APIs, JSON, asynchronous programming, version control, SDLC integration, code review, and small- and large-scale refactoring, introduced with "including", so treat the list as examples of a wider skill: would you ship a Claude-backed service with the same discipline as any other networked system? Candidates who studied only Claude features report being caught out here, because a large share of items read like generic backend questions with a Claude call somewhere in the stem.

The stem usually hides one engineering fact that decides the answer: the HTTP method is not idempotent, the integer is larger than 2^53, the coroutines were all created at once, the refactor mixes behaviour changes with structure, the reviewer is a model with no authority to approve. Distractors are built from things that sound responsible (another retry loop, a bigger timeout, a stronger prompt, a one-shot rewrite) but fail for a nameable mechanical reason.

The Claude-specific overlay is thin but scored: the SDKs already implement retries, backoff, timeouts and cursor pagination, so reimplementing them is the classic wrong answer; prompts, tool schemas, eval sets and `CLAUDE.md` are versioned code; and an eval suite is a release gate in CI the same way a unit test suite is.

<Callout type="key" title="The point-winning idea">
Every question in this objective is answered by asking what the platform, the protocol, or a deterministic tool already guarantees, and refusing to rebuild or bypass it. HTTP defines which retries are safe; the SDK already retries; JSON Schema defines shape but not meaning; a semaphore, not `async`, bounds concurrency; tests and small steps, not confidence, make a refactor safe; a human, not a review bot, approves the merge.

## Mechanism

### REST APIs

<SubskillAnchor id="swe.rest" />

**Method semantics decide retry safety.** A method is *safe* if it is read-only from the client's point of view (GET, HEAD, OPTIONS). A method is *idempotent* if sending the same request N times has the same intended effect on the server as sending it once: all safe methods plus PUT and DELETE. POST and PATCH are not guaranteed to be idempotent. Idempotent does not mean "same response": a second DELETE typically returns 404 where the first returned 200, and the server may still log each call [Certain, MDN].

| Method | Safe | Idempotent | Typical use | Blind retry after timeout |
|---|---|---|---|---|
| GET, HEAD, OPTIONS | yes | yes | read | safe |
| PUT | no | yes | replace at a client-known URI | safe (same final state) |
| DELETE | no | yes | remove | safe (second call may 404) |
| POST | no | no | create, trigger an action | unsafe without an idempotency key |
| PATCH | no | not guaranteed | partial update | unsafe unless the patch is absolute |

**A timeout is an unknown outcome, not a failure.** The request may have committed before the connection dropped. For idempotent methods, retry. For POST, attach an `Idempotency-Key` header: the client generates one random key (a UUID) per *logical operation* and reuses it on every retry; the server stores the first response under that key and replays it. The IETF httpapi draft specifies that reusing a key with a different payload gets 422 and a retry that arrives while the original is still processing gets 409 [Certain that the draft says this; Likely it is still a draft, not an RFC]. The alternative design is to let the client choose the resource ID and use PUT, which is idempotent by definition.

**Status code families and retryability.**

| Code | Meaning | Retry? |
|---|---|---|
| 400, 401, 402, 403, 404, 413, 422 | request is wrong, unauthenticated, unpaid, forbidden, missing, too large, semantically invalid | No. Fix the request. |
| 408 | client was too slow | Yes |
| 409 | conflicts with current resource state | Only after re-reading state; the Anthropic SDKs retry it [Certain] |
| 412 | `If-Match` precondition failed (someone else changed it) | Re-fetch, merge, retry with new ETag |
| 429 | too many requests | Yes, after `Retry-After` |
| 500, 502, 503, 504 | server or gateway problem | Yes, with backoff |
| 529 | Anthropic overloaded | Yes, with backoff |

`Retry-After` carries either delay-seconds or an HTTP date and accompanies 429 and 503 (and 301) [Certain, MDN]. On the Claude API, a 429 carries `retry-after` in seconds, and `anthropic-ratelimit-*` headers report limit, remaining and reset (RFC 3339) for requests, input tokens and output tokens [Certain]. One exception worth knowing as engineering knowledge: the monthly spend-cap 429 has no `retry-after` and retrying cannot succeed until access resumes; `error.details.error_code` is `enforced_spend_limit_reached` [Certain for the docs today; Likely not exam content].

**What the SDK already does.** The official SDKs retry connection errors, 408, 409, 429 and 5xx twice by default with exponential backoff, honoring `retry-after`, and time out after 10 minutes by default (seconds in Python, milliseconds in TypeScript). Timeouts are retried too, so worst-case wall clock for one call is roughly `timeout x (max_retries + 1)` plus backoff [Certain]. Every response carries a `request-id` header, surfaced as `_request_id`; log it, because it is what support needs [Certain].

**Concurrency control on writes.** Two editors read version 7 and both PUT. Without a guard, the second silently overwrites the first (the lost update). `If-Match: "<etag>"` makes the write conditional; the loser gets 412 and must re-read [Certain, MDN]. 409 is the more general "conflicts with current state" signal [Certain, MDN].

**Pagination.** Offset pagination (`?offset=200&limit=100`) is simple and supports jumping to page N, but rows inserted or deleted while you page cause skips and duplicates, and deep offsets get slow because the database still walks the skipped rows. Cursor pagination returns an opaque pointer to the last item (`after_id`, `next_cursor`) and asks for "items after this one": stable under concurrent writes and constant-cost per page, but no random access. Anthropic list endpoints are cursor-based; the SDKs auto-paginate with `for` / `async for` / `for await`, or expose `has_next_page()` and `get_next_page()` plus the cursor (`last_id`) for manual control [Certain].

**Versioning strategies.** Path (`/v1/`), header, query parameter, or media type. Anthropic uses both: a `/v1` path and a required dated `anthropic-version` header (the SDKs send `2023-06-01`). Within a version Anthropic preserves existing inputs and outputs but may add optional inputs, output fields, and new enum-like values such as streaming event types [Certain]. The engineering consequence is the *tolerant reader*: ignore unknown fields, and give every `switch` on a server enum a default branch. A client that crashes on an unrecognised `stop_reason` or event type is the bug, not the API.

**Rate limiting.** The Claude API uses a token bucket that replenishes continuously, measured as RPM, input tokens per minute and output tokens per minute per model; a 60 RPM limit may be enforced as 1 per second, so bursts fail even under the per-minute number, and a sharp ramp can hit separate acceleration limits [Certain]. For most models cached input reads do not count toward ITPM [Certain], which is why caching raises effective throughput.

**Exam angle:** cues are "duplicate records after retries" (idempotency key), "returns 400/401/403" (do not retry), "429 during bursts" (bound concurrency, honour `Retry-After`), "two users overwrite each other" (`If-Match`/412), "items skipped while paging" (cursor). The usual distractor adds a retry loop or raises a timeout.

### JSON

<SubskillAnchor id="swe.json" />

JSON has six value kinds: object, array, string, number, boolean, null. Everything else is convention, and the conventions are where bugs live.

| Pitfall | Mechanism | Fix |
|---|---|---|
| Big integers | JavaScript parses every JSON number as an IEEE 754 double; integers beyond 2^53 - 1 (9007199254740991) silently round, so `MAX_SAFE_INTEGER + 1 === MAX_SAFE_INTEGER + 2` is true [Certain, MDN] | Send IDs and money as strings, or revive to `BigInt` via the reviver's `context.source` [Certain, MDN] |
| Floats | `0.1 + 0.2` is not `0.3` in binary floating point | Integer minor units (`amount_cents`) or decimal strings; Python `json.loads(..., parse_float=Decimal)` [Certain] |
| Dates | No date type | RFC 3339 strings with an offset; JSON Schema `format: "date-time"` uses RFC 3339 [Certain] |
| NaN and Infinity | Not valid JSON, but Python emits them by default (`allow_nan=True`) [Certain] | `allow_nan=False` at boundaries |
| Duplicate keys | Python keeps the last value [Certain]; other parsers differ | Reject with `object_pairs_hook` where it matters |
| Encoding | JSON exchanged between systems is UTF-8; Python escapes non-ASCII by default (`ensure_ascii=True`) [Certain for Python] | Decode bytes as UTF-8 explicitly |
| Python int vs JS number | Python ints are arbitrary precision, so a Python service round-trips an ID that a TypeScript client corrupts | Same contract on both sides: strings for identifiers |

**JSON Schema basics.** `type`, `properties`, `required`, `additionalProperties`, `enum`, `items`. Two defaults catch people: properties are optional unless listed in `required` (and a `null` value does not satisfy "required"; the key must be present), and additional properties are allowed unless `additionalProperties: false` [Certain]. `format` is an annotation by default; validators need not enforce it [Certain]. Note that JSON Schema has `integer` as a schema-level concept although JSON itself has only `number`.

**Validate at the boundary.** Parse once where data enters your process (HTTP handler, queue consumer, model output, tool input), validate against the schema plus domain rules, then pass typed objects inward. Model output is an input from an untrusted source like any other.

**Structured outputs narrow, but do not remove, that job.** `output_config.format` with a JSON schema uses constrained decoding: output is valid JSON with the required fields and types [Certain]. It does not enforce `minimum`/`maximum`, string lengths, or `minItems` above 1; `additionalProperties` must be `false`; enum casing is not guaranteed; and a `refusal` or `max_tokens` stop can still produce output that does not match [Certain]. The SDK parse helpers move unsupported constraints into descriptions and re-check them client-side [Certain]. So domain checks (positive amounts, dates in range, foreign keys exist) remain your code.

**Streaming and partial JSON.** When a `tool_use` block streams, each `input_json_delta` carries a `partial_json` string fragment; accumulate the fragments and parse at `content_block_stop`, or use the SDK streaming helpers, which expose the parsed input incrementally [Certain]. Never `JSON.parse` an individual fragment. New event types may appear, so ignore unknown ones [Certain].

**Exam angle:** "IDs off by one in the browser" (big integers), "valid JSON but wrong values" (domain validation), "must always be valid JSON" (structured outputs, not prompt wording), "parse error mid-stream" (accumulate until block stop). Distractor: a stronger prompt instruction.

### Asynchronous programming

<SubskillAnchor id="swe.async" />

Claude calls are slow, I/O-bound and independent, which is the textbook case for async concurrency. The failure modes are also textbook.

**Python.** `AsyncAnthropic` exposes the same interface as `Anthropic` with `await`; an optional `aiohttp` backend improves high-concurrency performance [Certain]. Coroutines do nothing until awaited or scheduled; `create_task` schedules them, and the event loop keeps only weak references to tasks, so unreferenced tasks can vanish mid-flight [Certain]. Prefer `asyncio.TaskGroup` (structured concurrency): if one task raises, the rest are cancelled and an `ExceptionGroup` is raised. `gather` without `return_exceptions=True` propagates the first exception *without* cancelling the others [Certain]. So decide per job: all-or-nothing (TaskGroup, let errors escape) or best-effort (catch per item inside the task and record failures).

**TypeScript.** Every SDK call returns a promise, and a promise starts executing when created. `await Promise.all(items.map(call))` therefore launches every request at once. `Promise.all` rejects on the first rejection; `Promise.allSettled` waits for all and returns `{status, value | reason}` per item [Certain, MDN].

**Bounded concurrency is the fix for both.** An `asyncio.Semaphore(16)` around the call, or N workers draining a shared iterator in TypeScript, caps in-flight requests no matter how many items are queued. Ramp gradually: the docs warn that a sharp increase can hit acceleration limits even under your steady-state limit [Certain].

**Backpressure.** A semaphore bounds HTTP in flight but not memory: creating 2 million task objects up front still costs RAM. When producers outpace consumers, use a bounded queue (`asyncio.Queue(maxsize=...)`) so `put` blocks the producer, and a fixed set of consumer workers. Backpressure means slowness propagates upstream instead of accumulating as an unbounded backlog.

**Timeouts and cancellation.** Three layers: the SDK per-request timeout (default 10 minutes, retried), a per-item budget, and a whole-job deadline. `asyncio.timeout()` (3.11+) cancels the enclosed work and raises `TimeoutError` outside the block; if you catch `CancelledError` for cleanup, re-raise it [Certain]. In TypeScript, pass a per-request `{ timeout }` option and break out of or abort streams (`stream.controller.abort()`) [Certain]. For long generations, stream rather than raising the non-streaming timeout: the SDKs refuse non-streaming requests expected to exceed about 10 minutes because idle connections get dropped [Certain].

**When async beats batch, and vice versa.**

| Need | Async concurrency | Message Batches API |
|---|---|---|
| Result latency | seconds | most batches under 1 hour, up to 24 hours, then expire [Certain] |
| Price | standard | 50% off [Certain] |
| Dependent steps (tool loops, chained calls) | yes | no; each request independent |
| Volume ceiling | your RPM/ITPM/OTPM | 100,000 requests or 256 MB per batch, separate queue limits [Certain] |
| Ordering | you control it | results unordered; join on `custom_id` [Certain] |

Async is the answer when a user or downstream step is waiting; batch is the answer when nobody is. Both are scored; batch mechanics belong to <ObjLink id="claude-api-mechanics" />.

**Exam angle:** "429s spike at job start" or "works for 50 items, fails for 5,000" points to a semaphore or worker pool. Distractors: switch models, raise `max_retries`, add `sleep`. "User waiting" rules out batch; "next step depends on the previous answer" rules out batch too.

### Version control

<SubskillAnchor id="swe.vcs" />

**Branching strategies.** Long-running branches hold code at different stability levels (for example `main` and `develop`) and commits graduate between them; topic branches are short-lived, one concern each, which makes review easy because every change in the branch relates to one topic [Certain, Pro Git]. Trunk-based development pushes topic branches to their limit: branches live hours or a day, merge to `main` behind feature flags, and `main` is always releasable. For a Claude application that ships prompt changes frequently, short-lived branches plus flags beat long-lived release branches, because prompt behaviour drifts fast and long branches accumulate untestable combinations.

**PR flow.** Branch, commit small logical steps, open a pull request, CI runs, reviewers approve, merge (squash or merge commit by team convention), delete the branch. Protect `main` so merges require passing checks and human approval.

**Conventional Commits** structure messages as `type(scope): description` with optional body and footers. `fix` maps to a SemVer PATCH, `feat` to MINOR, and a `BREAKING CHANGE:` footer or `!` after the type to MAJOR; other types include `build`, `chore`, `ci`, `docs`, `style`, `refactor`, `perf`, `test` [Certain]. The point is machine-readable history: changelogs and version bumps can be generated.

**Semantic Versioning.** MAJOR for incompatible API changes, MINOR for backward-compatible features, PATCH for backward-compatible fixes; `0.y.z` is initial development where anything may change; pre-release (`1.0.0-rc.1`) sorts before the release; a released version's contents must never be modified, any change is a new version [Certain]. Note that the Anthropic SDKs say they generally follow SemVer but may ship some backward-incompatible changes (type-only, internal) in minor versions [Certain], so pin and read changelogs.

**Tagging releases.** Tag the exact commit you deployed (`git tag -a v2.3.0 -m ...`, then push tags). Annotated tags carry author, date and message; the tag is the anchor for rollback and for "which prompt version produced this output".

**What belongs in the repo.** Everything that determines behaviour: source, lockfiles, prompts and system prompts as files, tool schemas, eval datasets and graders, `CLAUDE.md`, shared `.claude/settings.json`, `.mcp.json`, CI workflows. A prompt edit is a behaviour change and deserves a diff, a review and a tag. Personal overrides such as `.claude/settings.local.json` stay out [Likely].

**What never belongs.** Secrets. The Claude Code GitHub Actions docs say never commit API keys or OAuth tokens and reference them as `secrets.ANTHROPIC_API_KEY` [Certain]; the Python SDK docs suggest a `.env` file so the key is not in source control [Certain]. Git history is permanent and cloned everywhere: a committed key is a leaked key even after a revert, so the response is rotation, not deletion. Key management itself is <ObjLink id="identity-secrets-and-key-management" />.

**Exam angle:** "which prompt was live when quality dropped" (prompts versioned and releases tagged), "key found in a commit" (rotate, then scan and block in CI). Distractor: "delete the file in a new commit".

### SDLC integration

<SubskillAnchor id="swe.sdlc" />

<Flow title="Release path for a prompt or model change" steps={[{label: "Lint, types, unit tests", kind: "guard", note: "Claude mocked, no network"}, {label: "Eval suite gate", kind: "guard", note: "pass rate vs baseline"}, {label: "Human PR review", kind: "decision"}, {label: "Canary behind flag", kind: "api", note: "small % of traffic"}, {label: "Full rollout", kind: "api", note: "flag flip, instant rollback"}]} caption="Each gate is deterministic code or an accountable human. Nothing is gated on the model saying it is fine." />

**CI gates.** Fast deterministic checks first (format, lint, type check, unit tests with the Claude client stubbed so tests are free and repeatable), then contract tests that validate fixtures against the JSON schemas your tools and outputs use, then the eval suite.

**Evals as tests.** A prompt or model change can degrade quality without throwing an exception, so the error-rate dashboard stays green. An eval suite is a fixed, task-specific dataset with automated grading (exact match, code-graded checks, or LLM-graded rubrics), and Anthropic's guidance favours many automatically graded cases over a few hand-graded ones [Certain]. Because outputs vary run to run, gate on an aggregate (pass rate at or above baseline minus a tolerance), not on byte-equal snapshots, and run the eval only when prompt, model or tool-schema paths change to control cost.

<PostGuide>
On current models, non-default `temperature`, `top_p` and `top_k` return 400, so "set temperature to 0 for deterministic CI" is no longer available. Treat eval runs as statistical: repeat cases, compare pass rates, and pin the model ID. Engineering knowledge, not a basis for exam answers.
</PostGuide>

**Claude Code in CI.** `claude -p "..."` runs non-interactively and exits non-zero on failure; `--output-format json` returns a result object, `--json-schema` adds a `structured_output` field, and `--allowedTools` pre-approves only the tools a job needs [Certain]. `--permission-mode dontAsk` denies anything not pre-approved, which is what an unattended run wants, and `--bare` skips auto-discovered hooks, plugins, MCP servers and `CLAUDE.md` so CI behaves the same on every machine [Certain for current docs; Likely for exam purposes, flags drift]. The GitHub Action `anthropics/claude-code-action@v1` runs interactively on `@claude` mentions or in automation mode when given a `prompt`; it requires the triggering user to have write access and rejects bot actors unless allow-listed; cost controls include `--max-turns` in `claude_args`, workflow timeouts and concurrency limits [Certain].

**Staged rollout and feature flags.** Deploy is not release. Ship the new prompt dark behind a flag, enable it for internal users, then a canary percentage, while watching quality signals (eval scores on sampled traffic, user feedback, refusal and `max_tokens` rates, cost per task) alongside latency and errors. A flag is also the kill switch: rolling back a prompt should be a config flip, not a redeploy. Life-cycle framing for these practices sits in <ObjLink id="systems-life-cycle" />; production guardrails sit in <ObjLink id="guardrails-and-safe-deployment" />.

**Exam angle:** "quality regressed but no errors" (eval gate), "roll back in seconds" (feature flag), "same result on every CI runner" (pinned model, bare/headless config, stubbed unit tests). Distractor: "ask Claude in the prompt to be careful".

### Code review

<SubskillAnchor id="swe.code-review" />

**What reviewers check.** Correctness against the requirement, including edge cases and error paths; tests that would fail if the change were wrong; security (input validation, authorization, secrets, injection, logging of PII); API and schema compatibility (is this a breaking change, does it need a MAJOR bump or an expand and contract migration); concurrency and resource use; observability; scope (does the PR do one thing). Small PRs get real review; 2,000-line PRs get rubber stamps.

**AI-assisted review.** Claude Code's managed Code Review runs several agents over the diff with full-repo context, verifies candidate findings, and posts inline comments tagged Important, Nit or Pre-existing; findings never approve or block a PR, and its check run always completes neutral so it cannot gate merges through branch protection [Certain for current docs; Likely for exam, research preview]. `CLAUDE.md` violations surface as nits; a `REVIEW.md` tunes severity, skip rules and repo-specific checks [Certain]. Locally, `/code-review` reviews a diff in a fresh subagent context [Certain]. Anthropic's own best practices recommend a writer/reviewer split across sessions because a fresh context is not biased toward code it just wrote [Certain].

**Limits.** A reviewer asked to find gaps will usually report some even when the work is sound, and chasing every finding produces over-engineering [Certain]. AI review cannot know unwritten business intent, misses issues outside the diff it was shown, and produces both false positives and false negatives. It is one layer, not the gate.

**Human in the loop for generated code.** Apply the same bar to Claude-written code as to human code. The merging human owns it. Fluent code hides wrong assumptions well: a retry loop duplicated on top of the SDK, a schema that validates but inverts two fields, an `except Exception: pass`. Require evidence (test output, the command run) rather than an assertion that it works [Certain, best practices].

**Exam angle:** "AI-generated PR, can review be lighter" (no), "automated reviewer approved it" (it cannot; humans approve), "must block merges on X" (a deterministic CI check or branch protection rule, not a review bot comment or a prompt).

### Small- and large-scale refactoring

<SubskillAnchor id="swe.refactoring" />

Refactoring changes structure without changing observable behaviour. The definition is the safety rule: if behaviour changes in the same step, it is not a refactor and cannot be verified as one.

**Tests first.** You need a test that pins current behaviour before moving code. For legacy code with no tests, write *characterization tests*: feed representative inputs, record what the code does today (bugs included), and assert that. They document reality, not intent, and turn "did I break it?" into a red/green answer.

**Small-scale.** Rename, extract function, inline variable, introduce parameter object, replace conditional with polymorphism. Use the IDE or language server for mechanical renames (they are scope-aware; text search is not), keep each step green, commit each step separately.

**Large-scale.**

| Technique | Use when | How it stays safe |
|---|---|---|
| Strangler fig | replacing a legacy service or module | a facade routes one capability at a time to the new implementation; the old one shrinks until removed |
| Branch by abstraction | swapping an internal dependency on trunk | introduce an interface, move callers to it, swap the implementation behind it, delete the old one |
| Expand and contract (parallel change) | changing an API or DB schema with live clients | add the new field/endpoint, migrate readers and writers, then remove the old one in a later release |
| Codemod | the same mechanical edit across hundreds of files | an AST-based transform is deterministic, re-runnable and reviewable as a script plus a sample diff |

Split large refactors into PRs that are each behaviour-preserving and green, with refactor commits separate from feature commits, so `git bisect` and reverts stay surgical.

**Using Claude Code safely.** Plan before editing when the change spans files or the approach is unclear: plan mode reads and proposes without writing [Certain]. Delegate investigation to subagents so exploring hundreds of files does not fill the main context [Certain]. Give Claude a check it can run (tests, build, type check) so it iterates to green instead of to "looks done" [Certain]. For a large migration, generate the file list, run on two or three files, refine the prompt, then fan out with `claude -p` in a loop using `--allowedTools` and `--permission-mode dontAsk`, or `/batch`, which splits work across subagents in separate worktrees [Certain for current docs]. Checkpoints only capture edits made through Claude's file tools, not Bash, and are not a replacement for git [Certain]: commit before each step. When a rule must hold every time (tests run after every edit, no writes to `migrations/`), use a hook, not a `CLAUDE.md` line.

For repeated mechanical patterns, prefer having Claude write a codemod and running the codemod, over having Claude hand-edit 400 files: the script is deterministic and reviewable once.

**Exam angle:** "no tests exist" (characterization tests first), "replace the legacy system without downtime" (strangler fig), "rename a field used by external clients" (expand and contract), "same edit across 600 files" (codemod or tested fan-out). Distractor: the big-bang rewrite.

## Decision table

| If the stem says... | Choose | Why the runner-up loses |
|---|---|---|
| Team wraps `messages.create` in a custom retry decorator "to be safe" | Remove it; tune `max_retries` on the client if needed | A second layer multiplies attempts during the very incident it targets; the SDK already backs off and honours `retry-after` |
| Duplicate tickets appear after network timeouts on a create endpoint | Idempotency key reused across retries | Raising the timeout narrows the window but cannot remove it; disabling retries trades duplicates for lost writes |
| A call returns 400, 401, 403, 404 or 413 | Fix the request; do not retry | Retrying a request that is wrong returns the same error and burns rate limit |
| 429s cluster in the first seconds of a large job | Semaphore or worker pool, ramp gradually | More retries or a different model leave the burst intact; acceleration limits punish sharp ramps |
| User is waiting on the result | Async concurrency with streaming | Batch is cheaper but results can take up to 24 hours |
| Output "must always" parse as JSON with required fields | `output_config.format` JSON schema | Prompt wording is a request, not a guarantee |
| Schema-valid output has out-of-range numbers | Domain validation after parsing | Schema `minimum`/`maximum` is not enforced by structured outputs |
| Order IDs are wrong by one in the browser only | Serialize IDs as strings | Python ints are exact; the JS double rounds above 2^53 - 1 |
| Two admins overwrite each other's edits | `If-Match` with ETag, handle 412 | Last-write-wins loses data silently |
| Prompt change degraded answers, error rate unchanged | Eval suite as a CI gate plus flagged canary | Unit tests and error dashboards do not measure quality |
| Need to roll back a bad prompt in seconds | Feature flag | A revert plus redeploy takes minutes and redeploys everything else too |
| Claude-written PR "passed evals so review can be light" | Full human review | Provenance does not change risk; the merger is accountable |
| Legacy module, no tests, must be restructured | Characterization tests, then small green steps | Refactoring without a behaviour pin is guessing |
| Replace an old service while it keeps serving | Strangler fig behind a facade | Big-bang cutover has no partial rollback |
| API key found in git history | Rotate the key, then add secret scanning | A deleting commit leaves the key in every clone |

<Walkthrough title="Scenario: duplicate refunds from a support agent">

<Step title="Read the scenario">
A support assistant uses Claude with a client tool, `issue_refund`, that calls the company's payments REST service with `POST /v1/refunds`. The tool handler uses a plain HTTP client with three retries on timeouts. During a payments-service slowdown, finance finds customers refunded two or three times. The requirement from finance: a refund must never be applied twice. Which change fixes this?

A. Add to the system prompt: "Never call issue_refund more than once per conversation."
B. Generate an idempotency key once per refund decision, send it as `Idempotency-Key` on every attempt, and have the payments service replay the stored result for a repeated key.
C. Raise the HTTP client timeout from 5 to 60 seconds.
D. Remove the retries from the tool handler entirely.
</Step>

<Step title="Find the constraint">
Two buried facts decide it. First, the duplicates appear during a slowdown, so they come from retries after timeouts, not from Claude calling the tool twice. A timeout on a POST is an unknown outcome: the first refund probably committed and the client never heard back. Second, "must never" rules out anything probabilistic.
</Step>

<Step title="Eliminate the distractors">
A fails twice: the duplicate calls are made by the HTTP client's retries, not by the model, and a prompt is a request, not a guarantee. C shrinks the window but a slow enough response still times out and retries, so "never" is not met. D stops duplicates but converts every timeout into an unknown state with no recovery, so refunds that did not commit are silently lost and someone has to reconcile by hand.
</Step>

<Step title="Choose">
B. POST is not idempotent, so the fix is to make the operation idempotent at the protocol level. The key is generated once per logical refund, not per attempt, and the server stores the first response under it. Retries become safe and can stay. This is the same shape as the Claude SDK's own retries being safe for `messages.create`, except that here the side effect is money, so the server must deduplicate.
</Step>

<Step title="The deciding cue">
"During a slowdown" plus "must never be applied twice" on a POST. Timeouts mean unknown outcome; POST means unsafe retry; "must never" means a deterministic control. That combination points to an idempotency key, never to a prompt or a timeout value.
</Step>

</Walkthrough>

<Walkthrough title="Scenario: migrating 600 handlers to a new logging API">

<Step title="Read the scenario">
A platform team must move 600 request handlers from a deprecated logging call to a structured logger with different arguments. Test coverage on the handlers is thin. They plan to use Claude Code. Which approach is safest?

A. One session: "Migrate every handler to the new logger," then open a single PR.
B. Characterize the handlers that lack tests, have Claude write and test a codemod on a few files, run it across the repo in small reviewable PRs, keep CI green between them.
C. Put "always use the new logger" in `CLAUDE.md` and let handlers migrate as people touch them.
D. Have Claude migrate the files, then ask Claude to review its own diff in the same session before merging.

B. **Bounded async concurrency that trusts the SDK's retries.** The semaphore (Python) and worker pool (TypeScript) cap in-flight requests; per-item errors are recorded rather than retried again, because by the time the SDK raises, its own retries are spent.

```python
import asyncio
import anthropic

# Defaults are max_retries=2 and timeout=600 s; shorten the timeout for short calls.
client = anthropic.AsyncAnthropic(timeout=60.0)
IN_FLIGHT = asyncio.Semaphore(16)
LABELS = {"billing", "outage", "account", "other"}


def text_of(resp) -> str:
    return "".join(b.text for b in resp.content if b.type == "text")


async def classify(body: str) -> str:
    async with IN_FLIGHT:  # at most 16 HTTP requests open, however many tasks exist
        resp = await client.messages.create(
            model="claude-haiku-4-5",
            max_tokens=16,
            system="Reply with exactly one word: billing, outage, account, or other.",
            messages=[{"role": "user", "content": body}],
        )
    label = text_of(resp).strip().lower()
    return label if label in LABELS else "other"  # validate at the boundary


async def classify_all(tickets: dict[str, str]) -> tuple[dict[str, str], dict[str, str]]:
    results: dict[str, str] = {}
    failures: dict[str, str] = {}

    async def one(ticket_id: str, body: str) -> None:
        try:
            results[ticket_id] = await classify(body)
        except anthropic.APIStatusError as e:  # raised only after SDK retries are spent
            failures[ticket_id] = f"http {e.status_code}"
        except anthropic.APITimeoutError:
            failures[ticket_id] = "timeout"
        except anthropic.APIConnectionError:
            failures[ticket_id] = "connection"

    async with asyncio.timeout(900):  # whole-job deadline
        async with asyncio.TaskGroup() as tg:  # tasks are referenced by the group
            for ticket_id, body in tickets.items():
                tg.create_task(one(ticket_id, body))
    return results, failures
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

// Defaults are maxRetries 2 and timeout 600_000 ms; TypeScript uses milliseconds.
const client = new Anthropic({ timeout: 60_000 });
const LABELS = new Set(["billing", "outage", "account", "other"]);

function textOf(msg: Anthropic.Message): string {
  return msg.content.map((b) => (b.type === "text" ? b.text : "")).join("");
}

async function classify(body: string): Promise<string> {
  const msg = await client.messages.create({
    model: "claude-haiku-4-5",
    max_tokens: 16,
    system: "Reply with exactly one word: billing, outage, account, or other.",
    messages: [{ role: "user", content: body }],
  });
  const label = textOf(msg).trim().toLowerCase();
  return LABELS.has(label) ? label : "other";
}

// tickets.map(classify) would start every request at once, because a promise
// runs as soon as it is created. A fixed pool of workers shares one iterator.
export async function classifyAll(tickets: Map<string, string>, limit = 16) {
  const results = new Map<string, string>();
  const failures = new Map<string, string>();
  const queue = tickets.entries();

  async function worker(): Promise<void> {
    for (const [id, body] of queue) {
      try {
        results.set(id, await classify(body));
      } catch (err) {
        // APIConnectionError is a subclass of APIError with no status.
        if (err instanceof Anthropic.APIError) failures.set(id, `http ${err.status ?? "none"}`);
        else throw err;
      }
    }
  }

  await Promise.all(Array.from({ length: limit }, () => worker()));
  return { results, failures };
}
```

**Structured output still needs domain validation.** The schema guarantees shape; the code checks the stop reason, the range, the enum casing and the date, which the schema cannot enforce.

**A safe retry for your own non-idempotent endpoint.** This is for a service you call from a tool handler, not for the Claude API (the SDK already retries those calls). One key per logical operation, retry only retryable statuses, honour `Retry-After`.

```python
import json
import random
import time
import urllib.error
import urllib.request
import uuid

RETRYABLE = {408, 429, 500, 502, 503, 504}


def retry_after_seconds(value: str | None, fallback: float) -> float:
    try:
        return float(value) if value is not None else fallback
    except ValueError:  # Retry-After may also be an HTTP date; fall back
        return fallback


def create_refund(base_url: str, payload: dict, attempts: int = 3) -> dict:
    key = str(uuid.uuid4())  # one key per refund decision, reused on every attempt
    body = json.dumps(payload).encode("utf-8")
    for attempt in range(attempts):
        req = urllib.request.Request(
            f"{base_url}/v1/refunds",
            data=body,
            method="POST",
            headers={"Content-Type": "application/json", "Idempotency-Key": key},
        )
        backoff = (2 ** attempt) + random.random()  # exponential with jitter
        try:
            with urllib.request.urlopen(req, timeout=10) as resp:
                return json.loads(resp.read())
        except urllib.error.HTTPError as e:  # subclass of URLError: catch first
            if e.code not in RETRYABLE or attempt == attempts - 1:
                raise
            time.sleep(retry_after_seconds(e.headers.get("Retry-After"), backoff))
        except (urllib.error.URLError, TimeoutError):
            if attempt == attempts - 1:
                raise
            time.sleep(backoff)
    raise RuntimeError("unreachable")
```

```typescript
const RETRYABLE = new Set([408, 429, 500, 502, 503, 504]);
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

function retryAfterMs(value: string | null, fallbackMs: number): number {
  const seconds = value === null ? NaN : Number(value);
  return Number.isFinite(seconds) ? seconds * 1000 : fallbackMs; // HTTP-date form falls back
}

export async function createRefund(baseUrl: string, payload: unknown, attempts = 3) {
  const key = crypto.randomUUID(); // one key per refund decision
  const body = JSON.stringify(payload);
  for (let attempt = 0; attempt < attempts; attempt++) {
    const backoff = 2 ** attempt * 1000 + Math.random() * 1000;
    let res: Response;
    try {
      res = await fetch(`${baseUrl}/v1/refunds`, {
        method: "POST",
        headers: { "Content-Type": "application/json", "Idempotency-Key": key },
        body,
        signal: AbortSignal.timeout(10_000),
      });
    } catch (err) {
      if (attempt === attempts - 1) throw err; // network error or timeout
      await sleep(backoff);
      continue;
    }
    if (res.ok) return res.json();
    if (!RETRYABLE.has(res.status) || attempt === attempts - 1) {
      throw new Error(`refund failed: HTTP ${res.status}`);
    }
    await sleep(retryAfterMs(res.headers.get("retry-after"), backoff));
  }
  throw new Error("unreachable");
}
```

## Recall checks

<Recall q="Which HTTP methods are idempotent, and why does that matter after a timeout?">
GET, HEAD, OPTIONS, PUT and DELETE are idempotent; POST and PATCH are not guaranteed to be. A timeout leaves the outcome unknown, so an idempotent request can simply be retried, while a POST needs an idempotency key (or a client-chosen ID with PUT) or the retry may repeat the side effect.
</Recall>

<Recall q="What do the Anthropic SDKs retry by default, and what is the worst-case latency of one call?">
Connection errors, 408, 409, 429 and 5xx, twice, with exponential backoff that honours `retry-after`. Timeouts are retried as well, so one call can take roughly `timeout x (max_retries + 1)` plus backoff; that is why adding your own retry layer on top multiplies load.
</Recall>

<Recall q="Why is cursor pagination preferred over offset pagination for a live dataset?">
Offsets are positions, so inserts and deletes during paging shift rows and cause skips or duplicates, and deep offsets get slower. A cursor names the last item seen, so each page continues from a stable point at constant cost.
</Recall>

<Recall q="A Python service returns order IDs that are wrong by one in a TypeScript dashboard. What happened and what is the fix?">
JavaScript parses JSON numbers as doubles, which are exact only up to 2^53 - 1, so larger IDs round. Python ints are exact, which is why only the browser is wrong. Send identifiers as strings in the contract.
</Recall>

<Recall q="Structured outputs guarantee schema-valid JSON. Name three things you still validate.">
Numeric ranges and string lengths (not enforced), enum casing (not guaranteed), and the stop reason, because a refusal or `max_tokens` stop can yield output that does not match. Beyond that, domain facts such as existing foreign keys are never the schema's job.
</Recall>

<Recall q="Why does `await Promise.all(items.map(callClaude))` trigger 429s, and what fixes it?">
Promises start when created, so the `map` launches every request at once and bursts past per-second and acceleration limits. A fixed worker pool (or a semaphore in Python) caps in-flight requests and lets the job ramp.
</Recall>

<Recall q="When is the Message Batches API the wrong choice even though it is half price?">
When someone is waiting on the result or the next step depends on it: batches usually finish within an hour but can take up to 24 hours, and each request is independent, so tool loops and chained calls do not fit.
</Recall>

<Recall q="An API key was committed and the commit reverted. Is the incident closed?">

<Recall q="Why is an eval suite, not the unit test suite, the gate for a prompt change?">
A prompt change alters behaviour without throwing errors, so unit tests and error dashboards stay green. An eval suite scores outputs on a fixed task-specific dataset and gates on an aggregate pass rate against the baseline.
</Recall>
