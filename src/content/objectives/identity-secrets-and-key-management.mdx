## What this objective actually tests

This is Domain 7, not Domain 2 — it's about the credential and identity plane, not general app configuration. It covers where secrets live across dev and production, how tightly an API key is scoped, and how identity/access decisions get verified and monitored — as distinct from `CLAUDE.md`/`settings.json` version-control hygiene, which is a sibling Domain 2 objective covering a different surface.

## Mechanism

**Secrets never live in source, client-side code, `CLAUDE.md`, a committed config file, or logs.** They live in a secret manager (Vault, AWS Secrets Manager, a platform's built-in secret store) and are injected at runtime as environment variables or fetched by reference — never hardcoded, never string-concatenated into a prompt or a URL.

**The client-side rule is absolute, not a hardening tip**: a key shipped to a browser, mobile app, or any other client-controlled binary is compromised the moment it ships. Obfuscation, minification, or "just in the build config" only delays extraction — it doesn't prevent it. The fix is architectural: proxy the call through a backend that holds the key server-side, which also gives you a natural place to enforce per-user authorization and rate limiting.

**Scoping and rotation**:
- Separate keys per environment (dev/staging/prod), per service, and per tenant where blast radius matters — a leaked dev key should never be able to touch production data.
- Workspace-scoped keys with spend limits bound the damage of a leak even before rotation happens.
- Rotate on a schedule *and* on suspicion of compromise; design the system so rotation is a config change, not a deploy — a key that requires a code push to rotate will be rotated late.

**Identity, access, and monitoring** — the three pieces beyond the key itself:
- **Identity validation and authentication** — authenticate the human (or calling service) behind a request, not just whichever service credential is attached to it.
- **Access approval and level verification** — checked at the tool/resource boundary, per request (the same principle as the least-privilege pattern in Guardrails and Safe Deployment).
- **Authorized access monitoring** — log who invoked what, under which identity, against which resource, so a compromised key or an over-broad grant shows up in an audit trail rather than silently.

## Decision table

| When the stem says... | ...the answer is |
|---|---|
| A mobile or browser app calls Claude directly | Wrong by construction — proxy through a backend; the key must never ship to the client |
| A key is "obfuscated" or minified in a client bundle "for security" | Still a client-side key — compromised on ship regardless of obfuscation |
| A dev key and a prod key share one value "to keep it simple" | Wrong — separate keys per environment bound blast radius on leak |
| A key needs a code deploy to rotate | Wrong design — rotation should be a config/secret-manager change, not a deploy |
| "Which service called this" is the only thing logged | Insufficient — monitoring must capture identity, action, and resource together |
| Secrets management appears bundled with `CLAUDE.md`/config-file questions | Scope check — secrets are Domain 7, not Domain 2 Configuration Management |

## Example

```python
import os
from anthropic import Anthropic

# Injected at runtime by the platform's secret manager (env var here), never
# hardcoded and never committed. A separate key per environment means a
# leaked staging key can't touch production spend or data.
client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])  # workspace-scoped, spend-limited
```

The key never appears in the diff, in `CLAUDE.md`, or in a log line — only the environment variable name does. Rotating it means updating the secret manager entry, not shipping a new build.

## Named traps, expanded

**A key shipped to a client is compromised on ship; obfuscation only delays extraction.** This is attractive to violate because obfuscating or minifying a client-bundled key feels like a real mitigation — it does raise the effort required to extract it. It's wrong because "raises the effort" is not the bar; any determined party can pull a key out of a shipped binary or a browser's network tab, so the key must be treated as already public the moment it's in client-reachable code. Recognize this trap whenever a stem describes a mobile app, browser extension, or any client-controlled artifact holding a real API key, with or without claimed obfuscation — the only correct fix is moving the call server-side.
