## Concept

The lightest objective by weight, but its reasoning is reused all over the exam: a prompt is a request, a hook is a control. Hooks are commands (or HTTP calls, MCP tool calls, prompts or agents) that Claude Code runs at fixed lifecycle points. The safety-relevant one is `PreToolUse`, which sees each tool call before it executes and can stop it.

This page covers how a hook blocks, how it fails, where it is registered, and what it cannot do.

<Callout type="key" title="The point-winning idea">
To prevent an action, use `PreToolUse` and block with exit 2 (or a JSON deny). Every other non-zero exit, a crash, or a timed-out command hook lets the action proceed. If the guard must hold, make it fail closed and back it with a deny rule.
</Callout>

## Mechanism

### Hooks as guardrails and safety controls

<SubskillAnchor id="hk.guardrails" />

<Flow title="Where a PreToolUse guard sits" steps={[{label: "Claude emits tool_use", kind: "model"}, {label: "PreToolUse hooks", kind: "guard", note: "exit 2 or deny blocks here"}, {label: "Deny and ask rules", kind: "guard", note: "evaluated even after a hook allow"}, {label: "Mode and allow rules", kind: "decision"}, {label: "Tool runs", kind: "tool"}, {label: "PostToolUse", kind: "guard", note: "feedback only"}]} caption="A hook deny holds even in bypassPermissions. Nothing after the tool runs can take it back." />

**The contract is the exit code** **[Certain]**:

| Exit | Effect on PreToolUse |
|---|---|
| `0` | No block. Stdout that is a JSON object is read for decisions such as `permissionDecision: "deny"` |
| `2` | Blocks the call. Stderr (or the JSON reason) is fed back to Claude. Wins even over JSON that says `allow` |
| Anything else | Non-blocking error unless stdout holds valid JSON; the call proceeds with a `hook error` notice |

A missing script or interpreter exits 127 and lands in the same non-blocking bucket; the docs warn that "a mistyped path in `settings.json` leaves the gate silently disabled". Hooks can also return structured JSON: `permissionDecision` of `allow`, `deny`, `ask` or `defer`, with `deny` taking precedence when several hooks disagree.

**Per event.** Exit 2 blocks `PreToolUse`, `UserPromptSubmit` (the prompt never reaches Claude) and `Stop` (Claude keeps working). It cannot block `PostToolUse` ("the tool already ran") and is not honoured on `PermissionRequest`, which decides through its own JSON.

**Matchers** select which tool calls run the hook, by tool name. Letters, digits, `_`, spaces and pipe-separated names are exact matches; any other character makes the matcher an unanchored, case-sensitive regex, so `Edit.*` also matches `NotebookEdit` **[Certain]**. Arguments are invisible to the matcher: the script reads `tool_input` from stdin.

**Fail closed.** Lab 09 ran this for real on 2026-10-06: a guard with a typo exited 127 and the simulated `rm -rf /` was allowed; the same script with `set -euo pipefail` and an `ERR` trap that exits 2 blocked instead. For a security guard, blocking everything until someone fixes it is the right trade; for a formatter, failing open is fine. Timeouts follow the same logic: a timed-out command hook on `PreToolUse` does not block, while an Agent SDK callback that times out does **[Certain]** (recent behaviour).

**Where hooks are registered** **[Certain]**: `~/.claude/settings.json` (all your projects), `.claude/settings.json` (shared, committed), `.claude/settings.local.json` (personal), managed policy settings (organization-wide), a plugin's `hooks/hooks.json`, and skill or subagent frontmatter (active after the skill is invoked, or while the subagent runs). Hooks from different levels merge rather than replace. Administrators can set `allowManagedHooksOnly` so only managed hooks run, and project hooks wait for workspace trust.

**Exam angle:** "must happen every time", "regardless of permission mode" point to a PreToolUse hook. Distractors: a CLAUDE.md or system prompt rule, a PostToolUse hook, a guard that exits 1.

### Preventing destructive actions

<SubskillAnchor id="hk.destructive" />

Typical targets are recursive deletes, force pushes, writes to production systems and edits to secrets files. Build the guard in layers, because each layer has a known gap:

| Layer | Stops | Known gap |
|---|---|---|
| Deny rule, for example `Bash(rm *)`, `Edit(//secrets/**)` | The usual spelling, in every mode | `/bin/rm`, `bash -c 'rm ...'` per the permissions docs |
| PreToolUse hook parsing the command or path | Variants your parser understands | Anything your parser does not (wrappers, encodings) |
| Least privilege: read-only credentials, no prod tokens in the environment | Actions the identity cannot perform at all | Needs IAM work, not just config |
| OS sandbox for filesystem and network | Damage outside allowed paths and hosts | Setup cost |

**What hooks cannot do:**
- **Undo.** PostToolUse can log, alert, add context or replace the output Claude sees; the file is still deleted.
- **Override rules.** A hook allow "doesn't bypass deny rules from settings" **[Certain]**.
- **See everything.** Files referenced with `@` in a prompt are inserted without a tool call, so no PreToolUse hook fires; the docs point to a `Read` deny rule instead **[Certain]**.
- **Match intent.** A denylist matches text; lab 09 showed `/bin/rm -rf build` passing a whitespace-anchored regex.

Hands-on: [Lab 09](../../labs/09_hooks/) runs a guard, the 127 footgun and the fail-closed fix.

**Exam angle:** "a variant of the command still ran" points to layering (deny rule, least privilege, sandbox), not a longer regex. "Undo the deletion" is never a hook answer.

## Decision table

| If the stem says... | Choose | Why the runner-up loses |
|---|---|---|
| Stop a destructive command before it runs | `PreToolUse` hook that exits 2 (or JSON deny) | `PostToolUse` fires after the tool ran |
| Guard errored and the command ran anyway | Trap errors and exit 2 (fail closed) | Exit 1 or 127 is a non-blocking error |
| Must hold even in bypassPermissions | Hook deny or a deny rule | Allow lists and modes are evaluated later |
| A custom hook approved a call a settings deny rule blocks | The deny rule wins; fix the rule | A hook allow never bypasses deny or ask rules |
| Matcher written as "drop table" never fires | Match the tool name, inspect `tool_input` in the script | Matchers never see prompt text or arguments |
| `/bin/rm` or `bash -c` slipped past the guard | Add least privilege and sandboxing to the hook | A longer regex leaves the next variant open |
| Org-wide guard users must not disable | Managed settings hook, optionally `allowManagedHooksOnly` | Project or user hooks can be edited or disabled |

## Worked walkthrough

<Walkthrough title="Scenario: the force push that the guard missed">

<Step title="Read the scenario">
A platform team ships `.claude/settings.json` with a PreToolUse hook on `Bash` that blocks `git push --force` to protected branches. It works on laptops. On the new CI runner image, Claude Code force-pushed to `main`. The hook log shows `PreToolUse hook error: jq: command not found`. What is the best fix?
</Step>

<Step title="Find the constraint">
"Hook error" plus "jq: command not found" says the guard never reached its logic. The shell returned 127, which is a non-blocking error, so the push proceeded. The guard failed open.
</Step>

<Step title="Eliminate the wrong event and the prompt">
Moving the check to `PostToolUse` fires after the push landed. Adding "never force push" to CLAUDE.md is advisory and does not fix a broken control.
</Step>

<Step title="Eliminate the wrong exit code">
Changing the script's block path from `exit 2` to `exit 1` makes it worse: exit 1 is also non-blocking.
</Step>

<Step title="Choose">
Make the guard fail closed (no external dependency, or an `ERR` trap that exits 2), add a `Bash(git push --force *)` deny rule as a second layer, and protect `main` with branch protection on the server.
</Step>

<Step title="The deciding cue">
"Hook error" in the log. Any exit other than 2 lets the action through, so the fix is the guard's own error handling, not a different event or a stronger prompt.
</Step>

</Walkthrough>

## Code

**A fail-closed guard for Bash, Edit and Write.** It splits compound commands, normalizes `/bin/rm` to `rm`, catches force pushes and protected paths, and exits 2 on any internal error. Register it with the JSON below.

```python
#!/usr/bin/env python3
# .claude/hooks/guard.py: PreToolUse guard for Bash, Edit and Write.
# Exit 2 blocks and stderr becomes the reason Claude reads. Any unexpected error also exits 2.
import json
import shlex
import sys

PROTECTED = (".env", "/secrets/", ".git/")
OPERATORS = {"&&", "||", ";", "|", "&"}


def segments(command: str):
    lexer = shlex.shlex(command, posix=True, punctuation_chars=True)
    lexer.whitespace_split = True
    current = []
    for token in lexer:
        if token in OPERATORS:
            yield current
            current = []
        else:
            current.append(token)
    yield current


def block_reason(event: dict):
    tool, args = event["tool_name"], event["tool_input"]
    if tool in ("Edit", "Write"):
        path = args["file_path"]
        return f"{path} is a protected path." if any(p in path for p in PROTECTED) else None
    for words in segments(args["command"]):
        if not words:
            continue
        program = words[0].rsplit("/", 1)[-1]  # /bin/rm counts as rm
        flags = [w for w in words[1:] if w.startswith("-")]
        if program == "rm" and any(f == "--recursive" or (not f.startswith("--") and "r" in f.lower()) for f in flags):
            return "Recursive rm is blocked by policy."
        if program == "git" and "push" in words and any(w.startswith(("--force", "-f", "+")) for w in words[2:]):
            return "Force push is blocked. Open a pull request instead."
    return None


try:
    reason = block_reason(json.load(sys.stdin))
except Exception as exc:  # malformed payload, unbalanced quotes, missing key: fail closed
    print(f"guard error, failing closed: {exc!r}", file=sys.stderr)
    sys.exit(2)
if reason:
    print(reason, file=sys.stderr)
    sys.exit(2)
sys.exit(0)
```

```typescript
#!/usr/bin/env -S npx tsx
// .claude/hooks/guard.ts: same policy. Simpler tokenizing than Python's shlex, so quoted
// operators are split too; the try/catch still turns any failure into exit 2.
import { readFileSync } from "node:fs";

const PROTECTED = [".env", "/secrets/", ".git/"];

function blockReason(event: { tool_name: string; tool_input: Record<string, string> }): string | null {
  const { tool_name: tool, tool_input: args } = event;
  if (tool === "Edit" || tool === "Write") {
    return PROTECTED.some((p) => args.file_path.includes(p)) ? `${args.file_path} is a protected path.` : null;
  }
  for (const segment of args.command.split(/&&|\|\||;|\||&/)) {
    const words = segment.trim().split(/\s+/).filter(Boolean);
    if (words.length === 0) continue;
    const program = words[0].split("/").pop();
    const flags = words.slice(1).filter((w) => w.startsWith("-"));
    if (program === "rm" && flags.some((f) => f === "--recursive" || (!f.startsWith("--") && /r/i.test(f)))) {
      return "Recursive rm is blocked by policy.";
    }
    if (program === "git" && words.includes("push") && words.slice(2).some((w) => /^(--force|-f|\+)/.test(w))) {
      return "Force push is blocked. Open a pull request instead.";
    }
  }
  return null;
}

try {
  const reason = blockReason(JSON.parse(readFileSync(0, "utf8")));
  if (reason) {
    process.stderr.write(reason + "\n");
    process.exit(2);
  }
  process.exit(0);
} catch (err) {
  process.stderr.write(`guard error, failing closed: ${err}\n`);
  process.exit(2); // fail closed
}
```

## Recall checks

<Recall q="Which hook event can stop a destructive tool call, and what does exit 2 do on PostToolUse?">
PreToolUse, because it runs before the tool executes; exit 2 or a JSON deny blocks the call and the reason goes back to Claude. On PostToolUse exit 2 only shows stderr to Claude, because the tool already ran.
</Recall>

<Recall q="A guard script exits 1 when it finds a forbidden command. What happens, and what should it do instead?">
Exit 1 without valid JSON is a non-blocking error, so the command runs and the transcript shows a hook error notice. The guard should exit 2, or exit 0 with a JSON permissionDecision of deny.
</Recall>

<Recall q="What does a hook matcher match against, and where does command inspection happen?">
The tool name, as an exact name or pipe-separated list, or as an unanchored case-sensitive regex when it contains other characters. The command, file path or SQL is read from tool_input inside the hook script.
</Recall>

<Recall q="Can a PreToolUse hook that returns allow override a deny rule in settings.json?">
No. Deny and ask rules are evaluated regardless of what the hook returns, so hooks can tighten restrictions but never loosen them past what the permission rules allow.
</Recall>

<Recall q="Why is a regex hook alone not enough to prevent recursive deletes, and what completes the defence?">
It matches text, so variants such as /bin/rm or bash -c wrappers can slip past both regexes and Bash deny rules. Add deny rules, least-privilege credentials and an OS-level sandbox, and make the hook fail closed.
</Recall>
