## Concept

This objective tests whether you can reason from how an LLM produces text to the engineering consequence a stem is after. The mechanics are few: text becomes tokens, tokens fill a context window, the model emits one token at a time by sampling from a distribution, and the result is not perfectly repeatable.

The second half is the **model modes**: fast mode, extended thinking, adaptive thinking and effort. All of them touch cost and latency, so they blur. Keep them apart by what each changes: fast mode changes **speed of the same model**, thinking changes **whether the model reasons before answering**, effort changes **how much output of every kind the model spends**. None of them changes which model answers.

The third piece is vocabulary: zero-, single- and multi-shot prompting.

**Scope boundary.** Not this:

- Which tier to pick, and breaking changes on a model swap: <ObjLink id="model-selection-and-tradeoffs" />.
- Building, diversifying and placing few-shot examples inside a prompt: <ObjLink id="prompt-engineering" />.
- Prompt caching economics, batch discounts and budget dashboards: <ObjLink id="cost-and-token-management" />.
- Curating what goes into the window (compaction, retrieval, context rot mitigation): <ObjLink id="context-engineering" />.
- Handling `stop_reason` values and parsing output: <ObjLink id="output-handling" />.

<Callout type="key" title="The single idea that wins the most points">
Every dial in this objective is either a **hard limit enforced by the API** (context window, `max_tokens`, schemas) or **soft guidance the model interprets** (effort, prompt wording, examples). When a stem says something must hold every time, the answer is a hard limit or code. When it says "usually", "more" or "less", the answer is a soft dial.
</Callout>

## Mechanism

### Tokens

<SubskillAnchor id="llm.tokens" />

A token is the unit the model reads and writes: a word, part of a word, a character or a byte. Billing, rate limits, context windows and `max_tokens` are all denominated in tokens, never characters or words.

The rule of thumb is unreliable, and Anthropic's own pages show why. The glossary says a token is about 3.5 English characters; the pricing FAQ says about 4 characters or 0.75 words; the models overview says 1M tokens is roughly 555k words on the current tokenizer versus about 750k words on models before it. [Certain] that all three statements appear; [Likely] that the gap is the tokenizer change. The engineering conclusion is the stable part: **estimate with arithmetic, budget with `count_tokens`**.

Token counts are **model-specific**. Claude Opus 4.7 and later (and the Fable, Mythos and Sonnet 5 lines) use a newer tokenizer that produces approximately 30% more tokens for the same text than Claude Sonnet 4.6, Haiku 4.5 and earlier. [Certain, token counting and pricing pages] A count measured on one model is not valid for another.

What `count_tokens` gives you [Certain]:

- It accepts the same structure as `messages.create`: system, messages, tools, images, PDFs, thinking blocks.
- It counts under the tokenizer of the `model` you pass, so you can diff two models on the same request.
- It is free but rate-limited per minute, and its limits are independent of message creation limits.
- The result is an estimate; actual usage can differ slightly.
- It rejects server tools (other than the advisor tool), the MCP connector, and `url` or `file` image and document sources.

Images and PDF pages are tokens too and count against the window.

**Exam angle:** cue words are "estimate cost", "will it fit", "after migrating, costs rose at the same price". Answer is count with the target model. The distractor is a characters-divided-by-four estimate or reusing an old count.

### Context windows

<SubskillAnchor id="llm.context-windows" />

The context window is everything the model can reference while generating, **including the response itself**. Everything in the request counts: system prompt, every message (tool results, images, documents), tool definitions, plus the output generated this turn, thinking included. Cached prefixes still occupy the window; caching changes price, not occupancy. [Certain, context windows page]

<Flow title="What one request spends against the context window" steps={[{label: "tools", kind: "tool", note: "definitions count"}, {label: "system", kind: "client"}, {label: "messages", kind: "store", note: "history, tool results, images"}, {label: "thinking", kind: "model", note: "output, inside max_tokens"}, {label: "reply text", kind: "model", note: "output, inside max_tokens"}]} caption="Input and output share one window. max_tokens bounds only the last two boxes." />

`max_tokens` is a different limit: the absolute maximum Claude generates this turn, and thinking tokens are a subset of it. The model may stop earlier. Each model has its own ceiling for `max_tokens`. [Certain] The SDKs require streaming above 21,333 `max_tokens` to avoid HTTP timeouts; that is client-side validation, not an API limit. [Certain, thinking page]

Overflow behaviour is precise and testable [Certain, context windows page]:

| Situation | Result |
|---|---|
| Input alone exceeds the window | 400 `invalid_request_error`, "prompt is too long", every model |
| Input plus `max_tokens` exceeds the window (Claude 4.5 and newer) | Accepted; if generation hits the window, `stop_reason: "model_context_window_exceeded"` |
| Output reaches `max_tokens` | HTTP 200, `stop_reason: "max_tokens"`, truncated reply |

Bigger is not automatically better. Accuracy and recall degrade as token count grows (context rot), so curation matters as much as capacity. Window sizes are per model: the current Opus, Sonnet and Fable lines have 1M tokens with 128K max output; Haiku 4.5 has 200K with 64K max output. [Certain as of 2026-10-06, drifts] Query the Models API (`max_input_tokens`, `max_tokens`) rather than hardcoding.

**Exam angle:** "conversation no longer fits" is a window problem (trim, compact, retrieve). "Answers cut off" is a `max_tokens` problem (raise it or lower effort). Swapping those two remedies is the classic distractor.

### Sampling

<SubskillAnchor id="llm.sampling" />

At each step the model produces a probability distribution over the vocabulary and the decoder **samples** one token from it. Three classic parameters shape that draw:

| Parameter | What it does | Classic use |
|---|---|---|
| `temperature` | Flattens (high) or sharpens (low) the distribution. Default 1.0, range 0.0 to 1.0 | Near 0 for analytical or multiple-choice work, near 1 for creative work |
| `top_p` | Nucleus sampling: keep the smallest set of tokens whose cumulative probability reaches p | Trim the long tail |
| `top_k` | Keep only the k most likely tokens | Trim the long tail, advanced use only |

[Certain, Messages API reference] The concept is examinable and stable: lower temperature means more conservative, more probable phrasing; higher means more diverse output. It does **not** make the model smarter, and it does not make output reproducible.

<PostGuide title="Post-guide change: current models reject sampling parameters">
On Claude Opus 4.7 and later, Opus 5 and 5.5, Sonnet 5 and 5.5, and the Fable and Mythos models, a non-default `temperature`, `top_p` or `top_k` returns a 400 on every request. The API reference phrases it as "models released after Claude Opus 4.6", accepting only `temperature` 1.0 and `top_p` of 0.99 or more for backwards compatibility; the Sonnet 5.5 migration guide says Sonnet 4.6 still accepts them. [Certain that both statements exist; Likely that the thinking page's model list is the precise one.] On older models the restriction applies only while thinking is on. The replacement levers are effort, prompt instructions and structured outputs. Treat this as engineering knowledge, not exam content.
</PostGuide>

**Exam angle:** sampling questions test the concept (what temperature changes and what it cannot). A stem that offers "set temperature to 0" as the way to guarantee consistent JSON is offering the wrong layer: a schema guarantees shape.

### Non-determinism

<SubskillAnchor id="llm.nondeterminism" />

Anthropic states it directly: even with temperature 0.0, results are not fully deterministic, and identical inputs may produce different outputs across calls, on first-party and cloud-provider inference alike. [Certain, glossary and API reference] Two further sources of drift sit outside your request entirely. Model IDs are pinned snapshots with fixed weights, but the serving infrastructure around them (router, safety classifiers, sampling logic) can change and occasionally shifts observable behaviour. [Certain, model IDs page] And adaptive thinking means the amount of reasoning varies request to request by design.

So non-determinism is a property you engineer around, not a setting you turn off:

| Need | Engineering answer | Why a prompt or sampling setting is not enough |
|---|---|---|
| Same shape every time | Structured outputs (`output_config.format`) or strict tools | A schema is enforced; an instruction is a request |
| Same answer every time for audit | Store the output and replay it; key it by input hash | Regeneration can differ |
| Confidence in a label | Sample several times, take the majority, route disagreement to review | Disagreement is signal you lose with one call |
| Regression safety | Evals scored as pass rates over many runs | One green run proves little |
| Safe side effects | Idempotent downstream writes, validation before acting | The model may emit a different but valid action |

**Exam angle:** "must", "identical", "reproducible", "audit" point to code (schema, storage, validation). Any option that achieves determinism with a sampling parameter or a "be consistent" instruction is the distractor.

### Next-token generation

<SubskillAnchor id="llm.next-token" />

Claude's underlying model is autoregressive: pretrained to predict the next token given everything before it. [Certain, glossary] Generation is a loop: read the whole context, emit one token, append it, repeat until a stop condition.

<Flow title="Autoregressive generation loop" steps={[{label: "Context so far", kind: "store", note: "prompt plus tokens already emitted"}, {label: "Forward pass", kind: "model", note: "distribution over next token"}, {label: "Sample one token", kind: "decision"}, {label: "Append and repeat", kind: "store"}, {label: "Stop", kind: "guard", note: "end_turn, stop_sequence, max_tokens, window"}]} caption="Every output token waits for the one before it. Input is read up front." />

What follows from the loop, each of which shows up in stems:

- **No lookahead, no revision.** A token, once emitted, conditions everything after it. If you ask for the verdict first and the justification second, the justification rationalises a verdict already committed. Ask for reasoning before the answer, or use thinking, which exists precisely to do scratch work before the visible answer.
- **Latency tracks output length.** Output tokens are produced sequentially; input is processed up front. [Likely: the mechanism; Certain: the economics] Output is priced at five times input across the current lineup (for example $10 versus $2 per MTok on Sonnet 5.5, from `facts.json`). Shortening output is the strongest latency and cost lever.
- **Structure in the prompt steers the distribution.** XML tags separate instructions, context and examples so the model does not confuse them. For long inputs, put documents at the top and the query at the end; Anthropic reports up to 30% better responses in tests with complex multi-document inputs. [Certain, prompting best practices]
- **Stops are mechanical.** `end_turn` when the model finishes, `stop_sequence` when a custom string appears, `max_tokens` when the cap hits, `model_context_window_exceeded` when the window fills. All arrive on HTTP 200. [Certain, API reference]
- **Prefill used to exploit this loop.** Seeding the assistant turn forced the continuation. Since the Claude 4.6 models it returns a 400; use structured outputs or instructions instead. [Certain, prompting best practices]

**Exam angle:** stems that ask why "answer first, explain after" produces confident wrong answers, or why output length dominates latency, are testing this loop. The distractor blames the context window or temperature.

### Fast mode

<SubskillAnchor id="llm.fast-mode" />

Fast mode runs **the same model** with a faster inference configuration: same weights, same behaviour, no change to intelligence. It delivers up to 2.5x higher **output tokens per second**; it does not target time to first token. You opt in per request with `speed: "fast"` plus the `fast-mode-2026-02-01` beta header, on the beta Messages endpoint, and `usage.speed` reports what you got. [Certain, fast mode page]

The trade is money for throughput:

| Property | Fast mode |
|---|---|
| Quality | Unchanged (same model) |
| Output speed | Up to 2.5x |
| Time to first token | Not the target |
| Price | Premium, roughly 2x standard per token [Likely as a ratio; per-model prices drift] |
| Rate limit | Separate from standard limits; 429 with `retry-after` when exceeded |
| Prompt cache | Not shared across speeds; switching speed is a cache miss |
| Batch API, Priority Tier | Not available |

<PostGuide title="Post-guide detail: fast mode availability and price">
As of 2026-10-06 fast mode is a research preview (access by request) on Claude Opus 5.5, Opus 5 and Opus 4.8, on the Claude API and Managed Agents only, not Amazon Bedrock, Google Cloud, Microsoft Foundry or Claude Platform on AWS. Opus 5.5 fast mode is $8 / $40 per MTok against $4 / $20 standard. On Opus 4.7 `speed: "fast"` errors; on Opus 4.6 it silently runs at standard speed and reports `usage.speed: "standard"`. [Certain on the fast mode page today; model list and prices drift.]
</PostGuide>

**Exam angle:** the cue is "same quality" plus "responses take too long to finish" plus "willing to pay more". Distractors: a smaller model (changes quality), lower effort (changes behaviour), streaming (improves perceived latency, not throughput), and the Batch API (slower, cheaper, and incompatible).

### Extended thinking

<SubskillAnchor id="llm.extended-thinking" />

Thinking lets Claude work through a problem in `thinking` content blocks before the visible answer. **Extended thinking** is the manual mode: `thinking: {type: "enabled", budget_tokens: N}`. [Certain, extended thinking page]

- `budget_tokens` minimum is 1,024 and must be less than `max_tokens`, because thinking counts toward `max_tokens` (interleaved thinking is the one exception).
- The budget is a target, not a strict cap. `max_tokens` remains the hard ceiling.
- Claude thinks on every request; manual mode trades adaptivity for predictable latency and cost.
- Changing `budget_tokens` between requests invalidates prompt cache breakpoints.
- Thinking tokens bill as output tokens, even when the displayed text is a summary.
- Forced tool use (`tool_choice` `any` or `tool`) is incompatible with manual extended thinking.

Lifecycle, which is the part that drifts: extended thinking is deprecated on the Claude 4.6 models, rejected with a 400 on Claude 4.7 and later, and the **only** thinking mode on Claude Haiku 4.5, Sonnet 4.5 and Opus 4.5, where sending `adaptive` returns a 400. [Certain, extended thinking and thinking pages] Migration is mechanical: remove `budget_tokens`, set `thinking: {type: "adaptive"}`, control depth with `output_config.effort`. There is no fixed budget-to-effort mapping, so evaluate at two or three effort levels. [Certain, Sonnet 5.5 migration guide]

**Exam angle:** "fixed, predictable thinking spend" or "Haiku with thinking" points to extended thinking. "Let the model decide" points to adaptive. A stem that adds `budget_tokens` to a current Opus or Sonnet request is describing a 400.

### Adaptive thinking

<SubskillAnchor id="llm.adaptive-thinking" />

Adaptive thinking (`thinking: {type: "adaptive"}`) lets Claude decide **per request whether to think and how much**. A simple factual question may get no thinking block at all; a multistep debugging task gets deep reasoning. [Certain, steering thinking page]

Mechanics worth knowing:

- **No thinking block is guaranteed.** Turns where Claude chose not to think are valid history, and code must not assume `content[0]` is thinking or text. Iterate by `type`.
- **Interleaved thinking is automatic**: Claude can reason between tool calls without a beta header.
- **Effort is the primary steering lever**, then prompt guidance ("think carefully before responding" or "respond directly") if triggering still misses.
- **Cost bounds**: `max_tokens` is the hard cap on thinking plus text; effort is soft guidance. A `max_tokens` sized for a no-thinking reply is often too small once thinking starts. If you see `stop_reason: "max_tokens"`, either raise the cap (the reasoning was needed) or lower effort (it was over-thought).
- **Billing**: thinking bills as output whether or not you see it. `usage.output_tokens_details.thinking_tokens` reports the reasoning share. [Certain, API reference]

<PostGuide title="Post-guide detail: thinking on by default, display omitted">
On Opus 5, Opus 5.5, Sonnet 5, Sonnet 5.5 and Fable models, omitting `thinking` already runs adaptive thinking. On Opus 5.5 and the Fable models it cannot be turned off (`disabled` is a 400). Sonnet 5.5 rejects `disabled` and offers `{type: "between_tools"}` instead. Thinking text is `display: "omitted"` by default on these models: blocks arrive with an empty `thinking` field, still billed. [Certain on the thinking page today.]
</PostGuide>

**Exam angle:** cue words "mixed workload", "some requests trivial, some hard", "let the model decide". The distractor is a fixed `budget_tokens` sized for the hardest request, which overspends on easy ones.

### Effort levels

<SubskillAnchor id="llm.effort" />

`output_config.effort` (inside `output_config`, not top-level and not inside `thinking`) trades thoroughness against token spend **within one model**. [Certain, effort page]

| Level | Behaviour | Typical use |
|---|---|---|
| `low` | Most efficient; may skip thinking on simple tasks | Subagents, chat, high-volume routes |
| `medium` | Moderate thinking, moderate savings | Balanced agentic work |
| `high` | Thinks on most requests that benefit | Complex reasoning, hard coding |
| `xhigh` | More readily and deeper than high | Long-horizon agentic and coding work |
| `max` | No constraint on token spend | Frontier problems where correctness beats cost |

Five properties carry most questions:

1. **It affects all output tokens**: text, tool calls and thinking. Lower effort means fewer, terser tool calls and less preamble. It works with or without thinking.
2. **It is a behavioural signal, not a cap.** At low effort Claude still thinks on genuinely hard problems, just less.
3. **Defaults differ by model.** Most models default to `high`; Claude Opus 5.5 defaults to `medium`. Setting the default explicitly equals omitting it. Not every model with `max` has `xhigh`. Claude Haiku 4.5 does not support effort at all. [Certain, effort page and models overview; drifts]
4. **Changing top-level effort mid-conversation invalidates the prompt cache**, exactly as changing `budget_tokens` did. Pick one level per conversation.
5. **Effort does not reliably control visible length** on some models; prompt for length when brevity is the requirement. [Certain for Opus 5 on the effort page]

<PostGuide title="Post-guide detail: per-model effort recalibration">
Claude Opus 5.5 defaults to `medium` (one level below Opus 5). Claude Sonnet 5.5 keeps `high` but recalibrated its levels, so the same name produces a different amount of thinking than on Sonnet 5; re-run the effort sweep. A beta per-message effort change (`mid-conversation-output-config-2026-07-01`) avoids the cache reset on some current models. [Certain on the effort page today.]
</PostGuide>

**Exam angle:** "trade quality for cost or latency without changing the evaluated model" points to effort. Distractors: swapping models (invalidates evals), `budget_tokens` (legacy), temperature (wrong concept).

### Zero-shot, single-shot and multi-shot prompting

<SubskillAnchor id="llm.shot" />

The taxonomy counts worked examples in the prompt:

| Term | Examples | When it fits |
|---|---|---|
| Zero-shot | None, instructions only | Task the model already does well; format obvious from instructions |
| Single-shot (one-shot) | Exactly one | One example fully disambiguates the format |
| Multi-shot (few-shot) | Several | Format, tone or edge-case handling must be consistent |

Anthropic calls examples one of the most reliable ways to steer format, tone and structure, and recommends 3 to 5 examples that are **relevant** (mirror the real use case), **diverse** (cover edge cases so Claude does not latch onto an unintended pattern) and **structured** (wrapped in `<example>` tags). Examples also shape how Claude approaches similar problems inside its thinking. [Certain, prompting best practices]

Every example costs input tokens on every call (keep them in a stable, cacheable prefix), and near-duplicates teach accidental surface patterns. A single example is the most prone to being copied, because there is nothing to contrast it with. [Guessing]

The guide lists this taxonomy here and "few-shot examples" under D6 Prompt Engineering. Naming the technique and saying why examples help is this objective; constructing, diversifying and placing them is <ObjLink id="prompt-engineering" />.

**Exam angle:** "outputs inconsistent in format despite clear instructions" points to adding diverse examples. Distractors: lowering temperature, raising effort, switching to a larger model.

## Decision table

| If the stem says... | Choose | Why the runner-up loses |
|---|---|---|
| Responses cut off mid-sentence; `stop_reason` is `max_tokens` | Raise `max_tokens` or lower effort | A larger context window does not change the per-turn output cap |
| Long chat history now fails with "prompt is too long" | Trim, compact or retrieve less (window problem) | Raising `max_tokens` adds pressure on the same window |
| Migrated model, same price per token, bill rose about 30% | Recount with `count_tokens` on the new model | Old counts came from a different tokenizer |
| Output must be byte-identical on every run for audit | Store and replay the output; validate with a schema | temperature 0 is documented as not fully deterministic |
| Same model, same quality, long answers finish too slowly, budget approved | Fast mode | Lower effort or a smaller model changes behaviour; streaming fixes perceived, not actual, throughput |
| Mixed easy and hard requests; reasoning should scale with difficulty | Adaptive thinking steered by effort | Fixed `budget_tokens` overspends on easy requests and is rejected on current models |
| Need thinking on Claude Haiku 4.5 | Extended thinking with `budget_tokens` | Haiku 4.5 rejects adaptive thinking and has no effort parameter |
| Cut cost on a route whose behaviour is already evaluated | Lower effort on the same model | A model swap invalidates the evals |
| Hard ceiling on output spend per request | `max_tokens` | Effort is soft guidance, not a cap |
| Format drifts across outputs despite precise instructions | Multi-shot: 3 to 5 diverse examples in `<example>` tags | Sampling and effort do not teach a format |
| "Answer first, then explain" yields confident wrong answers | Reason before answering (or thinking on) | Next-token generation cannot revise a committed answer |

## Worked walkthrough

<Walkthrough title="Scenario: Incident-report drafts that take too long to finish">

<Step title="Read the scenario">
A platform team generates incident post-mortem drafts with Claude Opus 5.5 at its default effort. Drafts score well on the team's eval suite, and the on-call lead has signed off on the quality. Responses already stream, and the first words appear quickly, but a full draft takes long enough to finish that responders abandon the page. Finance has approved a higher per-request cost. What should the team change?
</Step>

<Step title="Find the buried constraint">
Three facts decide it. Quality is evaluated and approved, so anything that changes model behaviour is a regression risk. The first token is already fast, so the problem is output throughput, not time to first token. And budget is available, so a premium is acceptable.
</Step>

<Step title="Eliminate the distractors">
Switching to Haiku 4.5 is cheaper and faster, but it is a different model: the approved quality and every eval result no longer apply. Lowering effort to `low` would shorten the work, but effort changes how much the model reasons and writes, which is exactly the evaluated behaviour. Enabling streaming is already done and only improves perceived latency. Moving the job to the Message Batches API makes completion slower and asynchronous, and fast mode is not available there anyway.
</Step>

<Step title="Choose">
Enable fast mode on the existing Opus 5.5 requests (`speed: "fast"` with the beta header), keep effort and prompts unchanged, and add a fallback to standard speed on a fast-mode 429. Same weights, so the evals still describe production; up to 2.5x output tokens per second, paid for with premium pricing.
</Step>

<Step title="The deciding cue">
"Quality approved" plus "first words appear quickly" plus "cost increase approved". The first rules out model and effort changes; the second rules out time-to-first-token fixes; the third is the price of fast mode.
</Step>

</Walkthrough>

**Adaptive thinking plus effort, and what thinking costs.** `max_tokens` is the hard cap; effort is guidance; thinking tokens show up in `usage`.

```python
import anthropic

client = anthropic.Anthropic()

def text_of(resp) -> str:
    return "".join(b.text for b in resp.content if b.type == "text")

PROMPT = (
    "A Delta table has 40 partitions; nightly MERGE time doubled after a schema change "
    "added a nested column. List the three most likely causes, most likely first."
)

for effort in ("low", "high"):
    resp = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=16000,                   # hard cap: thinking plus text
        thinking={"type": "adaptive"},      # model decides whether and how much to think
        output_config={"effort": effort},   # soft guidance, not a token budget
        messages=[{"role": "user", "content": PROMPT}],
    )
    details = getattr(resp.usage, "output_tokens_details", None)
    thinking = getattr(details, "thinking_tokens", 0) if details else 0
    kinds = [b.type for b in resp.content]  # never assume content[0] is text
    print(effort, resp.stop_reason, resp.usage.output_tokens, thinking, kinds)
    print(text_of(resp)[:200])
```

```typescript

  console.log(effort, resp.stop_reason, resp.usage.output_tokens, thinking,
    resp.content.map((b) => b.type));
  console.log(textOf(resp).slice(0, 200));
}
```

**Engineering around non-determinism.** A schema fixes the shape; repeated sampling measures agreement; disagreement goes to a human.

```python
import json
from collections import Counter

import anthropic

client = anthropic.Anthropic()

SCHEMA = {
    "type": "object",
    "properties": {"severity": {"type": "string", "enum": ["sev1", "sev2", "sev3"]}},
    "required": ["severity"],
    "additionalProperties": False,
}

def classify(alert: str) -> str:
    resp = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=2048,
        output_config={"effort": "low", "format": {"type": "json_schema", "schema": SCHEMA}},
        messages=[{"role": "user", "content": f"Classify this alert.\n<alert>{alert}</alert>"}],
    )
    text = next(b.text for b in resp.content if b.type == "text")
    return json.loads(text)["severity"]

alert = "Checkout p99 latency 4s for 12 minutes in one region; error rate normal."
votes = Counter(classify(alert) for _ in range(5))
label, n = votes.most_common(1)[0]
print(dict(votes), "agreement", n / 5, "-> review" if n < 4 else "-> auto")
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const SCHEMA = {
  type: "object",
  properties: { severity: { type: "string", enum: ["sev1", "sev2", "sev3"] } },
  required: ["severity"],
  additionalProperties: false,
};

async function classify(alert: string): Promise<string> {
  const resp = await client.messages.create({
    model: "claude-sonnet-5-5",
    max_tokens: 2048,
    output_config: { effort: "low", format: { type: "json_schema", schema: SCHEMA } },
    messages: [{ role: "user", content: `Classify this alert.\n<alert>${alert}</alert>` }],
  });
  const block = resp.content.find((b): b is Anthropic.TextBlock => b.type === "text");
  return JSON.parse(block?.text ?? "{}").severity;
}

const alert = "Checkout p99 latency 4s for 12 minutes in one region; error rate normal.";
const votes = new Map<string, number>();
for (let i = 0; i < 5; i++) {
  const label = await classify(alert);
  votes.set(label, (votes.get(label) ?? 0) + 1);
}
const top = Math.max(...votes.values());
console.log(Object.fromEntries(votes), "agreement", top / 5, top < 4 ? "-> review" : "-> auto");
```

<Output kind="illustrative">

```text
{'sev2': 4, 'sev3': 1} agreement 0.8 -> auto
```

The schema guarantees every vote parses. It cannot guarantee the votes agree.

**Fast mode with a fallback.** Separate rate limit, so fail fast on 429 and drop back to standard speed (a cache miss, but the same model).

```python
import anthropic

client = anthropic.Anthropic()

def draft(prompt: str):
    messages = [{"role": "user", "content": prompt}]
    try:
        return client.with_options(max_retries=0).beta.messages.create(
            model="claude-opus-5-5",
            max_tokens=8000,
            speed="fast",
            betas=["fast-mode-2026-02-01"],
            messages=messages,
        )
    except anthropic.RateLimitError:
        return client.messages.create(
            model="claude-opus-5-5", max_tokens=8000, messages=messages
        )

resp = draft("Draft a post-mortem from these notes: ...")
print(getattr(resp.usage, "speed", "standard"))
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

async function draft(prompt: string) {
  const messages: Anthropic.MessageParam[] = [{ role: "user", content: prompt }];
  try {
    return await client.beta.messages.create(
      {
        model: "claude-opus-5-5",
        max_tokens: 8000,
        speed: "fast",
        betas: ["fast-mode-2026-02-01"],
        messages,
      },
      { maxRetries: 0 },
    );
  } catch (err) {
    if (!(err instanceof Anthropic.RateLimitError)) throw err;
    return client.messages.create({ model: "claude-opus-5-5", max_tokens: 8000, messages });
  }
}

const resp = await draft("Draft a post-mortem from these notes: ...");
console.log((resp.usage as { speed?: string }).speed ?? "standard");
```

## Recall checks

<Recall q="Why can a token budget measured on Claude Sonnet 4.6 be wrong for Claude Sonnet 5.5 even though the prompt text is identical?">
Token counts come from each model's tokenizer. Sonnet 5.5 uses the newer tokenizer that yields about 30% more tokens for the same text, so cost, window fit and max_tokens headroom all change. Recount with count_tokens passing the new model ID.
</Recall>

<Recall q="A request with a huge history fails with 'prompt is too long'. A teammate proposes raising max_tokens. Why is that wrong?">
The input alone exceeds the context window, which is a 400 on every model. max_tokens only caps generated output; raising it cannot admit more input and only increases pressure on the same window. Trim, compact or retrieve less.
</Recall>

<Recall q="What does lowering temperature change, and what can it never guarantee?">
It sharpens the next-token distribution so output favours more probable phrasing. It cannot guarantee identical output: Anthropic documents that even temperature 0.0 is not fully deterministic, and current models reject non-default sampling values anyway.
</Recall>

<Recall q="Name three code-level techniques that make an LLM feature dependable despite non-determinism.">
Enforce shape with structured outputs or strict tools, store and replay outputs where reproducibility matters, and measure behaviour with multi-run evals or majority votes that route disagreement to review. Each puts the guarantee in code rather than in a prompt or a sampling setting.
</Recall>

<Recall q="Why does asking for the verdict before the justification produce less reliable answers?">
Generation is autoregressive with no lookahead: once the verdict tokens are emitted they condition everything after. The justification then rationalises a committed answer. Reasoning first, or thinking, does the work before the answer is fixed.
</Recall>

<Recall q="What does fast mode trade, and what does it not change?">
It trades a premium per-token price for up to 2.5x higher output tokens per second. It runs the same model weights, so quality and behaviour do not change, and it does not target time to first token.
</Recall>

<Recall q="Give two constraints on budget_tokens in extended thinking, and the model family where it is still the only thinking mode.">
budget_tokens must be at least 1,024 and less than max_tokens (thinking counts toward max_tokens, except with interleaved thinking). Claude Haiku 4.5 (with Sonnet 4.5 and Opus 4.5) supports only extended thinking; sending adaptive there returns a 400.
</Recall>

<Recall q="Your parser reads the first content block as text and breaks intermittently after you enable adaptive thinking. Why?">
Adaptive thinking decides per request whether to think, so some responses start with a thinking block and some do not. Iterate content blocks and select those with type text instead of indexing.
</Recall>

<Recall q="Effort is set to low, yet a hard request still produces substantial thinking. Is that a bug?">
No. Effort is a behavioural signal, not a token cap, and Claude still thinks on sufficiently difficult problems at low effort. The hard ceiling is max_tokens.
</Recall>

<Recall q="A classifier labels correctly but returns inconsistent formats. Which shot style fixes it, and which domain covers building the examples?">
Multi-shot: 3 to 5 relevant, diverse examples wrapped in example tags. Naming the technique is D5 LLM Fundamentals; constructing and placing the examples is D6 Prompt Engineering.
</Recall>
