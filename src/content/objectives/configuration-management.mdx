## Concept

This objective tests whether you treat Claude configuration like a Databricks bundle or a Terraform module: an artifact that is **versioned, reviewed, pinned and shared on purpose**. For each of the five surfaces (CLAUDE.md, settings.json, model IDs, prompts, plugins) the exam asks *where does this belong* (shared or personal, advisory or enforced) and *what stops it changing underneath you*.

Two failures recur: drift without a deploy (an alias or unconstrained dependency resolving to something new while the repository is unchanged), and a control on the wrong layer (a "never do X" in CLAUDE.md instead of settings.json, or a team guardrail in a personal file nobody else receives).

**Scope boundary.** This page owns *what to put where* and *how config is versioned, pinned and shared across a team*. The mechanics of the tool itself (how the CLAUDE.md hierarchy loads, slash commands, headless and auto mode, skills and subagents) live in <ObjLink id="claude-code-operation" />. Writing hook scripts that block destructive actions is <ObjLink id="claude-hooks" />. Choosing *which* model to pin is <ObjLink id="model-selection-and-tradeoffs" />.

Not this:
- Storing, injecting or rotating API keys and credentials: <ObjLink id="identity-secrets-and-key-management" /> (Domain 7), even when the key sits in a settings file.
- How Claude interprets instructions across claude.ai, Desktop, the API and Claude Code: <ObjLink id="claude-application-design" />.
- Generic release processes (Agile, ITIL change management): <ObjLink id="systems-life-cycle" />.

<Callout type="key" title="The single idea that wins the most points">
Two axes decide every item. **Advisory vs enforced**: CLAUDE.md and prompts are requests; permissions, hooks and schemas are code. **Floating vs pinned**: an alias, a branch ref or an unconstrained dependency can move without a commit; a full model ID, a commit SHA or a version range you tested cannot. When a stem says behaviour changed with no deploy, look for the floating reference. When it says something must always hold, look for the enforced layer.
</Callout>

## Mechanism

### CLAUDE.md files

<SubskillAnchor id="cfg.claude-md" />

CLAUDE.md is the memory file Claude reads at session start. For configuration management the question is *which file a given line belongs in* and *who receives it*.

| File | Who receives it | Put here |
|---|---|---|
| Managed policy CLAUDE.md (OS path, or the `claudeMd` key in managed settings) | Every user on machines IT deploys it to; cannot be excluded | Company coding standards, compliance and data-handling reminders |
| `./CLAUDE.md` or `./.claude/CLAUDE.md` | The team, via source control | Build and test commands, architecture, naming conventions, workflow rules |
| `./CLAUDE.local.md` | Only you, this project (add it to `.gitignore`) | Your sandbox URLs, preferred test data |
| `~/.claude/CLAUDE.md` | Only you, every project | Personal style and tooling preferences |

What belongs in the project file: facts Claude should hold in *every* session, concrete enough to verify ("Run `npm test` before committing", not "test your changes"). Add a line when Claude makes the same mistake twice. A multi-step procedure belongs in a skill and guidance for one part of the tree in a path-scoped rule, because both load only when needed. Target under 200 lines per file: longer files cost context on every request and reduce adherence. **[Certain]**

**Imports.** `@path/to/file` in a CLAUDE.md expands that file into context at launch. Relative paths resolve from the importing file, and imports nest up to four hops. Imports organise a long file but **do not reduce its context cost**, because imported files also load at launch. An import resolving outside the project (for example `@~/.claude/my-notes.md`) triggers a one-time approval dialog, so a committed CLAUDE.md cannot silently pull in arbitrary files. **[Certain]**

**Team versus personal is a git question.** The project CLAUDE.md is reviewed in pull requests like code; a personal preference committed there becomes everyone's instruction, and a team convention kept in `CLAUDE.local.md` never reaches CI. In a monorepo, `claudeMdExcludes` skips an irrelevant ancestor CLAUDE.md (set it in your local settings). Managed CLAUDE.md cannot be excluded.

**Advisory, not enforced.** Per the docs, settings rules are enforced by the client regardless of what Claude decides; CLAUDE.md shapes behaviour but is not a hard enforcement layer. Block tools or paths with `permissions.deny`; put style and compliance reminders in CLAUDE.md.

**Exam angle:** cues are "conventions every teammate's session should know", "personal sandbox", "organisation-wide reminder". The distractor is CLAUDE.md offered for something that must be guaranteed, or a team rule placed in a personal file.

### settings.json

<SubskillAnchor id="cfg.settings-json" />

settings.json is configuration the harness enforces: permissions, hooks, environment variables, model, plugins. Five levels, highest precedence first: **[Certain]**

| Level | File | Use it for |
|---|---|---|
| 1. Managed | `managed-settings.json`, MDM, or server-managed from the console | Security policy nobody can override |
| 2. Command line | `claude --settings <file-or-json>`, flags | One session |
| 3. Project local | `.claude/settings.local.json` (kept out of git) | Your overrides for this repo |
| 4. Shared project | `.claude/settings.json` (committed) | Team permissions, hooks, plugins, project env |
| 5. User | `~/.claude/settings.json` | Your defaults across all projects |

Three behaviours matter more than the order itself:

- **Scalar keys override; list keys merge.** A `model` set in project local beats the shared file. But `permissions.allow` arrays from every level are combined, so each file adds rules without deleting another's.
- **Deny beats allow across every scope.** Rules are evaluated deny, then ask, then allow, first match wins, and specificity does not reorder them. A user-level deny blocks a project-level allow and vice versa. No level can allow what a managed deny blocks. **[Certain]**
- **Restrictive rules apply immediately; permissive ones wait for trust.** In a committed `.claude/settings.json`, `permissions.allow` rules (and most `env` values) apply only after a developer accepts the workspace trust dialog, while `deny` and `ask` apply at once. A cloned repository cannot quietly grant itself capability. **[Likely]** (detail verified today; exact gating has shifted across releases)

**Hooks registration** lives in the same files. A hook is registered under `hooks`, keyed by event name, with a `matcher` and a list of handlers; a hook in `.claude/settings.json` is shared with the team, one in `~/.claude/settings.json` or the local file is not. A blocking `PreToolUse` hook (exit code 2) stops the call before permission rules are evaluated, so it holds even against an allow rule. Script design is <ObjLink id="claude-hooks" />.

**`env`** sets variables for every session and its subprocesses: the standard way to roll a project's variables (or a model pin) out to the team. A shell-exported `ANTHROPIC_MODEL` still beats a file's `model` key, so per-machine model drift is often a stray export.

Commit to the shared file: team permission rules, hooks, `enabledPlugins`, project env. Keep in the local file: personal approvals (Claude Code saves "Yes, don't ask again" answers there), personal model choice, `claudeMdExcludes`. Credentials are a Domain 7 question.

**Exam angle:** cues are "every developer", "every clone", "cannot be overridden", "for this session only". The distractor is the right rule in the wrong file (local instead of shared, user instead of managed).

### Model version pinning

<SubskillAnchor id="cfg.model-pinning" />

A pin is a model reference that cannot change meaning without a commit. Whether a string is a pin depends on the surface:

| Reference | Floats? | Notes |
|---|---|---|
| Claude API ID, 4.6 generation and later (`claude-sonnet-5-5`) | No | The dateless ID *is* the snapshot. Anthropic ships updates under a new ID. **[Certain]** |
| Claude API dated ID, pre-4.6 (`claude-haiku-4-5-20251001`) | No | Pinned snapshot |
| Claude API alias, pre-4.6 (`claude-sonnet-4-5`) | Yes | Convenience pointer to the most recent dated snapshot of that minor version |
| Claude Code alias (`sonnet`, `opus`, `haiku`, `fable`, `best`, `opusplan`) | Yes | Points to the recommended version *for your provider* and updates over time |

The common misconception the docs call out: dateless IDs from 4.6 onward are **not** evergreen pointers. A Claude Code alias is. On the Anthropic API today `sonnet` resolves to Sonnet 5.5, while on Bedrock and Google Cloud it resolves to an older Sonnet, so the same alias means different models on different providers and different Claude Code versions. **[Likely]** (the resolution table drifts with every release)

**How to pin.** In application code, send a full model ID. In Claude Code, set the full model name in `model` or `--model`, or set `ANTHROPIC_DEFAULT_SONNET_MODEL` / `_OPUS_` / `_HAIKU_` / `_FABLE_` so an alias resolves to the version you chose. For third-party deployments the docs say to pin before rolling out: unpinned aliases resolve to a built-in default that can lag the newest release or be unavailable in the account. **[Certain]**

**Cloud vendors pin differently.** The ID string changes per platform, so a pin is per platform too:

- **Amazon Bedrock**: `anthropic.` prefix (`anthropic.claude-sonnet-5-5`); pre-4.6 IDs add a date and `-v1:0`; inference profile IDs can add a geography prefix such as `us.` **[Likely]**. Bedrock sets its own retirement dates.
- **Google Cloud**: same as the API for 4.6 and later; pre-4.6 separates the date with `@` (`claude-haiku-4-5@20251001`). Google sets its own retirement dates.
- **Microsoft Foundry**: you send a deployment name you defined; Foundry follows Anthropic's lifecycle.
- **Claude Code `modelOverrides`** maps an Anthropic model ID to a provider string (for example a Bedrock inference profile ARN) for governance or regional routing.

**Why production pins.** Reproducibility (an eval result describes one model), attribution (a regression maps to your change) and controlled upgrades. The cost: pinned models move through **Active, Legacy, Deprecated, Retired**. Deprecated models get a named replacement and a retirement date with at least 60 days' notice for publicly released models; requests to a retired model fail. A pin is therefore a scheduled migration, run through the eval suite before the date. **[Certain]**

Caveat from the versioning page: weights are fixed per ID, but serving infrastructure (routing, safety classifiers, sampling logic) can change and occasionally shifts behaviour slightly on a pinned ID. Pinning removes model drift, not the need for monitoring.

**Exam angle:** cues are "changed with no deploy", "different results on Bedrock than in dev", "control when users move". The distractor relocates an alias (env var, settings file) instead of replacing it with a full ID.

### Prompt versioning

<SubskillAnchor id="cfg.prompt-versioning" />

Prompts are code. The production unit you evaluated is not "the prompt"; it is the tuple **(prompt version, pinned model ID, tool definitions, output schema, effort)**. Change any element and the eval result no longer describes production.

The discipline, in order:

1. **Source control.** System prompts, few-shot sets and tool descriptions live in the repository as files, reviewed in pull requests. Editing a production prompt in a database row or a live console without a trail is the anti-pattern.
2. **Identify every call.** Log `prompt_id@version` (or a content hash) and the model ID on every request, so an output can be traced to the exact release that produced it.
3. **Eval-gate the change.** A prompt edit that fixes one reported case commonly regresses others. Run the regression suite on every prompt change and every model upgrade before promotion. Anthropic's guidance on agent evals describes exactly this: capability evals that graduate into a regression suite run continuously in CI/CD "on each agent change and model upgrade". **[Certain]**
4. **Promote and roll back by version.** Rollback is redeploying the previous tagged prompt, as fast as a code rollback, because it *is* a code rollback.

Side effect: a new prompt version is a prompt-cache miss. The cache prefix runs `tools`, then `system`, then `messages`, and a change at one level invalidates it and everything after, so expect a cost bump right after a deploy. **[Certain]**

<Flow title="A prompt or model change, as a release" steps={[{label: "PR edits prompt file or model pin", kind: "client"}, {label: "Regression evals on candidate", kind: "guard", note: "same cases, pinned model"}, {label: "Pass rate vs baseline", kind: "decision"}, {label: "Tag prompt@version, deploy", kind: "store"}, {label: "Log prompt@version + model per call", kind: "api", note: "rollback = redeploy prior tag"}]} />

**Exam angle:** cues are "a prompt tweak broke other cases", "cannot tell which prompt produced this output", "roll back quickly". The distractor is "test the new prompt manually on the failing example" or "store prompts in a database so they can be edited without a deploy".

### Plugin dependencies

<SubskillAnchor id="cfg.plugin-deps" />

A Claude Code plugin packages skills, subagents, hooks and MCP servers as one unit, described by `.claude-plugin/plugin.json` and listed in a marketplace catalog (`marketplace.json`). The questions here: which version a user actually gets, what a plugin pulls in, and how a team receives it.

**Version resolution.** The plugin's computed version comes from `plugin.json` first, then the marketplace entry. Do not set it in both: `plugin.json` wins, and only `claude plugin validate` reports the mismatch. Users get a new copy only when the computed version changes, so either bump `version` every release or omit it everywhere and let users track commits. Pushing commits under an unchanged `"version": "1.0.0"` ships nothing. **[Certain]**

**Source pinning.** Git-based sources take `ref` (a branch or tag) and `sha` (a full 40-character commit). When both are set, Claude Code checks out the `sha`. A `ref` to a moving branch is a floating reference; a `sha` is a pin.

**Declared dependencies.** A plugin lists the plugins it relies on in a `dependencies` array in `plugin.json`. A bare name tracks whatever its marketplace publishes, so an upstream rename of an MCP tool breaks every user on their next update. An object entry takes a semver range (`~2.1.0`, `^2.0`) resolved against git tags named `<plugin-name>--v<version>`. Dependencies from a *different* marketplace are refused unless the root marketplace allowlists it, so one catalog cannot silently install code from a source the user never reviewed. **[Likely]**

**Team distribution.** Install scope maps to the settings files: user scope, project scope (written to the shared settings so every collaborator gets it) or local scope. An organisation can require plugins through `enabledPlugins` in managed settings, and a platform team can publish a "bundle" plugin whose only content is a `dependencies` list.

<Callout type="note" title="Exam confidence">
The guide names plugin dependencies but no mechanics, and the plugin system changes often. Expect items on the principle (pin versions, treat an update like any dependency bump, prefer an exact commit for reproducible installs) rather than on field names such as `dependencies` or tag formats.
</Callout>

**Exam angle:** cues are "reproducible installs", "users still get the old build", "an upstream update broke our plugin". The distractor pins a branch `ref` and calls it reproducible, or bumps the catalog version while `plugin.json` still declares the old one.

## Decision table

| If the stem says... | Choose | Why the runner-up loses |
|---|---|---|
| Output changed on a day with no deploy, no prompt edit, no config commit | Replace the floating alias with a full model ID (or set `ANTHROPIC_DEFAULT_*_MODEL`) and gate the next bump on evals | "Move the model name into an env var" keeps the alias; the drift moves with it |
| Every developer and every clone must get the same deny rule | `permissions.deny` in the committed `.claude/settings.json` (or managed settings if it must be unoverridable) | `.claude/settings.local.json` is personal and gitignored; teammates never receive it |
| No individual developer may be able to switch a rule off | Managed settings (or managed CLAUDE.md for guidance) | Shared project settings can be overridden by a developer's local file for scalar keys |
| Claude keeps forgetting the build command and test flags | Project CLAUDE.md, concrete and short | A hook enforces actions; it does not teach Claude facts |
| Claude must never run a command, whatever the prompt says | Deny rule or `PreToolUse` hook in shared settings | A CLAUDE.md "NEVER" is a request the model usually follows |
| A prompt fix for one ticket regressed other categories | Version the prompt, run the regression suite on each change, promote by tag | Hand-testing the failing example cannot reveal what else broke |
| Same model alias, different behaviour on Bedrock versus the Anthropic API | Pin per-provider IDs (`ANTHROPIC_DEFAULT_*_MODEL`, `modelOverrides`) | Aliases resolve per provider and can lag; a shared alias is not a shared model |
| Marketplace entry bumped, users still on the old plugin | Fix or remove the stale `version` in `plugin.json` | `plugin.json` silently wins over the catalog entry |
| Plugin installs must be identical across the team | Git source with an explicit `sha` | A `ref` to a branch moves with every push |
| How should the app's API key be stored and rotated | Out of scope here: Domain 7 secrets management | Naming settings.json does not make it a configuration-management item |

## Worked walkthrough

<Walkthrough title="Scenario: a Claude Code rollout on Amazon Bedrock that changed on its own">

<Step title="Read the scenario">
A platform team rolls Claude Code out to 60 engineers through Amazon Bedrock, with `"model": "sonnet"` in the committed `.claude/settings.json`. Three weeks later engineers report that the same refactoring requests now produce noticeably different diffs, yet the repository, CLAUDE.md and settings files have no new commits since rollout. The lead wants every engineer to stay on the version the team evaluated until the team decides to move.

Options: (A) add "Always use the Sonnet version we evaluated" to the project CLAUDE.md; (B) ask each engineer to run `/model sonnet` at the start of every session; (C) set `ANTHROPIC_DEFAULT_SONNET_MODEL` to the evaluated Bedrock model ID in the `env` block of the shared or managed settings, and change it only after an eval run; (D) move `"model": "sonnet"` from the project file into managed settings so nobody can override it.
</Step>

<Step title="Find the buried constraint">
"No new commits" plus "behaviour changed" means something resolved differently on its own. The only floating reference is the alias `sonnet`, which tracks the provider's recommended version and changes over time (including when engineers update Claude Code). "Until the team decides to move" demands an explicit, reviewable value.
</Step>

<Step title="Eliminate A and B">
**A** puts model selection into CLAUDE.md, but Claude does not choose which model serves the session, and CLAUDE.md is advisory anyway. **B** is manual, unenforced, and still selects the drifting alias.
</Step>

<Step title="Eliminate D, the strongest distractor">
**D** looks rigorous because managed settings top the precedence stack. But the value is still `sonnet`, so it resolves to whatever Claude Code maps it to on Bedrock this week. Moving where a value is read from is not pinning.
</Step>

<Step title="Choose C">
**C** binds the alias to a full, provider-specific model ID that changes only through a reviewed edit, as the model configuration docs recommend for third-party deployments. Gate future edits on an eval run.
</Step>

<Step title="The deciding cue">
"**No new commits**" with changed behaviour points to a floating reference, and "**stay on the version the team evaluated**" demands a full model ID. Any option that keeps the word `sonnet` as the value, wherever it lives, fails.
</Step>

</Walkthrough>

## Code

**A release is a tuple: prompt version plus pinned model, logged on every call.** The allowlist makes "use an unevaluated model" a code-review event instead of a runtime surprise.

```python
import hashlib
import anthropic

client = anthropic.Anthropic()

# Model IDs that have passed the regression suite. Adding one is a reviewed PR.
EVALUATED_MODELS = {"claude-sonnet-5-5", "claude-haiku-4-5-20251001"}

RELEASE = {
    "prompt_id": "ticket-triage",
    "prompt_version": "3.2.0",
    "model": "claude-haiku-4-5-20251001",  # dated pre-4.6 ID: a pinned snapshot
    "system": (
        "You label support tickets for a payments product. "
        "Reply with exactly one word: billing, access, bug, or other."
    ),
}


def text_of(resp) -> str:
    return "".join(b.text for b in resp.content if b.type == "text")


def triage(ticket: str) -> dict:
    if RELEASE["model"] not in EVALUATED_MODELS:
        raise ValueError(f"{RELEASE['model']} has not passed evals")
    resp = client.messages.create(
        model=RELEASE["model"],
        max_tokens=16,
        system=RELEASE["system"],
        messages=[{"role": "user", "content": ticket}],
    )
    return {
        "label": text_of(resp).strip().lower(),
        "prompt": f"{RELEASE['prompt_id']}@{RELEASE['prompt_version']}",
        "prompt_sha": hashlib.sha256(RELEASE["system"].encode()).hexdigest()[:12],
        "model": resp.model,  # what actually served the request
    }


print(triage("I was charged twice for my May invoice."))
```

```typescript
import Anthropic from "@anthropic-ai/sdk";
import { createHash } from "node:crypto";

const client = new Anthropic();

// Model IDs that have passed the regression suite. Adding one is a reviewed PR.
const EVALUATED_MODELS = new Set(["claude-sonnet-5-5", "claude-haiku-4-5-20251001"]);

const RELEASE = {
  promptId: "ticket-triage",
  promptVersion: "3.2.0",
  model: "claude-haiku-4-5-20251001", // dated pre-4.6 ID: a pinned snapshot
  system:
    "You label support tickets for a payments product. " +
    "Reply with exactly one word: billing, access, bug, or other.",
};

function textOf(resp: Anthropic.Message): string {
  return resp.content
    .filter((b): b is Anthropic.TextBlock => b.type === "text")
    .map((b) => b.text)
    .join("");
}

async function triage(ticket: string) {
  if (!EVALUATED_MODELS.has(RELEASE.model)) {
    throw new Error(`${RELEASE.model} has not passed evals`);
  }
  const resp = await client.messages.create({
    model: RELEASE.model,
    max_tokens: 16,
    system: RELEASE.system,
    messages: [{ role: "user", content: ticket }],
  });
  return {
    label: textOf(resp).trim().toLowerCase(),
    prompt: `${RELEASE.promptId}@${RELEASE.promptVersion}`,
    promptSha: createHash("sha256").update(RELEASE.system).digest("hex").slice(0, 12),
    model: resp.model, // what actually served the request
  };
}

console.log(await triage("I was charged twice for my May invoice."));
```

**An eval gate: a candidate prompt version ships only if it does not regress the fixed case set.** Same pinned model on both sides, so the only variable is the prompt.

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-haiku-4-5-20251001"

CASES = [
    ("I was charged twice for my May invoice.", "billing"),
    ("SSO login loops back to the sign-in page.", "access"),
    ("Export to CSV drops the last row.", "bug"),
    ("Do you have an office in Lisbon?", "other"),
]


def text_of(resp) -> str:
    return "".join(b.text for b in resp.content if b.type == "text")


def pass_rate(system: str) -> float:
    hits = 0
    for ticket, expected in CASES:
        resp = client.messages.create(
            model=MODEL,
            max_tokens=16,
            system=system,
            messages=[{"role": "user", "content": ticket}],
        )
        hits += text_of(resp).strip().lower() == expected
    return hits / len(CASES)


def gate(baseline: str, candidate: str) -> bool:
    base, cand = pass_rate(baseline), pass_rate(candidate)
    print(f"baseline={base:.2f} candidate={cand:.2f}")
    return cand >= base  # promote only on no regression
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();
const MODEL = "claude-haiku-4-5-20251001";

const CASES: [string, string][] = [
  ["I was charged twice for my May invoice.", "billing"],
  ["SSO login loops back to the sign-in page.", "access"],
  ["Export to CSV drops the last row.", "bug"],
  ["Do you have an office in Lisbon?", "other"],
];

function textOf(resp: Anthropic.Message): string {
  return resp.content
    .filter((b): b is Anthropic.TextBlock => b.type === "text")
    .map((b) => b.text)
    .join("");
}

async function passRate(system: string): Promise<number> {
  let hits = 0;
  for (const [ticket, expected] of CASES) {
    const resp = await client.messages.create({
      model: MODEL,
      max_tokens: 16,
      system,
      messages: [{ role: "user", content: ticket }],
    });
    if (textOf(resp).trim().toLowerCase() === expected) hits++;
  }
  return hits / CASES.length;
}

export async function gate(baseline: string, candidate: string): Promise<boolean> {
  const [base, cand] = [await passRate(baseline), await passRate(candidate)];
  console.log(`baseline=${base.toFixed(2)} candidate=${cand.toFixed(2)}`);
  return cand >= base; // promote only on no regression
}
```

## Recall checks

<Recall q="Why does moving `model: sonnet` from code into an environment variable or managed settings not fix 'quality changed with no deploy'?">
Because the value is still an alias, and an alias resolves to the recommended version for the provider, which changes over time. Pinning means changing the value to a full model ID (or setting the `ANTHROPIC_DEFAULT_*_MODEL` variable to one), not relocating where the alias is read.
</Recall>

<Recall q="Is `claude-sonnet-5-5` a floating alias like `claude-sonnet-4-5`?">
No. From the 4.6 generation on, the dateless ID is the canonical snapshot and Anthropic ships updates under a new ID. `claude-sonnet-4-5` is a pre-4.6 convenience alias that points to the latest dated snapshot of that minor version.
</Recall>

<Recall q="A guardrail deny rule was added to `.claude/settings.local.json`. Why do teammates not have it, and where should it go?">
The local file is personal and kept out of git, so it never reaches other clones, CI or cloud sessions. Put it in the committed `.claude/settings.json`, or in managed settings if no developer may override it.
</Recall>

<Recall q="User settings allow `Bash(git push *)` and project settings deny it. What happens and why?">
The push is blocked. Deny rules from every scope are evaluated before allow rules, first match wins, so no level can carve an allow out of another level's deny.
</Recall>

<Recall q="What does a CLAUDE.md `@import` do to context cost?">
Nothing good: imported files expand into context at launch alongside the importing file, so imports organise a long CLAUDE.md without shrinking it. To cut cost, move part-of-tree guidance into path-scoped rules and procedures into skills.
</Recall>

<Recall q="What is the unit you version and eval for a production prompt, and why?">
The tuple of prompt version, pinned model ID, tool definitions, output schema and effort, because changing any element invalidates the eval result. Log the prompt version and model on every call so a regression traces to one change and rollback is redeploying the previous tag.
</Recall>

<Recall q="A marketplace entry says 2.0.0, the plugin's `plugin.json` says 1.4.0, and users never receive the update. Why?">
The computed version comes from `plugin.json` first, so users see 1.4.0, which matches their cached copy, and nothing updates. Set the version in one place only, and bump it every release (or omit it and track commits).
</Recall>
