## Concept

The guide asks you to choose a model **for a task**: match tier to difficulty, latency and volume, know which tiers accept which thinking controls, price the choice per completed task, and recognise that moving to a new release is a migration with breaking changes. Version numbers drift; the tradeoffs do not. Learn the shape of each tier and treat specific IDs and prices as `facts.json` data.

**Scope boundary.** Not this:

- What tokens, thinking, effort and fast mode *are*: <ObjLink id="llm-fundamentals" />.
- Caching, batch discounts and spend monitoring as cost tools: <ObjLink id="cost-and-token-management" />. The Batch API itself is <ObjLink id="claude-api-mechanics" />.
- Where the model ID lives and how it is promoted between environments: <ObjLink id="configuration-management" />.

<Callout type="key" title="The single idea that wins the most points">
Inside one model, **effort** is the low-risk quality/cost dial because it preserves evaluated behaviour. **Changing the model** is the high-risk move: it invalidates evals and can break request shapes. Exhaust effort first; swap tiers only behind evals.
</Callout>

## Mechanism

### Opus vs Sonnet vs Haiku use cases

<SubskillAnchor id="ms.tiers" />

| Tier | Shape | Reach for it when | Current example (from `facts.json`) |
|---|---|---|---|
| Haiku | Fastest, cheapest, 200K window, 64K output, extended thinking only | High-volume, latency-sensitive, narrow tasks: routing, classification, extraction, sub-agent work | `claude-haiku-4-5`, $1 / $5 per MTok |
| Sonnet | Best combination of speed and intelligence, 1M window | Default production and agentic work, code generation, data analysis | `claude-sonnet-5-5`, $2 / $10 |
| Opus | Deep reasoning, long-running agentic coding and knowledge work, 1M window | Hard multistep reasoning, large refactors, autonomous agents where Sonnet's ceiling binds | `claude-opus-5-5`, $4 / $20 |

Above Opus sits a "most capable" tier (currently Claude Fable 5.1 at $10 / $50, slower) for work where Opus at high effort still falls short. Comparative latency on the overview runs Fastest (Haiku), Fast (Sonnet), Moderate (Opus), Slower (Fable). [Certain as of 2026-10-06, models overview; drifts]

Anthropic describes two ways to pick a starting point [Certain, choosing a model]:

- **Efficiency-first**: start on Haiku, test, upgrade only for proven capability gaps. Fits prototypes, tight latency, cost-sensitive and high-volume straightforward work.
- **Capability-first**: start on the strongest model, optimise prompts, then lower effort or downgrade while evals hold. Fits complex reasoning, nuanced understanding, accuracy over cost, high-autonomy agents.

The docs disagree on the default: the pricing page says Haiku for simple tasks, Sonnet for most production, Opus for the most complex; the current overview says start most workloads on Opus 5.5. [Certain that both exist; Likely that guide-era items follow the Haiku / Sonnet / Opus split.] Either way, the stem's framing (volume versus feasibility) picks the direction, and evals decide.

**Exam angle:** "high volume", "narrow", "real time" point to Haiku; "everyday production", "balanced" to Sonnet; "hardest reasoning", "long-horizon agent" to Opus. The distractor defaults to the most capable model for a routing step.

### Adaptive thinking support

<SubskillAnchor id="ms.adaptive" />

Thinking controls are not uniform across tiers, and that is the testable part:

| Model | Adaptive thinking | `budget_tokens` | Effort |
|---|---|---|---|
| Haiku 4.5 | 400 error | Required for thinking (min 1,024, below `max_tokens`) | Not supported |
| Sonnet 4.6, Opus 4.6 | Supported, set explicitly | Deprecated, still works | Supported |
| Opus 4.7 and later, Sonnet 5 and later, Fable | Supported (on by default from Opus 5 and Sonnet 5) | 400 error | Supported, five levels |

[Certain, thinking and effort pages] Haiku is the trap: it is not a small Sonnet. You cannot "turn effort down" on it, and adaptive thinking fails outright. Opus 4.5 is the one extended-thinking-only model that also takes effort.

<PostGuide title="Post-guide detail: thinking defaults on the newest models">
Opus 5.5 and Fable models run adaptive thinking always; `disabled` is a 400. Sonnet 5.5 rejects `disabled` and uses `thinking: {"type": "between_tools"}` as its lowest setting. Opus 5.5 defaults to `medium` effort while most models default to `high`. [Certain on the thinking and effort pages today.]
</PostGuide>

**Exam angle:** "mixed difficulty, let the model decide how much to reason" requires an adaptive-capable tier. A stem pairing Haiku with effort or adaptive thinking is describing a request that fails.

### Quality, latency and cost tradeoffs

<SubskillAnchor id="ms.tradeoffs" />

Apply levers in order of risk [Certain for the guidance on the choosing-a-model and effort pages; the ordering is Likely]:

1. **Effort on the current model.** Often a better lever than switching models. Lower effort means fewer tokens, fewer tool calls, lower latency.
2. **Tier.** Changes quality, latency and price together, and requires re-running evals.
3. **Delivery mode.** Fast mode buys output speed on supported Opus models at a premium; batch buys 50% off when nobody is waiting.

**Worked cost per task.** An email triage route extracts five fields per message. Measured on Haiku: 2,000 input tokens, 300 output tokens. Prices from `facts.json`. Thinking volumes are illustrative assumptions.

| Model and setting | Input tokens | Output tokens (text + thinking) | Cost per task | Per 1M tasks |
|---|---|---|---|---|
| Haiku 4.5, thinking off | 2,000 | 300 | $0.0020 + $0.0015 = **$0.0035** | $3,500 |
| Sonnet 5.5, effort `low` | 2,600 | 300 + 300 | $0.0052 + $0.0060 = **$0.0112** | $11,200 |
| Opus 5.5, effort `medium` | 2,600 | 300 + 900 | $0.0104 + $0.0240 = **$0.0344** | $34,400 |

Two corrections a naive per-token comparison misses. First, Sonnet 5.5 and Opus 5.5 use the newer tokenizer, so the same email is about 30% more input tokens (2,000 becomes about 2,600). [Likely; recount for real] Second, thinking bills as output on tiers where it runs by default.

Now price **completion**, not requests. If Haiku passes a schema-plus-rules validator on 92% of emails and the rest escalate to Sonnet, the cascade costs $0.0035 + 0.08 × $0.0112 = **$0.0044** per completed task. If those failures instead go to a human at $0.50 each, Haiku-only costs $0.0035 + 0.08 × $0.50 = **$0.0435**, more than Opus. The cascade only works when failures are machine-detectable.

<Flow title="Cost-aware cascade" steps={[{label: "Haiku 4.5", kind: "model", note: "cheap first pass"}, {label: "Validator", kind: "guard", note: "schema + business rules"}, {label: "Pass: done", kind: "store"}, {label: "Fail: Sonnet 5.5", kind: "model", note: "escalate the minority"}]} caption="Cost per completed task depends on the escalation rate and on failures being detectable in code." />

**Exam angle:** stems that give a failure rate or review cost next to per-token prices want cost per completed task. The distractor picks the lowest price per MTok.

### Breaking behaviour changes across releases

<SubskillAnchor id="ms.breaking" />

A breaking change means a request shape that worked returns an error, or the same request silently costs or behaves differently, purely because the model ID changed. Two predate the guide [Certain]:

- **Assistant prefill removed** from the Claude 4.6 models onward: a prefilled final assistant turn returns a 400 ("This model does not support assistant message prefill. The conversation must end with a user message."). Replace format-forcing prefill with structured outputs (<ObjLink id="output-handling" />), preamble-skipping with a system prompt instruction, and continuations with a user-turn instruction.
- **Manual thinking budgets deprecated** on the 4.6 models in favour of adaptive thinking plus effort.

<PostGuide title="Post-guide breaking changes (engineering knowledge, low exam confidence)">

| Change | Models | Symptom | Fix |
|---|---|---|---|
| `budget_tokens` rejected | Claude 4.7 and later | 400 "thinking.type.enabled is not supported for this model" | Adaptive thinking plus effort; evaluate 2 or 3 levels |
| Sampling parameters rejected | Opus 4.7+, Sonnet 5+, Fable | 400 on non-default `temperature`, `top_p`, `top_k` | Remove; use effort, instructions, schemas |
| Forced `tool_choice` rejected | Opus 5.5, Sonnet 5.5, Fable 5.1 | 400 "tool_choice: type tool and any are not supported for this model." | `auto` plus `strict: true`, or structured outputs |
| New tokenizer | Claude 4.7 and later models | About 30% more tokens, higher bills, earlier truncation | Recount with `count_tokens`; revisit `max_tokens` |
| Thinking on by default | Opus 5+, Sonnet 5+ | Old `max_tokens` truncates; output bill rises | Raise `max_tokens`; set effort explicitly |
| Effort default and calibration | Opus 5.5 (`medium`), Sonnet 5.5 (recalibrated) | Silent quality or cost shift | Set effort explicitly; re-run the effort sweep |
| Thinking display omitted | Sonnet 5.5 confirmed; other recent models [Likely] | Empty thinking text in UIs | `display: "summarized"` |

[Certain on the Sonnet 5.5 migration guide and thinking page today; model lists drift.]

</PostGuide>

How to migrate safely:

1. **Pin the ID** in configuration, not code. From the 4.6 generation, dateless IDs are fixed snapshots; older dateless names are aliases that move. Weights never change under an ID, but serving infrastructure can. [Certain, model IDs page]
2. **Read the target's migration guide**, then fix the request shapes above.
3. **Recount tokens** and re-baseline cost.
4. **Re-run the eval suite** on the new model, including an effort sweep. Anthropic calls a good evaluation set the most important step in deciding whether to change models. [Certain, choosing a model]
5. **Canary** behind a config flag with rollback, and watch retirement dates (each ID has its own schedule). See <ObjLink id="configuration-management" />.

**Exam angle:** "after updating the model ID, requests fail with 400" or "same price, higher bill" point here. Distractors: retrying the 400 (not transient), reverting forever (models retire), and shipping after only fixing the errors (no evals).

## Decision table

| If the stem says... | Choose | Why the runner-up loses |
|---|---|---|
| Millions of short routing calls, sub-second budget, evals pass on the small model | Haiku | Sonnet or Opus add cost and latency the task does not need |
| Route already passes evals; cost must drop | Lower effort on the same model | A tier swap invalidates the evals |
| "Lower the effort" on a Haiku 4.5 route | Not possible: use `budget_tokens` or move to Sonnet | Haiku has no effort parameter |
| Hard multistep agentic task; feasibility unproven | Start capability-first on Opus, optimise down | Starting cheap cannot tell a capability gap from a prompt problem |
| Per-token prices plus a failure rate and human review cost | Compare cost per completed task | Lowest price per MTok ignores escalation and review |
| New model ID, previously valid requests now return 400 | Fix request shapes per the migration guide, then re-run evals | Retrying a 400 never succeeds |
| Same price per token, bill up about 30% after migration | Recount with `count_tokens` on the new model | Old counts used the previous tokenizer |
| Behaviour shifted with no code or model change | Monitor and re-run evals | Pinned IDs keep weights, but serving infrastructure can change |

## Worked walkthrough

<Walkthrough title="Scenario: Moving a clause extractor to a newer Sonnet">

<Step title="Read the scenario">
A legal-ops team runs a clause extractor on `claude-sonnet-4-6`. It prefills the assistant turn with an opening brace to force JSON and sets `temperature` to 0. To cut cost they change the model string to `claude-sonnet-5-5`. Every request now returns a 400, and the head of legal requires that extraction accuracy must not regress. What is the right next step?
</Step>

<Step title="Find the constraint">
Two facts. The failures are 400s caused by request shape: prefill and a non-default sampling value, both rejected on the newer model. And "must not regress" makes evaluated accuracy the acceptance bar, not "requests succeed".
</Step>

<Step title="Eliminate the distractors">
Adding retries with backoff fails: a 400 is a validation error, not a transient fault. Moving to Haiku 4.5 because it still accepts prefill swaps tiers to dodge an error and still needs evaluation. Deleting the prefill and temperature lines and shipping fixes the errors but nothing proves accuracy held, and the new tokenizer changes token counts.
</Step>

<Step title="Choose">
Replace the prefill with structured outputs (`output_config.format` with the clause schema), remove `temperature`, recount tokens and adjust `max_tokens`, run the extraction eval suite on `claude-sonnet-5-5` at two or three effort levels, then canary behind a config flag with rollback to the pinned old ID.
</Step>

<Step title="The deciding cue">
"Every request now returns a 400" says request shape changed. "Must not regress" says evals gate the release. Only the option that does both is correct.
</Step>

</Walkthrough>

## Code

**Cost per completed task, measured.** Count input under each model's tokenizer, run one request to read real output and thinking tokens, and price with `facts.json` rates. Haiku takes no effort parameter.

```python
import anthropic

client = anthropic.Anthropic()

PRICES = {  # USD per MTok (input, output), from src/data/facts.json
    "claude-haiku-4-5": (1, 5),
    "claude-sonnet-5-5": (2, 10),
    "claude-opus-5-5": (4, 20),
}
EMAIL = "Hi, invoice INV-2291 for 4,200 EUR is overdue since 3 Sept. Please confirm the payment date."
messages = [{"role": "user", "content": f"Extract vendor, invoice_id, amount, currency, due_status.\n<email>{EMAIL}</email>"}]

def run(model: str):
    extra = {} if model == "claude-haiku-4-5" else {"output_config": {"effort": "low"}}
    return client.messages.create(model=model, max_tokens=4096, messages=messages, **extra)

for model, (p_in, p_out) in PRICES.items():
    counted = client.messages.count_tokens(model=model, messages=messages).input_tokens
    resp = run(model)
    cost = (resp.usage.input_tokens * p_in + resp.usage.output_tokens * p_out) / 1_000_000
    print(f"{model:18} counted_in={counted:5} out={resp.usage.output_tokens:5} cost=${cost:.5f}")
```

```typescript
const client = new Anthropic();

const PRICES: Record<string, [number, number]> = {
  // USD per MTok (input, output), from src/data/facts.json
  "claude-haiku-4-5": [1, 5],
  "claude-sonnet-5-5": [2, 10],
  "claude-opus-5-5": [4, 20],

  console.log(model, counted, resp.usage.output_tokens, cost.toFixed(5));
}
```

**Migration gate.** Run the same golden set on the pinned old ID and the candidate; promote only if the candidate's pass rate holds. Legacy `claude-sonnet-4-6` appears here as the migration source.

```python
import json

import anthropic

client = anthropic.Anthropic()

SCHEMA = {
    "type": "object",
    "properties": {"clause": {"type": "string", "enum": ["indemnity", "termination", "liability_cap", "other"]}},
    "required": ["clause"],
    "additionalProperties": False,
}
GOLDEN = [
    ("Either party may end this agreement on 30 days written notice.", "termination"),
    ("Total liability shall not exceed fees paid in the prior 12 months.", "liability_cap"),
]

def label(model: str, text: str) -> str:
    resp = client.messages.create(
        model=model,
        max_tokens=2048,
        output_config={"format": {"type": "json_schema", "schema": SCHEMA}},
        messages=[{"role": "user", "content": f"Classify the clause.\n<clause>{text}</clause>"}],
    )
    return json.loads(next(b.text for b in resp.content if b.type == "text"))["clause"]

def pass_rate(model: str) -> float:
    return sum(label(model, t) == want for t, want in GOLDEN) / len(GOLDEN)

baseline, candidate = pass_rate("claude-sonnet-4-6"), pass_rate("claude-sonnet-5-5")
print(baseline, candidate, "promote" if candidate >= baseline else "hold")
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const SCHEMA = {
  type: "object",
  properties: { clause: { type: "string", enum: ["indemnity", "termination", "liability_cap", "other"] } },
  required: ["clause"],
  additionalProperties: false,
};
const GOLDEN: [string, string][] = [
  ["Either party may end this agreement on 30 days written notice.", "termination"],
  ["Total liability shall not exceed fees paid in the prior 12 months.", "liability_cap"],
];

async function label(model: string, text: string): Promise<string> {
  const resp = await client.messages.create({
    model,
    max_tokens: 2048,
    output_config: { format: { type: "json_schema", schema: SCHEMA } },
    messages: [{ role: "user", content: `Classify the clause.\n<clause>${text}</clause>` }],
  });
  const block = resp.content.find((b): b is Anthropic.TextBlock => b.type === "text");
  return JSON.parse(block?.text ?? "{}").clause;
}

async function passRate(model: string): Promise<number> {
  let ok = 0;
  for (const [text, want] of GOLDEN) if ((await label(model, text)) === want) ok++;
  return ok / GOLDEN.length;
}

const baseline = await passRate("claude-sonnet-4-6"); // legacy migration source
const candidate = await passRate("claude-sonnet-5-5");
console.log(baseline, candidate, candidate >= baseline ? "promote" : "hold");
```

## Recall checks

<Recall q="A support router makes millions of short classification calls with a sub-second budget. Which tier fits, and what confirms the choice?">
Haiku: fastest and cheapest, built for high-volume narrow tasks. An eval on real traffic confirms it; if it fails, escalate the failing slice rather than moving the whole route up a tier.
</Recall>

<Recall q="Why does a request with adaptive thinking or effort fail on Claude Haiku 4.5?">
Haiku 4.5 supports only extended thinking with budget_tokens. Adaptive thinking returns a 400 and there is no effort parameter, so moving between Haiku and Sonnet changes request shape, not just price.
</Recall>

<Recall q="A Sonnet route passes its evals but costs too much. What do you try before changing tier, and why?">
Lower effort on the same model. It keeps the weights and behaviour the evals measured; a tier swap changes the model and invalidates every result.
</Recall>

<Recall q="Haiku costs a quarter of Opus per input token. When can Haiku-only still be the more expensive design?">
When failures need costly handling. If a slice of tasks fails and goes to human review, review cost per completed task can exceed the token savings; a cascade works only when failures are machine-detectable.
</Recall>

<Recall q="After swapping to a newer model ID, previously valid requests return 400 and the bill rose at the same price per token. Name two likely causes.">
Rejected request shapes (prefill, budget_tokens, non-default sampling or forced tool_choice) cause the 400s. The newer tokenizer produces about 30% more tokens for the same text, and thinking on by default adds billed output.
</Recall>

<Recall q="What does a pinned model ID guarantee, and what can still change?">
The weights stay fixed for the life of the ID. Serving infrastructure such as routing, safety classifiers and sampling logic can still change, so monitoring and periodic evals remain necessary.
</Recall>
