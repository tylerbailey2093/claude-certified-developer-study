## Concept

Claude Application Design asks one recurring question in five forms: **given what the stem requires, where does this thing belong?** Where does an instruction live so that it reaches exactly the right sessions for exactly the right length of time? Which channel does a piece of content travel in so the model can tell your instructions from someone else's text? What shape does a schema need so that the model can be correct instead of merely complete? Where does one session end and the next begin? Which plugins belong in every session, and which are a liability you have not reviewed?

None of these is about which workflow to build. Two teams can ship the same pipeline and differ completely here: one puts its must-never rule in a prompt, splices customer text into the system prompt, forces a required field the source rarely contains, and keeps one conversation per agent across all their customers. The shared failure mode is an application that works in a demo and fails quietly in production through drift, injection, fabrication or leakage.

The guide introduces its five areas with "including", so treat them as the core, not a fence. Items usually hide one constraint (an audience, a lifetime, a source of text, a "must") and offer three options that each fit a slightly different requirement.

**Scope boundary.** Choosing between prompt chaining, routing, parallelization, orchestrator-workers and evaluator-optimizer is <ObjLink id="agent-architecture" /> in Domain 1. How injection attacks work and the full layered defence belongs to <ObjLink id="ai-application-security" />; this page owns the structural boundary that makes those defences possible. Settings precedence, environment promotion and version pinning are <ObjLink id="configuration-management" />; this page uses them only to decide where an instruction lives. Parsing and validating what comes back is <ObjLink id="output-handling" />. Writing a good instruction (clarity, examples) is <ObjLink id="prompt-engineering" />; this page is about where that instruction goes.

Not this:
- Picking a workflow or multi-agent pattern (Domain 1).
- Secrets storage and key rotation (<ObjLink id="identity-secrets-and-key-management" />, Domain 7).
- Hook event names and exit codes in detail (<ObjLink id="claude-hooks" />, Domain 3).
- Building an MCP server (<ObjLink id="mcp-server-development" />).

<Callout type="key" title="The idea that wins the most points">

Match the instruction to a surface by **authority, durability and enforcement**. Authority: who wrote it (operator, user, third party) decides the channel. Durability: how many sessions, for how long, decides the file or parameter. Enforcement: if the stem says *must* or *always*, the answer is code (hook, permission rule, schema), because every text surface, from the system prompt to CLAUDE.md, is a request the model usually follows, not a guarantee.

</Callout>

## Mechanism

### Instruction interpretation across Claude Code, Desktop, claude.ai, API and SDKs

<SubskillAnchor id="cad.interfaces" />

For every surface, ask three questions. **What is authoritative** (who wrote it, how much weight it carries)? **What persists** (one request, conversation, repo, account or organization)? **What does the model actually see** (system prompt, a user-turn message, a tool definition, or nothing because the harness enforces it)? Candidates skip the third question, and most distractors live there.

**The Claude API.** The Messages API is stateless: the model sees exactly the `system`, `messages` and `tools` you send, and nothing persists unless your application resends it. `system` carries operator instructions; user turns carry the request and attached content. Tool definitions are prompts too: when you pass `tools`, the API constructs a special system prompt from the tool definitions, tool configuration and your system prompt, and the docs call detailed descriptions "by far the most important factor in tool performance" [Certain]. Structured outputs likewise add a system prompt explaining the expected format [Certain]. There is no hidden Anthropic prompt on the API: the claude.ai and mobile apps use one (it supplies things like the current date), and the release notes state those prompts do not apply to the Claude API [Certain]. If your API app needs today's date, you send it.

<PostGuide>

The API now accepts `role: "system"` entries inside `messages` on several current models. Later system messages take precedence over earlier ones and over the top-level `system` field for the turns that follow, and appending one leaves the cached prefix intact, so policy can change mid-session without a cache miss. `tool_addition` and `tool_removal` blocks use the same mechanism behind a beta header; the text form needs none [Certain on the cited page]. For exam purposes, "system prompt" means the top-level `system` parameter.

</PostGuide>

**The client SDKs** wrap the same REST surface. They add transport (typed requests, retries on connection errors, 408, 409, 429 and 5xx, timeouts, streaming helpers) but no instruction surface and no memory. Conversation state, per-user isolation and instruction versioning are your application's job.

**The Claude Agent SDK** runs the Claude Code harness as a library, so its defaults are a design decision. With no system prompt option set, it uses a **minimal** prompt that covers tool calling but omits the Claude Code preset's security and safety instructions, unlike `claude -p`, which uses the full prompt [Certain]. The choices are the minimal default, the `claude_code` preset (optionally with `append`, which adds text and removes nothing), or a custom string that replaces everything and makes you responsible for the safety rules you still need. CLAUDE.md takes a separate path: the SDK injects it into the conversation as project context when the matching setting source is enabled, leaving the system prompt untouched [Certain]. Omitting `settingSources` loads the user, project and local sources; an empty list isolates the session, though managed policy still loads [Certain: claude-code-features page, 2026-10-07]. This default was briefly changed in v0.1.0 and then reverted, so set `settingSources` or `setting_sources` explicitly.

<PostGuide>

The Agent SDK now records the system prompt on a session's first request and reuses it on `resume` or `continue`, so a different `append` is not seen until compaction or a new session. To change instructions mid-session, send them in the next user message or as hook `additionalContext`.

</PostGuide>

**Claude Code** layers several instruction surfaces, and the exam expects you to know which is which.

- **System prompt.** Claude Code's own prompt for software engineering work. You can add to it at launch with `--append-system-prompt`, which the memory page recommends for instructions you want at system-prompt level, mainly in scripts and automation [Certain].
- **CLAUDE.md files.** Managed policy (for example `/etc/claude-code/CLAUDE.md` on Linux), user (`~/.claude/CLAUDE.md`), project (`./CLAUDE.md` or `./.claude/CLAUDE.md`, committed) and local (`./CLAUDE.local.md`, gitignored). Files in the working directory and above load at launch; subdirectory files load when Claude reads, writes or edits there. Discovered files are **concatenated, not overridden**, root first, so instructions nearest the launch directory are read last [Certain]. Contradictions are not resolved by precedence (Claude may pick one arbitrarily), so remove them. A managed policy CLAUDE.md cannot be excluded.
- **What the model sees from CLAUDE.md.** It is delivered as a user message after the system prompt, not as part of the system prompt, with no guarantee of strict compliance [Certain].
- **Rules.** `.claude/rules/*.md` load like project CLAUDE.md; a `paths` frontmatter list makes a rule load only when Claude touches a matching file.
- **Skills and slash commands.** Custom commands have been merged into skills: `.claude/commands/deploy.md` and `.claude/skills/deploy/SKILL.md` both create `/deploy` [Certain]. Only a skill's name and description sit in context until it is invoked; `disable-model-invocation: true` keeps a side-effecting skill out of Claude's hands.
- **Output styles.** Session-wide role, tone and format (built-ins include Concise, Explanatory, Learning). The docs say an output style "doesn't guarantee that something always happens or never happens". A custom style drops the built-in engineering instructions unless it sets `keep-coding-instructions: true` [Certain].
- **settings.json.** Configuration the harness enforces, not text the model reads: permissions, hooks, environment, enabled plugins. Precedence, highest first: managed, command line, `.claude/settings.local.json`, `.claude/settings.json`, `~/.claude/settings.json` [Certain]. In the memory page's words: "Settings rules are enforced by the client regardless of what Claude decides to do."

**Claude Desktop** has two faces. The chat side shares your claude.ai account surfaces. The local side adds MCP servers packaged as desktop extensions (`.mcpb` files installed from Settings, Extensions, with sensitive values kept in the OS secure store and admin allowlists for organizations) [Certain]. The instruction surface Desktop adds is mostly the tool surface: extension tool descriptions are prompts. The Code tab's local sessions read the same settings files as the terminal and VS Code [Certain].

**claude.ai** is configured in the UI. Anthropic supplies a system prompt you do not control. The current support article lists account-wide **instructions for Claude**, **project instructions** that apply only inside one Project, and **Skills** [Certain]. Chats in a Project share its knowledge base and instructions, with a retrieval mode on paid plans when knowledge nears the context limit [Certain]. Team and Enterprise can share a Project with view or edit rights, making project instructions the closest analogue of a committed project CLAUDE.md. Guide-era material also describes per-chat **Styles**, which the current article no longer lists [Likely renamed or folded in; check the live UI]. None of these surfaces enforces anything.

**Exam angle:** cue words are an audience and a lifetime ("everyone on this repo", "only me, every project", "this run", "the whole organization") or a surface name plus "where should". The usual distractor is a surface that works but has the wrong durability, or a text surface offered where the stem says "must".

### Content boundaries

<SubskillAnchor id="cad.content-boundaries" />

Every request mixes text from up to three authors, and the design job is to keep them structurally distinct so the model can weigh them correctly.

1. **Operator text** (you, the developer): the system prompt, tool definitions, CLAUDE.md you committed. This carries the most authority.
2. **User text**: what the person using your application typed or uploaded. It is trusted to express that user's intent, but not to rewrite your policy.
3. **Third-party content**: web pages, inbound email, OCR of an uploaded scan, rows from a database another team writes, the result of an MCP tool. This is data. It carries no authority at all, even when it is phrased as an instruction.

The structural rules follow directly.

- **Never interpolate user or third-party text into the system prompt.** Two independent reasons. It promotes untrusted text to operator authority, which is what an injected instruction wants. And the system prompt sits in the cached prefix (tools, then system, then messages), so a per-request value changes the prefix every call and caching stops hitting. Keep the system prompt constant and versioned in code.
- **Delimit and label content.** XML tags help Claude parse prompts that mix instructions, context and inputs. For documents, wrap each in `<document>` with `<source>` and `<document_content>` subtags, long material at the top and the question at the end; the docs report up to 30 percent better quality on complex multi-document inputs [Certain].
- **Say what the content is and state the policy.** Label provenance (for example, the body of an inbound email from an unknown sender) in the tool description or result, and say once in the system prompt that tool, file and search content is data to report on, never commands [Certain].
- **Prefer the tool-result channel for third-party content.** Current guidance is to deliver third-party content inside `tool_result` blocks, never in system prompts or plain user text, because Claude treats instructions there with appropriate skepticism, and to JSON-encode untrusted strings so an attacker cannot "break out" of a quote or tag [Certain on the cited page]. Older material says "a clearly delimited user turn". Both keep content out of the system prompt and labelled as data; if both appear, prefer the tool result for third-party content and the user turn for what the user wrote [Likely].
- **Do not put your own instructions in tool results.** Claude treats that text skeptically, so they may be ignored or flagged. Send them in the following user turn.

Boundaries reduce injection risk; they do not eliminate it. The same page pairs structure with least privilege, cheap screening of untrusted input and tool output, monitoring and red-teaming. A delimiter is a hint the model usually honours; a permission rule denying a dangerous tool is a guarantee. Put the boundary in the prompt *and* the consequence in code. The layered controls are taught in <ObjLink id="ai-application-security" /> and <ObjLink id="guardrails-and-safe-deployment" />.

Boundaries apply inside Claude Code too: a CLAUDE.md import from outside the working directory triggers a one-time approval dialog to protect you from files other people commit to a shared project [Certain]. A cloned repository's CLAUDE.md, skills and hooks deserve the same review as a dependency.

**Exam angle:** cues are "uploaded", "retrieved", "fetched", "inbound email", "tool returned", or a design that builds the system prompt per request. The distractor is the system prompt itself ("so Claude treats it as authoritative") or a delimiter offered as a complete defence where the stem demands a guarantee.

### Schema design

<SubskillAnchor id="cad.schema" />

Claude applications use schemas in two places, and the exam treats them as one skill.

- **Tool input schemas** (`input_schema` on a tool): the shape Claude must produce to call *your* code.
- **Output schemas** (`output_config.format` with `type: "json_schema"`): the shape of Claude's final answer.

Both are read by the model as prompt text, and both can be enforced. Structured outputs are generally available: JSON outputs constrain the response, and `strict: true` on a tool guarantees schema-valid tool names and inputs through constrained decoding [Certain]. `output_config` replaces the deprecated `output_format` and its beta header [Certain].

**A schema decides which answers are possible.** If a field is `required` and typed `string`, every legal output contains a string there. When the source has no such value, the model's only legal move is to produce one, and a plausible invented value is the worst error: it passes validation and corrupts everything downstream. "Do not guess" in the prompt asks for something the schema forbids. Make absence representable.

- **Nullable, required fields.** `"type": ["string", "null"]`, still listed in `required` [Certain that type arrays are supported]. The model must address the field and may answer `null`. An omitted optional key is ambiguous (forgot, or absent?); an explicit `null` is a decision.
- **Closed enums with an escape member.** Add `"unknown"` or `"other"` so the model is not forced into the nearest wrong category. Claude may return an enum value differing only in capitalization, so compare case-insensitively [Certain].
- **Descriptions on fields.** An instruction placed exactly where it is needed: units, format, what counts as present, what to do when absent.
- **Evidence fields.** A nullable `source_quote` beside an extracted value makes fabrication visible downstream.

**Strict-mode limits shape the design.** Objects must set `additionalProperties: false`. Supported: basic types, `enum`, `const`, `anyOf`, local `$ref`, common string formats, nullable type arrays. Not supported: recursive schemas, numeric and string-length bounds, `minItems` beyond 0 or 1. Documented ceilings are 20 strict tools, 24 optional parameters and 16 union-typed parameters per request [Certain on the cited page; numbers drift]. The SDK helpers (Pydantic, Zod) move unsupported constraints into descriptions and validate locally against your original schema. Copy that pattern: **the schema guarantees shape, your code checks meaning.**

**Schema-valid is not correct.** A `refusal` stop reason takes precedence over the schema (HTTP 200, billed); a `max_tokens` stop leaves output incomplete; a valid object can still be wrong. Check `stop_reason`, then parse, then validate business rules (<ObjLink id="output-handling" />).

**Version schemas like an API contract.**
- Keep a version constant next to the schema and store it with every persisted record.
- Prefer additive changes: a new nullable field is backward compatible; renaming or retyping is not.
- Expect a cost on change: a new schema pays grammar compilation (grammars are cached 24 hours from last use), and changing `output_config.format` invalidates the prompt cache for that thread [Certain].
- Gate schema changes on the eval set and promote them like code (<ObjLink id="configuration-management" />).

<PostGuide>

On Claude Opus 5.5, Sonnet 5.5 and Fable 5.1, forced `tool_choice` (`any` or a named tool) returns a 400. The documented replacement is `tool_choice: auto` with strict tools, or structured outputs when you need a fixed JSON shape [Certain on the define-tools page]. Older material that says "force the tool to guarantee structure" describes a pattern that no longer works on the newest models.

</PostGuide>

**Exam angle:** cues are "invents", "fabricates", "fills in a plausible value", "always returns a category even when none fits", or "downstream parser breaks". The distractors are a prompt instruction ("tell it not to guess"), marking the field required, or loosening the type to free text.

### Session hygiene

<SubskillAnchor id="cad.session-hygiene" />

A session is the unit of shared context. On the API it is whatever `messages` array your application keeps and resends. In Claude Code it is one conversation, with its own transcript, checkpoints and compaction history. On claude.ai it is a chat, optionally inside a Project whose knowledge and instructions are shared across chats. Session boundaries are a design decision, and three forces push on them.

**Quality: context rot.** Anthropic's context engineering article defines it: as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases [Certain]. The Claude Code best-practices page builds nearly all of its advice on the same constraint, noting that as the window fills Claude may start "forgetting" earlier instructions or making more mistakes [Certain]. A bigger window delays the problem; it does not remove it.

**Correctness: accumulated contradictions.** Every correction stays in context. The docs are specific: if you have corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches, so clear it and start again with a better prompt that incorporates what you learned. They name two failure patterns worth memorising: the **kitchen sink session** (unrelated tasks interleaved in one conversation) and **correcting over and over**. The fix for both is `/clear` [Certain].

**Security: isolation.** In a multi-user or multi-tenant application, a session that has seen one customer's data must never serve another customer. This is not a quality heuristic but an access-control boundary. A compaction summary is still a carrier: it exists precisely to preserve important details, so a summarised session can still leak [Likely]. One session per user per task, keyed by identity in your store, is the structural answer.

**When to start fresh:**
- The task changes (migration finished, now frontend work).
- Two corrections on the same issue have failed.
- A plan or spec is written and implementation is about to begin. The best-practices page recommends exactly this after an interview-style spec session: start a fresh session to execute it, with clean context focused on implementation.
- The user, tenant, customer or case changes.
- You want an unbiased review: a fresh context reviews code better than the session that wrote it.

**Claude Code controls.** `/clear` resets the context window entirely. `/compact` (optionally with focus instructions such as "Focus on the API changes") replaces the conversation with a structured summary; auto-compaction triggers near the limit. `/rewind` restores conversation, code or both to a checkpoint, or summarises from a chosen message. `/btw` asks a side question whose answer never enters history. `claude --continue` and `claude --resume` pick a session back up, and `/rename` lets you treat sessions like branches [Certain]. Know what survives compaction: the project-root CLAUDE.md is re-read from disk and re-injected, invoked skills are restored (capped per skill), but instructions given only in conversation can be lost [Certain]. That gives a clean rule: **anything that must outlive the conversation belongs in a file.**

**Carry state through files, not long sessions.** The context engineering article describes structured note-taking: agents write notes outside the context window (a `NOTES.md`, a to-do list) and read them back later [Certain]. In practice:
- Durable rules go in CLAUDE.md or rules, so they reload every session and after compaction.
- Task state goes in a plan, spec or progress file that a fresh session reads first.
- Exploratory reading goes to a subagent, which explores in its own context window and returns a summary, keeping the main session small.
- On the API, the same idea is your own store of per-user notes, or the memory tool (`memory_20250818` in `facts.json`), loaded deliberately into a new conversation rather than by never ending the old one.

**Exam angle:** cues are "drifted", "quality declined over a long session", "keeps repeating an earlier mistake", "another customer's", "shared conversation". Distractors are a larger context window, raising effort, a "forget that" message, or compaction offered as an isolation control.

### Plugin management

<SubskillAnchor id="cad.plugins" />

A Claude Code plugin is a directory of components installed and loaded as one unit, usually with a manifest at `.claude-plugin/plugin.json` giving a name and optionally a version [Certain]. It can bundle **skills** (run as `/plugin-name:skill-name`, so they never collide with local names), **agents**, **hooks**, **MCP servers**, plus LSP servers, output styles and a `bin/` directory added to the Bash tool's PATH [Certain]. All of these work without a plugin; use one to package several, share them, or publish versioned releases.

**Marketplaces.** A marketplace is a catalog (`.claude-plugin/marketplace.json`), not a hosted store. Claude Code adds Anthropic's `claude-plugins-official` on first interactive start unless policy blocks it; you add others with `/plugin marketplace add owner/repo`, optionally pinned with `#ref`. Official and community names are accepted only from `github.com/anthropics/` sources, so a third party cannot impersonate them [Certain].

**Install scopes.** The scope decides which settings file records the plugin under `enabledPlugins`:
- **User**: `~/.claude/settings.json`, you in every project on this machine.
- **Project**: `.claude/settings.json`, committed, enabled for everyone in the repo. Committing the entry does not download the plugin; each collaborator installs it once.
- **Local**: `.claude/settings.local.json`, you in this repo only.
- **Managed**: pushed by the organization; users cannot disable or uninstall it.

When a plugin is set at several scopes, local overrides project and project overrides user [Certain]. Manage it in the `/plugin` panel or with `claude plugin install`, `enable`, `disable` and `uninstall`, each taking `--scope`; a running session picks up changes with `/reload-plugins`.

**Cost: every enabled plugin is in every session.** The name and description of each skill, agent and command Claude can invoke sit in context on every turn, even when nothing from the plugin runs; its MCP servers run and its hooks fire [Certain]. Overlapping plugins cost twice: more always-on tokens and more near-duplicate choices. `claude plugin details <name>` reports the always-on token count.

**Trust: a plugin runs as you.** A plugin can execute arbitrary code with your user privileges [Certain]. Permission rules and the sandbox cover the tool calls *Claude* makes, including a plugin's MCP tools, but hooks, MCP server processes and mods run outside the sandbox. Skills and agents enter context as instructions. Review the **Will install** list, `hooks/hooks.json`, `.mcp.json` and `bin/` before installing.

**Versioning and dependencies.** Declared plugin dependencies install at the same scope, disable refuses while another enabled plugin needs one, and auto-installed dependencies stay until `claude plugin prune` [Certain]. Auto-update is on by default for the official marketplace and off for community and third-party ones; with it on, the files you reviewed can change [Certain]. Pin a third-party marketplace with `#ref` and update deliberately, as with any package (<ObjLink id="configuration-management" />). Managed settings can allowlist or block marketplaces, force-enable plugins and restrict hooks. Packaging a team's setup in depth is <ObjLink id="agentic-customization" />.

**Exam angle:** cues are "share with the whole team", "many plugins", "overlapping", "context fills", "from an unknown marketplace", "auto-updated overnight". Distractors claim plugins deduplicate overlapping tools, that permission rules sandbox plugin hooks, or that committing `.claude/settings.json` installs the plugin on every machine.

|---|---|---|
| "every engineer working in this repository, without anyone retyping it" | Committed project `./CLAUDE.md` (or `.claude/rules/`) | `~/.claude/CLAUDE.md` reaches only its owner; managed policy reaches every repo on the machine, which is over-scoped |

| "the model invents a value when the source lacks one" | Nullable field kept in `required`, with a field description saying when to return null | "Do not guess" in the prompt cannot override a schema that only allows a string; marking it required without null makes fabrication certain |
| "classification always lands in some category, even for out-of-scope inputs" | Add an explicit `"other"` or `"unknown"` enum member and compare case-insensitively | Free text loses the closed set downstream code depends on |
| "a long session that changed tasks twice is now repeating an earlier mistake" | `/clear` and start fresh with a sharper prompt; keep durable rules in CLAUDE.md | `/compact` keeps a summary of the polluted history; a larger window only delays context rot |
| "a draft for one customer referenced another customer's data" | One session per customer (and per task), keyed in the session store | Compaction, reminders and "forget" instructions leave the data in context or in the summary |
| "the team wants the same skills, agents and hooks in every repo, with versioned updates" | A plugin from a team marketplace, enabled at project scope, marketplace pinned to a tag | Copying `.claude/` folders between repos drifts and has no version or dependency handling |
| "after installing many plugins, context fills quickly and Claude picks the wrong tool" | Audit with plugin details, disable overlapping or unused plugins | Plugins do not deduplicate; each enabled one adds descriptions to every turn |

## Worked walkthrough

<Walkthrough title="Scenario: a naming convention that only works for one engineer">

<Step title="Read the scenario">

A data platform team keeps its Lakeflow pipeline code in one repository. Their lead put "Unity Catalog tables use the pattern domain_layer_entity" in a CLAUDE.md file, and the lead's Claude Code sessions follow it. A new hire's sessions in the same repository ignore it. The team wants the convention applied for everyone who works in the repository; it is guidance for writing code, not a control that must block anything. Where should it live?

</Step>

<Step title="Find the constraint">

Two phrases decide it. "Everyone who works in the repository" sets the audience and lifetime: all collaborators, every session, scoped to this repo. "Guidance, not a control that must block anything" removes the enforced layer from consideration. The symptom (works for the lead, not the new hire) tells you the file is at the wrong scope: almost certainly `~/.claude/CLAUDE.md`, which only its owner loads.

</Step>

<Step title="Eliminate the over-scoped option">

A managed policy CLAUDE.md would reach the new hire, but it reaches every session on every managed machine, in every repository, and needs IT to deploy it. The memory docs say managed CLAUDE.md is for organization-wide standards and tell you to commit a project CLAUDE.md for repository-specific guidance. Right audience plus far too much reach is a wrong answer.

</Step>

<Step title="Eliminate the per-launch and the enforced options">

Asking each engineer to launch with `--append-system-prompt` puts the rule at system-prompt level, but it lives in personal shell aliases, is not versioned with the repository, and silently disappears for anyone who forgets the flag. A PreToolUse hook that rejects writes with non-conforming table names would be deterministic, but the stem explicitly frames this as guidance; a blocking hook is heavier machinery than the requirement and turns every exploratory query into a failure. If the stem had said "must never create a table outside the pattern", the hook would win.

</Step>

<Step title="Choose">

Move the convention into the committed project `./CLAUDE.md` (or a `.claude/rules/` file scoped with `paths` to the pipeline directories). It loads for every collaborator at launch, survives compaction because the project-root file is re-read from disk, and changes through code review like any other team standard. The lead's personal preference for terse answers stays in their own user scope, for example an output style set in `~/.claude/settings.json`.

</Step>

<Step title="The deciding cue">

"For everyone who works in the repository" plus "guidance" selects the committed project CLAUDE.md. Swap "guidance" for "must never" and the answer moves to a permission rule or hook; swap the audience to "only me" and it moves to user scope.

</Step>

</Walkthrough>

<Walkthrough title="Scenario: an account copilot that remembers too much">

<Step title="Read the scenario">

A SaaS vendor builds an internal copilot on the Messages API for its account managers. Each account manager has one long-running conversation; they paste customer emails into it and ask for reply drafts across all their accounts. Last week a draft to one customer quoted another customer's renewal discount. The team must ensure this cannot recur. What change addresses the root cause?

</Step>

<Step title="Find the constraint">

"Another customer's renewal discount" converts a quality symptom into an isolation failure. "Must ensure this cannot recur" asks for a structural fix, not a better-behaved model. The design flaw is the session boundary: one conversation spans many customers, so every customer's data is in context for every draft.

</Step>

<Step title="Eliminate the prompt fix">

Adding "never mention details from other customers" to the system prompt is a request. The other customer's discount is still in the context window, and the model still sees it on every turn. A stem that says "cannot recur" rules out a control that works most of the time.

</Step>

<Step title="Eliminate the context-management fixes">

Server-side or client-side compaction shrinks the conversation, but its job is to preserve important details, and a renewal discount is exactly the kind of detail a summary keeps. A model with a larger context window makes the problem worse, because more customers fit in one conversation. Both treat the issue as context size; it is context scope.

</Step>

<Step title="Choose">

Key sessions by account manager and customer (and by task), start a fresh conversation for each, and carry durable per-customer facts in that customer's own notes record, loaded deliberately at the start of that customer's session. Keep the system prompt constant and pass each pasted email as labelled content in the message channel, never in `system`.

</Step>

<Step title="The deciding cue">

"Another customer's" data appearing in output means the session boundary is wrong. The answer is a separate session per customer, not an instruction, a summary or a bigger window.

</Step>

</Walkthrough>

**Schema design: nullable, enum with an escape member, field descriptions, a version you store.** The schema guarantees shape; the handler still checks `stop_reason` and meaning.

```python
import json
import anthropic

client = anthropic.Anthropic()

SCHEMA_VERSION = "invoice-v3"  # stored with every record; bump on breaking change

INVOICE_SCHEMA = {
    "type": "object",
    "properties": {
        "supplier_name": {"type": "string", "description": "Legal name as printed."},
        "purchase_order": {
            "type": ["string", "null"],
            "description": "PO number exactly as printed. null if the invoice shows none. Never infer one.",
        },
        "po_evidence": {
            "type": ["string", "null"],
            "description": "Verbatim text the PO number was read from, or null.",
        },
        "currency": {
            "type": "string",
            "enum": ["EUR", "GBP", "USD", "unknown"],
            "description": "ISO code printed on the invoice; unknown if not printed.",
        },
    },
    "required": ["supplier_name", "purchase_order", "po_evidence", "currency"],
    "additionalProperties": False,
}


def extract(invoice_text: str) -> dict:
    resp = client.messages.create(
        model="claude-haiku-4-5",
        max_tokens=1024,
        messages=[{"role": "user", "content": f"<document>\n{invoice_text}\n</document>\n\nExtract the fields."}],
        output_config={"format": {"type": "json_schema", "schema": INVOICE_SCHEMA}},
    )
    if resp.stop_reason in ("max_tokens", "refusal"):
        raise RuntimeError(f"no schema guarantee: stop_reason={resp.stop_reason}")
    data = json.loads("".join(b.text for b in resp.content if b.type == "text"))
    data["currency"] = data["currency"].upper() if data["currency"].lower() != "unknown" else "unknown"
    if data["purchase_order"] and data["po_evidence"] is None:
        raise ValueError("PO without evidence: treat as unverified")
    return {"schema_version": SCHEMA_VERSION, **data}
```

**Session hygiene on the API: one session per user, customer and task, with state carried in notes.** The store key is the isolation boundary; notes are the only thing that crosses into a new session.

```python
import anthropic

client = anthropic.Anthropic()

SYSTEM = "You help account managers draft customer replies. Use only the notes and messages in this conversation."
sessions: dict[tuple[str, str, str], list[dict]] = {}
notes: dict[str, str] = {}  # per-customer durable facts, written deliberately


def turn(manager_id: str, customer_id: str, task_id: str, user_text: str) -> str:
    key = (manager_id, customer_id, task_id)
    if key not in sessions:  # fresh session: seed it with this customer's notes only
        brief = notes.get(customer_id, "No notes yet.")
        sessions[key] = [{"role": "user", "content": f"<customer_notes>\n{brief}\n</customer_notes>"},
                         {"role": "assistant", "content": "Noted."}]
    history = sessions[key]
    history.append({"role": "user", "content": user_text})
    resp = client.messages.create(model="claude-sonnet-5-5", max_tokens=2048, system=SYSTEM, messages=history)
    history.append({"role": "assistant", "content": resp.content})
    return "".join(b.text for b in resp.content if b.type == "text")


def close_task(manager_id: str, customer_id: str, task_id: str, durable_fact: str) -> None:
    notes[customer_id] = (notes.get(customer_id, "") + "\n" + durable_fact).strip()
    sessions.pop((manager_id, customer_id, task_id), None)  # never reused for another task
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const SYSTEM = "You help account managers draft customer replies. Use only the notes and messages in this conversation.";
const sessions = new Map<string, Anthropic.MessageParam[]>();
const notes = new Map<string, string>();

export async function turn(managerId: string, customerId: string, taskId: string, userText: string) {
  const key = `${managerId}|${customerId}|${taskId}`;
  if (!sessions.has(key)) {
    const brief = notes.get(customerId) ?? "No notes yet.";
    sessions.set(key, [
      { role: "user", content: `<customer_notes>\n${brief}\n</customer_notes>` },
      { role: "assistant", content: "Noted." },
    ]);
  }
  const history = sessions.get(key)!;
  history.push({ role: "user", content: userText });
  const resp = await client.messages.create({ model: "claude-sonnet-5-5", max_tokens: 2048, system: SYSTEM, messages: history });
  history.push({ role: "assistant", content: resp.content });
  return resp.content.filter((b) => b.type === "text").map((b) => (b as Anthropic.TextBlock).text).join("");
}

export function closeTask(managerId: string, customerId: string, taskId: string, durableFact: string) {
  notes.set(customerId, `${notes.get(customerId) ?? ""}\n${durableFact}`.trim());
  sessions.delete(`${managerId}|${customerId}|${taskId}`);
}
```
