## Concept

This objective tests one judgment: given a scenario, what is the **cheapest shape of system that meets the requirement**. The options run from a single well-prompted call, through fixed workflows, to an autonomous agent, to a supervisor with subagents. Anthropic's own guidance is to find the simplest solution possible and add complexity only when it demonstrably improves outcomes, and the guide's traps are written around that rule: distractors offer an elegant multi-agent design where a prompt chain is correct.

Anthropic draws the line precisely. **Workflows** are "systems where LLMs and tools are orchestrated through predefined code paths": you wrote the control flow. **Agents** are "systems where LLMs dynamically direct their own processes and tool usage": the model decides the next step from what it observes. Both are "agentic systems", and the decision between them is about predictability of the steps, not about how impressive the task sounds.

The other half is **subagents**. A subagent is a separate agent instance with its own context window that receives a brief and returns a summary. The exam angle is why you would use one: mainly to keep a subtask's exploration out of the parent's context, secondarily for parallelism, tool restriction and cheaper models.

**Scope boundary.** This page owns the *decision*. The building blocks you assemble once the decision is made live next door.

<Callout type="key" title="The point-winning idea">
Pick the least autonomous architecture that satisfies the stem. Fixed steps mean a workflow; unpredictable steps mean an agent; a supervisor or subagents are justified only by a concrete need (context overflow, independent breadth, tool isolation) that the stem actually states.
</Callout>

## Mechanism

### Architecture principles, patterns and tradeoffs

<SubskillAnchor id="aa.principles" />

Anthropic's "Building effective agents" post gives three core principles: keep the design **simple**, make the agent's planning **transparent**, and invest in the **agent-computer interface** (tool documentation and testing) as much as you would in a human interface. Everything else on this page is a consequence of the first one.

The basic building block is the **augmented LLM**: a model with retrieval, tools and memory. For many applications, Anthropic notes that optimizing a single call with retrieval and in-context examples is enough. Only when that fails do you compose calls into workflows, and only when workflows fail do you hand control to an agent.

Autonomy has four costs, and stems are written so that one of them is the constraint:

| Cost | Mechanism | Stem signal |
|---|---|---|
| Tokens and money | Agents "trade latency and cost for better task performance". Anthropic measured agents at about 4x the tokens of chat and multi-agent systems at about 15x **[Certain]** | "Cost-sensitive", "high volume", "tight budget" |
| Latency | Every extra model call or handoff is a sequential round trip unless it can run in parallel | "Interactive", "user is waiting", "under two seconds" |
| Compounding errors | Each autonomous step can go wrong, and later steps build on earlier ones, so error rates multiply across a trajectory | "Long chains of steps", "occasional wrong actions", "must be reliable" |
| Observability | A workflow has a fixed path you can test step by step; an agent's path differs per run and needs tracing to debug | "Must be auditable", "hard to reproduce", "explain why it did X" |

The same post separates the **five workflow patterns** from agents. Learn each by its "use when" condition, because that condition is what a stem encodes.

| Pattern | Mechanism | Use when | Example |
|---|---|---|---|
| Prompt chaining | Fixed sequence of calls, each consuming the previous output, with optional programmatic **gates** between steps | Task decomposes cleanly into fixed subtasks; trading latency for accuracy per step | Draft, gate on a check, then translate |
| Routing | Classify the input, send it to a specialized prompt, tool set or model | Distinct categories are better handled separately | Simple questions to a cheap model, hard ones to a capable model |
| Parallelization: sectioning | Independent subtasks run at once, results aggregated in code | Subtasks are known and independent; speed or focus per aspect | One call answers, another screens for policy violations |
| Parallelization: voting | Same task run several times, outputs aggregated | Higher confidence needed from multiple attempts or perspectives | Several independent vulnerability reviews, flag on agreement |
| Orchestrator-workers | A central LLM decides subtasks **at runtime**, delegates, synthesizes | You cannot predict the subtasks; they depend on the input | A change touching an unknown set of files |
| Evaluator-optimizer | One call generates, another critiques against criteria, loop | Clear evaluation criteria exist and iteration measurably helps | Translation refined against explicit style rules |

Three tradeoffs recur inside the patterns themselves. Chaining buys accuracy per step by spending latency, because each call waits for the last. Routing buys specialization but adds a classification step that can misroute, so its categories must be genuinely distinct. Parallelization buys wall-clock time or confidence but multiplies tokens by the number of branches. None of these is free, which is why the pattern must be justified by the stem's stated need rather than by elegance.

**Observability is an architecture decision, not an afterthought.** A workflow can log each step's input and output against a fixed schema, so a regression shows up at a known step. An agent produces a different trajectory per run, so you need traces of every model decision and tool call to answer "why did it do that". Anthropic's research team describes adding production tracing to diagnose why agents failed, and building the ability to resume from where an agent was when an error occurred rather than restarting. If a stem stresses auditability or reproducibility, it is pushing you toward the more deterministic design, or toward a design where the autonomous part is small and well instrumented.

Two distinctions carry most of the points. **Sectioning versus orchestrator-workers**: if you could write the list of subtasks in code before seeing the input, it is sectioning. **Voting versus evaluator-optimizer**: independent attempts aggregated is voting; a critique fed back into a revision is evaluator-optimizer.

**Exam angle:** cue words are "fixed steps" (chaining), "distinct categories" (routing), "independent aspects" or "several attempts" (parallelization), "cannot predict which" (orchestrator-workers), "clear criteria, iterate" (evaluator-optimizer). The usual distractor is a more autonomous pattern than the stem needs.

### Workflow versus agent decision criteria

<SubskillAnchor id="aa.workflow-vs-agent" />

Use an **agent** for "open-ended problems where it's difficult or impossible to predict the required number of steps, and where you can't hardcode a fixed path". Use a **workflow** for well-defined tasks that need predictability and consistency. That single criterion decides most items. Supporting criteria:

| Question | Points to workflow | Points to agent |
|---|---|---|
| Can you list the steps before the run? | Yes, same steps every time | No, steps depend on what is discovered |
| Does the environment give feedback per step? | Not needed | Yes: tool results, test runs, query results provide "ground truth" to steer by |
| Is predictability required (audit, compliance, SLA)? | Yes | Tolerable variance |
| Cost of a wrong autonomous action? | High, irreversible | Low, or sandboxed and reversible |
| Volume and cost sensitivity | High volume, low margin | High-value tasks that justify the spend |

Anthropic adds the operating conditions for agents: they plan and act independently once the task is clear, can return to a human at **checkpoints** or when blocked, need **stopping conditions** such as a maximum number of iterations, and need "extensive testing in sandboxed environments, along with the appropriate guardrails". If a stem's scenario cannot provide those (no sandbox, no way to verify progress, irreversible actions), that is a reason to stay with a workflow or add a human approval step.

The criteria are about the *task*, not the *input*. Messy, free-form input is handled by an LLM step inside a workflow (extraction or routing). It does not by itself require an agent. Equally, "the steps might change next year" is not a reason for autonomy today; changing code is cheaper than paying for autonomy on every run.

Hybrid designs are normal and often correct: a workflow whose one open-ended step is an agent (for example, a fixed intake and approval process with a bounded investigation agent in the middle), or an agent whose tools are themselves deterministic workflows.

**Exam angle:** "same steps", "always", "fixed order", "predictable" point to a workflow. "Unknown number of steps", "depends on what it finds", "open-ended" point to an agent. Distractor: an agent proposed because the input is unstructured.

### Manager/supervisor hierarchies

<SubskillAnchor id="aa.hierarchies" />

A supervisor (manager, lead agent, orchestrator) holds the goal, decomposes it, delegates to workers, and synthesizes their results. It is the orchestrator-workers pattern run with agents rather than single calls. Anthropic's research system is the canonical example: a lead agent plans, spawns subagents that search in parallel, and synthesizes. With an Opus 4 lead and Sonnet 4 subagents it outperformed single-agent Opus 4 by 90.2% on Anthropic's internal research evaluation **[Certain]**, and token usage alone explained about 80% of the performance variance on the browsing evaluation they studied.

When a supervisor helps:

- **Breadth-first work** with many independent directions (research across many sources, auditing many services).
- **Context overflow**: the total material exceeds what one context can hold well, so splitting it across worker contexts is the only way to read it all.
- **Heterogeneous tools or permissions**: workers need different tool sets that should not be mixed.
- **High enough value**: Anthropic states multi-agent systems "require tasks where the value of the task is high enough to pay for the increased performance".

When it hurts: tasks where agents must "share the same context or involve many dependencies between agents". Anthropic names most coding tasks as a poor fit because there is less truly parallel work.

Failure modes to recognize in a stem:

| Failure | Cause | Fix |
|---|---|---|
| Over-spawning | No effort scaling; Anthropic saw early versions spawn 50 subagents for simple queries | Put scaling rules in the lead's prompt (simple: one agent, few calls; complex: more workers) and cap counts in code |
| Duplicated or gapped work | Vague delegation briefs | Each brief states objective, output format, tools or sources to use, and task boundaries |
| Game of telephone | Each layer summarizes the layer below, losing detail | Keep the tree shallow; let workers write full outputs to storage and pass references |
| Compounding errors | Minor failures cascade through long trajectories | Checkpoints, resume from the failure point, verification steps, human approval for risky actions |
| Synchronous bottleneck | Lead waits for the slowest worker | Accept it, or move to asynchronous execution at the cost of coordination complexity |
| Opaque failures | Non-deterministic paths | Production tracing of decisions and tool calls |

**Depth.** Every layer is another lossy summary, another round of tokens, and another place for errors to compound. Prefer one supervisor and one layer of workers; add depth only when a worker itself faces a breadth problem. Harnesses enforce this as configuration rather than trust.

<PostGuide since="2026-08">
Current Claude Code and Agent SDK documentation (verified 2026-10-06) lets a subagent spawn its own subagents, by default up to three layers below the main conversation, with `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` to change it (1 stops nesting), a default concurrency cap of 20 running subagents, and `max_budget_usd` covering subagent spend. Earlier documentation did not allow nesting **[Likely]**. Treat the specific numbers as engineering knowledge; the stable exam point is that depth, breadth and spend are bounded in the harness, not by asking the model to be restrained.
</PostGuide>

**Exam angle:** "breadth", "many independent sources", "too much for one context" justify a supervisor. "Tightly coupled", "shared state", "every step depends on the previous" argue against it. Distractor: adding another management layer to fix quality.

### Role of subagents in task execution

<SubskillAnchor id="aa.subagents" />

The primary role of a subagent is **context isolation**. It starts with a fresh window (its own system prompt plus the brief), does the noisy work there (dozens of file reads, searches, log dumps), and returns only its final message. Anthropic's context engineering post describes subagents returning condensed summaries of roughly 1,000 to 2,000 tokens so that "the detailed search context remains isolated within sub-agents" **[Certain]**. The parent's context grows by the summary, not the transcript, which keeps its later reasoning sharp.

Claude Code's documentation lists the benefits in this order **[Certain]**:

1. **Preserve context** by keeping exploration and implementation out of the main conversation.
2. **Enforce constraints** by limiting which tools a subagent can use (a reviewer with only read and search tools cannot edit).
3. **Reuse configurations** across projects.
4. **Specialize behavior** with a focused system prompt.
5. **Control costs** by routing tasks to faster, cheaper models such as Haiku.

The Agent SDK page adds **parallelization**: independent subtasks finish in the time of the slowest rather than the sum. That benefit is real but conditional. It exists only when subtasks are independent, and many subagent calls are effectively sequential because the parent needs each result before deciding the next step.

Costs to weigh against the benefit:

- **Briefing overhead and lost context.** The subagent does not see the parent's conversation. The only thing passed in is the delegation prompt, so file paths, error messages and decisions must be written into the brief. A non-fork subagent "starts fresh and may need time to gather context", so the Claude Code docs recommend the main conversation when latency matters **[Certain]**.
- **Lossy return.** The parent sees only the summary. If the parent needs the raw evidence, a subagent is the wrong tool, or the subagent must write it to storage and return a pointer.
- **Tokens.** Each subagent pays its own system prompt, tools and exploration.

When **not** to delegate: the task is small (a single read or lookup), the parent needs the full raw output verbatim, the work depends tightly on the parent's evolving reasoning, or latency matters more than context hygiene. In each case the brief, the fresh start and the lossy summary cost more than the context they save. A useful test is to ask what would land in the parent's context without the subagent: if it is a few hundred tokens, keep the work in the parent.

**Exam angle:** "main context fills up", "later answers degrade", "keep exploration out of the conversation" point to subagents for isolation. "Restrict a reviewer to read-only" points to subagent tool restriction. Distractor: subagents justified by speed alone, or a subagent for a small task whose result the parent needs verbatim.

## Decision table

| If the stem says... | Choose | Why the runner-up loses |
|---|---|---|
| Every request goes through the same steps in the same order | Prompt chain, with code gates between steps | A supervisor with specialist agents adds tokens, latency and nondeterminism for no gain |
| Requests fall into a few categories, each always handled the same way | Routing to fixed handlers | An autonomous agent is unjustified because the per-category path is known |
| Cheap model for easy requests, capable model for hard ones | Routing by difficulty | Always using the capable model wastes money; always using the cheap one fails hard cases |
| Which files, sources or services to examine depends on the request | Orchestrator-workers | Sectioning needs the subtask list fixed in advance |
| The same three aspects are checked on every document, independently | Parallelization: sectioning | Orchestrator-workers pays for an LLM to rediscover a list you already know |
| Flag only when several independent reviews agree | Parallelization: voting | Evaluator-optimizer revises one output; it does not give independent agreement |
| Explicit quality criteria, and revision measurably improves the output | Evaluator-optimizer | Voting picks among attempts but never feeds the critique back |
| Number of steps cannot be known; progress is verified by tool results | Agent with stopping conditions | A fixed workflow cannot adapt to what it finds |
| Main agent's context fills with search output and quality drops | Delegate the searching to subagents that return summaries | A larger context window still fills and still dilutes attention |
| Tightly coupled task where each step needs the full shared context | Single agent | Multi-agent splits context that every step needs |
| Quality fell as more management layers were added | Flatten the hierarchy; workers write outputs to storage | Another supervisor adds one more lossy handoff |

## Worked walkthrough

<Walkthrough title="Scenario: supplier invoice reconciliation">

<Step title="Read the scenario">
A finance team wants Claude to process supplier invoices. Every invoice goes through the same four steps: extract header and line items, match them against the purchase order from an internal lookup, draft an exception note when amounts differ, and check the note against a short list of wording rules. Auditors require that each step's output be reviewable. An architect proposes a supervisor agent that delegates each step to its own autonomous specialist agent. What architecture should the team use?
</Step>

<Step title="Find the constraint">
"Every invoice goes through the same four steps" means the path is known before the run. "Auditors require that each step's output be reviewable" demands predictability and inspectable intermediate results. Both point away from autonomy.
</Step>

<Step title="Eliminate the supervisor design">
A supervisor with four autonomous specialists pays multi-agent token costs, adds handoffs where detail can be lost, and makes the path vary per run. It solves a problem (unpredictable decomposition) that this stem does not have.
</Step>

<Step title="Eliminate a single autonomous agent and orchestrator-workers">
A single agent with all four tools would usually work but gives up the fixed, auditable path and needs tracing to explain each run. Orchestrator-workers lets an LLM decide subtasks at runtime, but the subtasks are already known. Evaluator-optimizer alone does not cover extraction and matching.
</Step>

<Step title="Choose">
A prompt chain: extraction, then a deterministic gate (totals add up, required fields present), then purchase order matching as a tool call in code, then the exception note, then a final check against the wording rules. Each step's output is stored for audit. The wording check can be an evaluator step if rules are fuzzy, but the backbone is a fixed chain.
</Step>

<Step title="The deciding cue">
"Every invoice goes through the same four steps." Fixed, known steps mean a workflow, and the simplest workflow that fits is a prompt chain with gates.
</Step>

</Walkthrough>

## Code

**A prompt chain with a programmatic gate.** The control flow lives in code. The gate is a plain check: if the draft omits a ticket ID, the chain stops instead of handing a bad draft to step 2. This is the cheapest correct answer to most "fixed steps" stems.

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"


def text_of(resp) -> str:
    return "".join(b.text for b in resp.content if b.type == "text")


def call(system: str, user: str, max_tokens: int = 800) -> str:
    resp = client.messages.create(
        model=MODEL,
        max_tokens=max_tokens,
        system=system,
        messages=[{"role": "user", "content": user}],
    )
    return text_of(resp)


changes = [
    ("DATA-412", "Add retry with backoff to the orders ingestion job"),
    ("DATA-419", "Rename column cust_id to customer_id in silver.customers"),
]
change_list = "\n".join(f"{tid}: {desc}" for tid, desc in changes)

# Step 1: draft internal release notes.
draft = call("Write terse internal release notes. Keep every ticket ID.", change_list)

# Gate: deterministic check in code, not a model judgment.
missing = [tid for tid, _ in changes if tid not in draft]
if missing:
    raise SystemExit(f"Gate failed, draft dropped tickets: {missing}")

# Step 2: rewrite for downstream consumers of the tables.
notice = call(
    "Rewrite these release notes for analysts who query the tables. "
    "Lead with breaking changes. Keep ticket IDs.",
    draft,
)
print(notice)
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();
const MODEL = "claude-sonnet-5-5";

const textOf = (r: Anthropic.Message) =>
  r.content.map((b) => (b.type === "text" ? b.text : "")).join("");

async function call(system: string, user: string, maxTokens = 800): Promise<string> {
  const resp = await client.messages.create({
    model: MODEL,
    max_tokens: maxTokens,
    system,
    messages: [{ role: "user", content: user }],
  });
  return textOf(resp);
}

const changes: [string, string][] = [
  ["DATA-412", "Add retry with backoff to the orders ingestion job"],
  ["DATA-419", "Rename column cust_id to customer_id in silver.customers"],
];
const changeList = changes.map(([id, d]) => `${id}: ${d}`).join("\n");

// Step 1: draft internal release notes.
const draft = await call("Write terse internal release notes. Keep every ticket ID.", changeList);

// Gate: deterministic check in code, not a model judgment.
const missing = changes.map(([id]) => id).filter((id) => !draft.includes(id));
if (missing.length) throw new Error(`Gate failed, draft dropped tickets: ${missing.join(", ")}`);

// Step 2: rewrite for downstream consumers of the tables.
const notice = await call(
  "Rewrite these release notes for analysts who query the tables. Lead with breaking changes. Keep ticket IDs.",
  draft,
);
console.log(notice);
```

**Orchestrator-workers with isolated worker contexts.** The defining trait is that the orchestrator decides the subtasks at runtime from the input. Structured output makes the plan machine-readable, the harness caps how many workers may run, workers use a cheaper model and see only their own brief, and only their short answers reach the synthesis call.

```python
import json
from concurrent.futures import ThreadPoolExecutor

import anthropic

client = anthropic.Anthropic()
MAX_WORKERS = 4  # bound fan-out in code, not in the prompt

PLAN_SCHEMA = {
    "type": "object",
    "properties": {
        "subtasks": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "objective": {"type": "string"},
                    "deliverable": {"type": "string"},
                },
                "required": ["objective", "deliverable"],
                "additionalProperties": False,
            },
        }
    },
    "required": ["subtasks"],
    "additionalProperties": False,
}


def text_of(resp) -> str:
    return "".join(b.text for b in resp.content if b.type == "text")


def plan(request: str) -> list[dict]:
    resp = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=1024,
        system="Split the request into the smallest set of independent subtasks. Use one subtask if one is enough.",
        messages=[{"role": "user", "content": request}],
        output_config={"format": {"type": "json_schema", "schema": PLAN_SCHEMA}},
    )
    return json.loads(text_of(resp))["subtasks"][:MAX_WORKERS]


def worker(task: dict) -> str:
    # Fresh context: the worker sees only its brief, never the other workers.
    resp = client.messages.create(
        model="claude-haiku-4-5",
        max_tokens=400,
        system="Do only the objective. Answer in the requested format, under 120 words.",
        messages=[{"role": "user", "content": f"Objective: {task['objective']}\nDeliverable: {task['deliverable']}"}],
    )
    return text_of(resp)


request = "Compare Delta Lake liquid clustering with Z-ordering for a 2 TB events table queried by date and user_id."
subtasks = plan(request)
with ThreadPoolExecutor(max_workers=MAX_WORKERS) as pool:
    answers = list(pool.map(worker, subtasks))

findings = "\n\n".join(f"[{t['objective']}]\n{a}" for t, a in zip(subtasks, answers))
final = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=800,
    system="Synthesize the findings into one recommendation with the deciding reason.",
    messages=[{"role": "user", "content": f"Request: {request}\n\nFindings:\n{findings}"}],
)
print(f"{len(subtasks)} workers")
print(text_of(final))
```

import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();
const MAX_WORKERS = 4; // bound fan-out in code, not in the prompt

type Subtask = { objective: string; deliverable: string };

const PLAN_SCHEMA = {
  type: "object",
  properties: {
    subtasks: {
      type: "array",
      items: {
        type: "object",
        properties: { objective: { type: "string" }, deliverable: { type: "string" } },
        required: ["objective", "deliverable"],
        additionalProperties: false,
      },
    },
  },
  required: ["subtasks"],
  additionalProperties: false,
};

const textOf = (r: Anthropic.Message) =>
  r.content.map((b) => (b.type === "text" ? b.text : "")).join("");

async function plan(request: string): Promise<Subtask[]> {
  const resp = await client.messages.create({
    model: "claude-sonnet-5-5",
    max_tokens: 1024,
    system: "Split the request into the smallest set of independent subtasks. Use one subtask if one is enough.",
    messages: [{ role: "user", content: request }],
    output_config: { format: { type: "json_schema", schema: PLAN_SCHEMA } },
  });
  return (JSON.parse(textOf(resp)).subtasks as Subtask[]).slice(0, MAX_WORKERS);
}

async function worker(task: Subtask): Promise<string> {
  // Fresh context: the worker sees only its brief, never the other workers.
  const resp = await client.messages.create({
    model: "claude-haiku-4-5",
    max_tokens: 400,
    system: "Do only the objective. Answer in the requested format, under 120 words.",
    messages: [{ role: "user", content: `Objective: ${task.objective}\nDeliverable: ${task.deliverable}` }],
  });
  return textOf(resp);
}

const request =
  "Compare Delta Lake liquid clustering with Z-ordering for a 2 TB events table queried by date and user_id.";
const subtasks = await plan(request);
const answers = await Promise.all(subtasks.map(worker));

const findings = subtasks.map((t, i) => `[${t.objective}]\n${answers[i]}`).join("\n\n");
const final = await client.messages.create({
  model: "claude-sonnet-5-5",
  max_tokens: 800,
  system: "Synthesize the findings into one recommendation with the deciding reason.",
  messages: [{ role: "user", content: `Request: ${request}\n\nFindings:\n${findings}` }],
});
console.log(`${subtasks.length} workers`);
console.log(textOf(final));

## Recall checks

<Recall q="State Anthropic's distinction between a workflow and an agent, and the one criterion that decides between them.">
A workflow orchestrates LLMs and tools through predefined code paths; an agent lets the LLM direct its own process and tool use. Choose an agent only when the number and order of steps cannot be predicted or hardcoded; otherwise a workflow is cheaper, faster and more predictable.
</Recall>

<Recall q="What separates orchestrator-workers from parallelization (sectioning)?">
Who decides the subtasks and when. In sectioning the subtask list is fixed in code before the run; in orchestrator-workers an LLM decides the subtasks at runtime from the specific input. If you could write the list in advance, it is sectioning.
</Recall>

<Recall q="Name four costs of adding autonomy, and the stem words that signal each.">
Tokens (agents about 4x chat, multi-agent about 15x; signalled by cost or volume), latency (interactive, user waiting), compounding errors (long trajectories, must be reliable), and observability (auditable, hard to reproduce). Each is a reason to prefer the least autonomous design that works.
</Recall>

<Recall q="When does a supervisor hierarchy help, and when does it hurt?">
It helps for breadth-first, high-value work with independent directions or more material than one context can hold. It hurts when agents must share the same context or have many dependencies, such as most coding tasks, because each handoff loses detail and adds cost.
</Recall>

<Recall q="Why does adding another management layer rarely fix quality problems in a hierarchy?">
The manager sees only summaries, so it cannot see mistakes made inside a worker's context. Each layer is another lossy handoff and another place for errors to compound. Better briefs, verification steps and a flatter tree address the cause.
</Recall>

<Recall q="What is the primary reason to use a subagent, and what are the secondary ones?">
Context isolation: the subagent's exploration stays in its own window and only a condensed summary returns, so the parent's context stays focused. Secondary benefits are parallelism for independent subtasks, tool restriction, specialized prompts and cheaper models.
</Recall>

<Recall q="What must a delegation brief contain, and why?">
Objective, output format, which tools or sources to use, and task boundaries. The subagent sees nothing of the parent's conversation, so anything it needs must be in the brief; vague briefs caused duplicated and missed work in Anthropic's research system.
</Recall>
