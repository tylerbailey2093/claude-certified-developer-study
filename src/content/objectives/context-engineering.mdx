## Concept

The guide frames this objective as **context and memory management**: what Claude can see on this call, what it can get back later, and what you deliberately keep out. Anthropic's engineering team defines the goal as finding "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome". Every token spends a finite attention budget, and recall degrades as the window fills, a gradient the docs call context rot, not a cliff at the limit.

Items here are diagnostic. A stem describes a symptom (forgets a rule, re-does work, gets vaguer, hits a limit, loses state between sessions) and four plausible fixes. Each fix works only on its own failure mode: summarizing history does not repair a diluted instruction, restating a rule does not shrink a 50,000-token tool dump, and a bigger window makes both worse. Learn the symptom-to-lever map and the lightest lever that solves each one.

**Scope boundary.** How to word an instruction belongs to <ObjLink id="prompt-engineering" />. How Claude interprets instructions across surfaces and session hygiene as a design concern belong to <ObjLink id="claude-application-design" />. Which workflow pattern to choose (orchestrator-workers, chaining, routing) is <ObjLink id="agent-patterns-and-frameworks" />; here only their effect on context matters. Request shapes, beta headers and `stop_reason` handling are <ObjLink id="claude-api-mechanics" />. What tokens cost is <ObjLink id="cost-and-token-management" />.

Not this:
- Choosing an agent pattern for its control flow
- Prompt caching economics
- Writing clearer instructions in isolation

<Callout type="key" title="Match the lever to the failure">
**Drift** (a rule fades): re-anchor it in the system prompt or CLAUDE.md, restate it at decision points, enforce it with code if it must hold. **Bloat** (low-value tokens pile up): prune at the source first, clear old tool results second, compact third. **Volume** (exploration would flood the window): isolate it in a subagent. **Continuity** (state must outlive the window): persist it in memory.
</Callout>

### Memory management

<SubskillAnchor id="ctx.memory" />

Memory is anything that persists **outside** the context window and comes back in on demand. Three forms appear in the docs.

**1. The memory tool (API).** Add `{"type": "memory_20250818", "name": "memory"}` to `tools`; no input schema and no beta header for the tool itself [Certain]. It is **client-side**: Claude requests `view`, `create`, `str_replace`, `insert`, `delete` or `rename` on paths under `/memories`, and your handler executes them against storage you control (files, a database, per-user keys) [Certain]. When the tool is present, the API adds a system prompt instruction to view the memory directory before anything else and to assume the context window may be reset at any moment [Certain]. Your handler owns security: validate every path to block traversal such as `/memories/../../secrets.env`, cap file sizes, expire stale files, and strip sensitive data [Certain]. It is available on all Claude 4 and later models [Certain].

**2. Claude Code memory files.** CLAUDE.md is what **you** write: managed policy, user (`~/.claude/CLAUDE.md`), project (`./CLAUDE.md` or `./.claude/CLAUDE.md`) and local (`./CLAUDE.local.md`) scopes load at launch; subdirectory files load on demand; `@path` imports expand at launch, up to four hops deep [Certain]. The docs recommend under 200 lines per file, because longer files consume context and reduce adherence [Certain]. Auto memory is what **Claude** writes: a per-repository `MEMORY.md` index whose first 200 lines or 25KB load every session, plus topic files read on demand [Certain]. Both are context, not enforcement: to block an action regardless of what Claude decides, use a PreToolUse hook [Certain]. Configuration details sit in <ObjLink id="claude-code-operation" />.

**3. External memory and retrieval.** A vector store, a database table, or files the agent reads by path. Prefer **just-in-time** retrieval: keep lightweight identifiers (file paths, stored queries, links) in context and load the data when needed, rather than pre-loading everything up front.

**Persist versus recompute.**

| Persist | Recompute or re-fetch |
|---|---|
| Decisions and the reason for them | File contents, table rows, prices: anything with a source of truth that can change |
| User constraints and preferences stated once | Raw tool output |
| Task progress, checklists, what was verified | Anything cheaper to re-derive than to store and keep fresh |
| Pointers (paths, IDs, query text) | The payload those pointers resolve to |

The rule: persist conclusions and pointers, not payloads. A stored copy of a mutable fact goes stale silently.

**Exam angle:** cues are "across sessions", "next run", "survive a restart", "after compaction". The distractor puts the state in a longer system prompt or a bigger window instead of memory.

### Context window management

<SubskillAnchor id="ctx.window" />

Everything counts toward the window: system prompt, tool definitions, every message including tool results, images and documents, and the output Claude generates for the turn, including thinking [Certain]. Cached tokens count too [Certain]. On current Opus, Sonnet and Fable models previous thinking blocks are **kept** and count as input; on Haiku and earlier Opus and Sonnet models the API strips them [Certain].

| Fact | Value |
|---|---|
| Window, Opus 4.6 and later, Sonnet 4.6 and later, Fable | 1M tokens, standard pricing [Certain] |
| Window, Haiku 4.5 and Sonnet 4.5 | 200k tokens [Certain] |
| Max output per request on 1M models | 128k (`max_tokens`) [Certain] |
| Input alone over the window | 400 `invalid_request_error`, "prompt is too long" [Certain] |
| Input plus `max_tokens` over the window (4.5 and later) | Accepted; stops with `stop_reason: "model_context_window_exceeded"` [Certain] |

**Budget the window like memory in a Spark executor.** Reserve output and thinking headroom, measure input with `count_tokens` before sending, and keep tool definitions lean (deferred loading through tool search exists for large tool sets [Certain]). Sonnet 4.5, Sonnet 4.6, Sonnet 5 and Haiku 4.5 receive injected budget tags showing remaining context; Opus 4.7 and later, Sonnet 5.5 and Fable do not, and use task budgets instead [Certain].

Size is not quality. A 1M window does not stop context rot; it gives bloat more room and dilutes instructions further.

**Exam angle:** cues are "prompt is too long", "how much room is left", "reserve space for the answer". The distractor is a larger-window model when the stem shows degradation far below the limit.

### Preventing context drift and bloat

<SubskillAnchor id="ctx.drift-bloat" />

| | Drift | Bloat |
|---|---|---|
| Definition | Behaviour moves away from the original instructions or goal as the session grows | The window fills with low-value tokens |
| Typical cause | A rule stated once is diluted by volume, contradicted by later turns, or summarized away | Raw tool output, redundant history, stale thinking, unused tool definitions |
| Symptom | Followed the rule at turn 3, ignores it at turn 40 | Slower, costlier, vaguer; re-reads or re-does work; nears the limit |
| Fix | Durable rules in the system prompt or CLAUDE.md; restate key constraints at decision points; goal and plan in memory, re-read each step; fresh session at task boundaries; a hook when it must always hold | Prune at the source, clear old tool results, compact, isolate |
| Wrong fix | Compaction (may delete the rule) or a bigger window (more dilution) | Restating instructions (adds tokens, removes none) |

They compound. Bloat makes each instruction a smaller fraction of the window, which accelerates drift. That is why an agent drowning in tool output also starts ignoring rules: fix the bloat first, then check whether the drift remains.

A durable rule placed where Claude Code re-injects it after compaction (system prompt, project-root CLAUDE.md, auto memory) survives `/compact`; one given only in conversation does not [Certain].

**Exam angle:** "ignores a rule it followed earlier" means drift; "returns the full", "dump", "re-reads" means bloat. The distractor applies the other failure's fix.

### Tool output pruning

<SubskillAnchor id="ctx.pruning" />

Prune in two places.

**At the source (strongest).** The tool returns only what the next decision needs: selected fields, error lines rather than whole logs, a page of results with a cursor, and a pointer to the full artifact. Server tools have equivalents, such as `max_content_tokens` on web fetch [Certain]. This is a tool design responsibility (see <ObjLink id="tool-implementation" />), and it pays on every call because the bulk never enters the window.

**After use (context editing).** Tool result clearing removes old results server-side once input passes a threshold. Beta header `context-management-2025-06-27`, strategy `clear_tool_uses_20250919` [Certain]:

| Parameter | Default | Purpose |
|---|---|---|
| `trigger` | 100,000 input tokens | When clearing starts |
| `keep` | 3 tool uses | Most recent tool pairs kept intact |
| `clear_at_least` | none | Minimum tokens cleared, so the cache rewrite is worth it |
| `exclude_tools` | none | Tools never cleared (for example `memory`) |
| `clear_tool_inputs` | false | Also clear the tool call parameters |

Cleared results become placeholder text, your client keeps the full history, and the response reports `context_management.applied_edits` [Certain]. Clearing invalidates the cached prefix at the clearing point, hence `clear_at_least` [Certain]. With the memory tool present, Claude gets a warning before clearing so it can save what matters [Certain]. Thinking blocks have a sibling strategy, `clear_thinking_20251015`, which must be listed first when combined [Certain].

**Exam angle:** cues are "returns 40,000 tokens but needs 200", "old search results". The distractor is compaction, which keeps the source unchanged so the bulk returns on the next call.

### Compaction

<SubskillAnchor id="ctx.compaction" />

Compaction replaces older turns with a summary. It is **lossy**: the engineering guidance is to tune the summary for recall first, then precision, because overly aggressive compaction drops subtle but critical context. Tool result clearing is the lightest form of compaction.

**Server-side compaction at a threshold (beta).** Header `compact-2026-01-12`, edit `{"type": "compact_20260112"}` in `context_management.edits` [Certain]. `trigger` defaults to 150,000 input tokens (minimum 50,000); `instructions` replaces the default summarization prompt entirely; `pause_after_compaction` returns `stop_reason: "compaction"` so you can re-insert recent turns [Certain]. The response contains a `compaction` block that you must send back; the API ignores every block before it [Certain]. Billing: top-level usage excludes the compaction pass, so sum `usage.iterations` [Certain]. Put a cache breakpoint on the system prompt so it stays cached when the conversation compacts [Certain]. Supported on Claude 4.6 and later models [Certain].

<PostGuide since="2026-09">
Compaction on demand (header `compact-2026-09-04`, top-level `compaction` parameter) lets your application decide when to compact, keep recent turns word for word, or compact in the background. The docs now recommend it wherever available. The client-side SDK `compaction_control` option is deprecated in favour of server-side strategies [Certain].
</PostGuide>

**Claude Code.** `/compact` summarizes the conversation and accepts focus instructions (`/compact focus on the auth bug fix`); auto-compaction runs near the limit [Certain]. After compaction, the system prompt still applies; project-root CLAUDE.md, unscoped rules and auto memory are re-injected from disk; up to five recently modified files are re-read; invoked skills return capped at 5,000 tokens each; nested CLAUDE.md files and path-scoped rules reload only on demand [Certain]. Instructions given only in conversation are summarized like everything else.

| | Context editing (clearing) | Compaction |
|---|---|---|
| Removes | Specific old tool results or thinking | Everything before the summary point |
| Replaced with | Placeholder text | A model-written summary |
| Loss | Exact, predictable | Lossy, depends on the summary prompt |
| Use when | Old tool output dominates | The whole conversation must continue past the limit |

**Exam angle:** cues are "long session must continue", "near the limit", "forgot after compacting". The distractor treats compaction as lossless or as the first response to tool bloat.

### Isolation through subagents or multi-step workflows

<SubskillAnchor id="ctx.isolation" />

Isolation keeps tokens from ever entering the parent's window, which is stronger than removing them later.

<Sequence title="Subagent isolation" actors={["Parent agent", "Subagent", "Tools"]}
  messages={[["Parent agent", "Subagent", "task + constraints, fresh context"],
             ["Subagent", "Tools", "read logs, search, query"],
             ["Tools", "Subagent", "60k tokens of raw output", "reply"],
             ["Subagent", "Subagent", "raw output stays in this window", "note"],
             ["Subagent", "Parent agent", "1-2k token summary + pointers", "reply"]]} />

A subagent gets its own window and system prompt, does the exploration, and returns a condensed summary, often 1,000 to 2,000 tokens. In Claude Code only the subagent's final text (plus a small metadata trailer) returns to the main conversation, and the main conversation's auto memory is not loaded into it [Certain].

**Multi-step workflows** isolate by construction: each step receives only the structured output of the previous step, not the transcript. A multi-session agent does the same across time: an initializer writes a progress log and checklist to memory, and each later session starts fresh by reading them [Certain].

Costs to name in an answer: total tokens rise (each subagent re-reads shared context), detail is lost at the handoff, and the return format must be designed. Isolation suits high-volume, separable exploration. It is a poor fit for tightly coupled edits where the parent needs the raw detail.

**Exam angle:** cues are "explore broadly", "many files", "keep the main thread focused", "in parallel". The distractor prunes after the fact, which still lets the raw output into the parent's window once.

## Decision table

| If the stem says... | Choose | Why the runner-up loses |
|---|---|---|
| Agent followed a formatting rule early, ignores it 40 turns later, window far from full | Re-anchor the rule in the system prompt or CLAUDE.md and restate it at the decision point | Compaction may summarize the rule away; it treats size, not dilution |
| Tool returns a full 50k-token log but the agent needs the error lines | Prune at the source: return error lines plus a pointer | Compaction lets the full log re-enter on every call |
| Old search results from earlier steps fill the window; recent ones matter | Context editing: clear old tool results, keep the last few | Compaction summarizes everything, including the turns still in use |
| Long-running session must continue past the window | Server-side compaction with summary instructions naming what to keep | Starting a new session drops state unless it was persisted |
| State must survive across separate sessions and restarts | Memory tool or memory files, re-read at session start | A longer system prompt is static and cannot record progress |
| Broad codebase exploration would flood the main conversation | Delegate to a subagent that returns a summary | Pruning after the fact still lets the raw reads in once |
| After `/compact` the agent forgot an instruction typed in chat | Move the instruction into project-root CLAUDE.md | CLAUDE.md is re-injected after compaction; chat-only instructions are summarized |
| Rule must hold every time, even after compaction | A hook or permission rule | CLAUDE.md and memory are advisory context, not enforcement |

## Worked walkthrough

<Walkthrough title="Scenario: pipeline triage agent that loses the thread">

<Step title="Read the scenario">
A Sonnet 5.5 agent triages failed nightly jobs. Its `get_job_logs` tool returns the full driver log for a job, 30,000 to 60,000 tokens each. After six or seven jobs the agent re-checks jobs it already diagnosed and its root-cause notes get vaguer, though total input is around 300,000 tokens of a 1M window. Options: (A) move to a model with a larger context window, (B) enable server-side compaction at 150,000 tokens, (C) change `get_job_logs` to return the error lines, job ID and a path to the full log, (D) add "never re-check a diagnosed job" to the system prompt.
</Step>

<Step title="Find the constraint">
The symptom appears far below the limit, and one tool contributes almost every token. This is bloat from tool output, with drift-like side effects because the instructions are now a tiny fraction of the window.
</Step>

<Step title="Eliminate the distractors">
(A) The window is a third used; more room does not stop context rot. (B) Compaction would summarize the logs after the fact, lose exact error strings, and the next `get_job_logs` call would bring 50,000 tokens straight back. (D) Restating a rule adds tokens and removes none; the dilution that caused the re-checking is still there.
</Step>

<Step title="Choose">
(C). Pruning at the source removes the dominant cause on every call. A path to the full log keeps the detail one tool call away (just-in-time retrieval). If the run still grows long, add tool result clearing and record diagnosed job IDs in memory.
</Step>

<Step title="The deciding cue">
"Returns the full driver log" combined with "far from the limit". Volume from one tool, degradation below the limit: prune at the source before any compaction or window change.
</Step>

</Walkthrough>

## Code

**A memory tool handler that cannot escape its root.** Claude asks; your code executes. Every path resolves inside one directory or the call fails.

```python
import anthropic
from pathlib import Path

client = anthropic.Anthropic()

ROOT = Path("./agent_memory").resolve()  # per user or tenant in production
ROOT.mkdir(exist_ok=True)


def safe_path(p: str) -> Path:
    if not p.startswith("/memories"):
        raise ValueError("path must start with /memories")
    real = (ROOT / p.removeprefix("/memories").lstrip("/")).resolve()
    real.relative_to(ROOT)  # raises ValueError if '..' escaped the root
    return real


def run_memory(cmd: dict) -> str:
    path = safe_path(cmd.get("path") or cmd.get("old_path") or "/memories")
    if cmd["command"] == "view":
        if path.is_dir():
            return "\n".join(str(f.relative_to(ROOT)) for f in sorted(path.rglob("*")))
        return path.read_text()
    if cmd["command"] == "create":
        path.parent.mkdir(parents=True, exist_ok=True)
        path.write_text(cmd["file_text"])
        return f"File created successfully at: {cmd['path']}"
    if cmd["command"] == "str_replace":
        text = path.read_text()
        if text.count(cmd["old_str"]) != 1:
            return "No replacement was performed: old_str must appear exactly once."
        path.write_text(text.replace(cmd["old_str"], cmd.get("new_str", "")))
        return "The memory file has been edited."
    return f"Error: {cmd['command']} is not supported by this handler"


messages = [{"role": "user", "content": "Continue triaging last night's failed jobs."}]
while True:
    resp = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=4_000,
        tools=[{"type": "memory_20250818", "name": "memory"}],
        messages=messages,
    )
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break
    results = []
    for b in resp.content:
        if b.type == "tool_use":
            try:
                out, err = run_memory(b.input), False
            except (ValueError, OSError) as e:
                out, err = f"Error: {e}", True
            results.append({"type": "tool_result", "tool_use_id": b.id, "content": out, "is_error": err})
    messages.append({"role": "user", "content": results})

print("".join(b.text for b in resp.content if b.type == "text"))
```

```typescript
import Anthropic from "@anthropic-ai/sdk";
import fs from "node:fs";
import path from "node:path";

const client = new Anthropic();

const ROOT = path.resolve("./agent_memory"); // per user or tenant in production
fs.mkdirSync(ROOT, { recursive: true });

function safePath(p: string): string {
  if (!p.startsWith("/memories")) throw new Error("path must start with /memories");
  const real = path.resolve(ROOT, p.slice("/memories".length).replace(/^\/+/, ""));
  const rel = path.relative(ROOT, real);
  if (rel.startsWith("..") || path.isAbsolute(rel)) throw new Error("path escapes the memory root");
  return real;
}

type MemoryCmd = { command: string; path?: string; old_path?: string; file_text?: string; old_str?: string; new_str?: string };

function runMemory(cmd: MemoryCmd): string {
  const p = safePath(cmd.path ?? cmd.old_path ?? "/memories");
  switch (cmd.command) {
    case "view":
      return fs.statSync(p).isDirectory()
        ? fs.readdirSync(p, { recursive: true }).map(String).sort().join("\n")
        : fs.readFileSync(p, "utf8");
    case "create":
      fs.mkdirSync(path.dirname(p), { recursive: true });
      fs.writeFileSync(p, cmd.file_text ?? "");
      return `File created successfully at: ${cmd.path}`;
    case "str_replace": {
      const text = fs.readFileSync(p, "utf8");
      if (text.split(cmd.old_str ?? "").length !== 2) return "No replacement was performed: old_str must appear exactly once.";
      fs.writeFileSync(p, text.replace(cmd.old_str ?? "", cmd.new_str ?? ""));
      return "The memory file has been edited.";
    }
    default:
      return `Error: ${cmd.command} is not supported by this handler`;
  }
}

const messages: Anthropic.MessageParam[] = [{ role: "user", content: "Continue triaging last night's failed jobs." }];
let resp: Anthropic.Message;
while (true) {
  resp = await client.messages.create({
    model: "claude-sonnet-5-5",
    max_tokens: 4_000,
    tools: [{ type: "memory_20250818", name: "memory" }],
    messages,
  });
  messages.push({ role: "assistant", content: resp.content });
  if (resp.stop_reason !== "tool_use") break;
  const results: Anthropic.ToolResultBlockParam[] = [];
  for (const b of resp.content) {
    if (b.type !== "tool_use") continue;
    try {
      results.push({ type: "tool_result", tool_use_id: b.id, content: runMemory(b.input as MemoryCmd) });
    } catch (e) {
      results.push({ type: "tool_result", tool_use_id: b.id, content: `Error: ${(e as Error).message}`, is_error: true });
    }
  }
  messages.push({ role: "user", content: results });
}
console.log(resp.content.filter((b): b is Anthropic.TextBlock => b.type === "text").map((b) => b.text).join(""));
```

**Clear old tool results, then compact if the session still grows (both beta).** Clearing is exact and cheap; compaction is the heavier, lossy step, so its instructions name what must survive.

```python
import anthropic

client = anthropic.Anthropic()

SYSTEM = "You triage failed data pipeline jobs. Record each diagnosis before moving on."
TOOLS = [{
    "name": "get_job_logs",
    "description": "Error lines and a log path for one job.",
    "input_schema": {"type": "object", "properties": {"job_id": {"type": "string"}}, "required": ["job_id"]},
}]
messages = [{"role": "user", "content": "Triage jobs 8812 through 8830."}]
```

**Prune at the source and isolate in a subagent.** The tool returns error lines and a pointer instead of the full log, and the exploration runs in a subagent whose window the parent never sees.

```python
import anthropic
import json

client = anthropic.Anthropic()


def fetch_driver_log(job_id: str) -> str:  # stand-in for your log store
    return "\n".join([f"INFO step {i}" for i in range(5000)] + ["ERROR AnalysisException: column order_ts not found"])


def get_job_logs(job_id: str) -> str:
    raw = fetch_driver_log(job_id).splitlines()
    errors = [line for line in raw if "ERROR" in line or "Exception" in line][:20]
    return json.dumps({"job_id": job_id, "error_lines": errors, "total_lines": len(raw),
                       "full_log": f"dbfs:/logs/{job_id}/driver.log"})  # pointer, not payload


LOG_TOOL = {"name": "get_job_logs", "description": "Error lines and a log path for one job.",
            "input_schema": {"type": "object", "properties": {"job_id": {"type": "string"}}, "required": ["job_id"]}}


def triage_subagent(job_id: str) -> str:
    """Own window, own loop. Only the final text reaches the parent."""
    msgs = [{"role": "user", "content": f"Find the root cause of failed job {job_id}. Reply in under 150 words with cause, evidence, fix."}]
    for _ in range(6):
        resp = client.messages.create(model="claude-haiku-4-5", max_tokens=1_500, tools=[LOG_TOOL], messages=msgs)
        msgs.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return "".join(b.text for b in resp.content if b.type == "text")
        msgs.append({"role": "user", "content": [
            {"type": "tool_result", "tool_use_id": b.id, "content": get_job_logs(b.input["job_id"])}
            for b in resp.content if b.type == "tool_use"]})
    return "Subagent hit its step limit; see job log path."


summaries = {job: triage_subagent(job) for job in ["8812", "8815"]}  # parent sees only these
print(summaries)
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

function fetchDriverLog(jobId: string): string { // stand-in for your log store
  return [...Array.from({ length: 5000 }, (_, i) => `INFO step ${i}`), "ERROR AnalysisException: column order_ts not found"].join("\n");
}

function getJobLogs(jobId: string): string {
  const raw = fetchDriverLog(jobId).split("\n");
  const errors = raw.filter((l) => l.includes("ERROR") || l.includes("Exception")).slice(0, 20);
  return JSON.stringify({ job_id: jobId, error_lines: errors, total_lines: raw.length,
    full_log: `dbfs:/logs/${jobId}/driver.log` }); // pointer, not payload
}

const LOG_TOOL: Anthropic.Tool = { name: "get_job_logs", description: "Error lines and a log path for one job.",
  input_schema: { type: "object", properties: { job_id: { type: "string" } }, required: ["job_id"] } };

async function triageSubagent(jobId: string): Promise<string> {
  // Own window, own loop. Only the final text reaches the parent.
  const msgs: Anthropic.MessageParam[] = [{ role: "user",
    content: `Find the root cause of failed job ${jobId}. Reply in under 150 words with cause, evidence, fix.` }];
  for (let step = 0; step < 6; step++) {
    const resp = await client.messages.create({ model: "claude-haiku-4-5", max_tokens: 1_500, tools: [LOG_TOOL], messages: msgs });
    msgs.push({ role: "assistant", content: resp.content });
    if (resp.stop_reason !== "tool_use")
      return resp.content.filter((b): b is Anthropic.TextBlock => b.type === "text").map((b) => b.text).join("");
    msgs.push({ role: "user", content: resp.content.filter((b): b is Anthropic.ToolUseBlock => b.type === "tool_use")
      .map((b) => ({ type: "tool_result" as const, tool_use_id: b.id, content: getJobLogs((b.input as { job_id: string }).job_id) })) });
  }
  return "Subagent hit its step limit; see job log path.";
}

const summaries = Object.fromEntries(await Promise.all(["8812", "8815"].map(async (j) => [j, await triageSubagent(j)])));
console.log(summaries); // parent sees only these
```

## Recall checks

<Recall q="What should an agent persist to memory, and what should it re-fetch?">
Persist conclusions, decisions with reasons, progress and pointers such as paths or IDs. Re-fetch anything with a source of truth that can change, and raw tool output, because a stored copy goes stale silently and costs window space when read back.
</Recall>

<Recall q="Who stores the data behind the memory_20250818 tool, and what must that code guard against?">
Your application does: the tool is client-side, so Claude only requests operations under /memories. Your handler must validate every path against traversal (for example /memories/../../secrets.env) and should cap sizes and expire stale files.
</Recall>

<Recall q="An agent degrades at 250k tokens on a 1M-token model. Why is a larger window the wrong fix?">
Recall degrades as token count grows (context rot), long before the limit. More room lets bloat grow and further dilutes instructions, so the fix is to remove low-value tokens, not add capacity.
</Recall>

<Recall q="Distinguish drift from bloat by symptom and fix.">
Drift is a rule or goal fading as the session grows; fix it by re-anchoring the rule in the system prompt or CLAUDE.md, restating it at decision points, or enforcing it with code. Bloat is low-value tokens filling the window; fix it by pruning, clearing old tool results, compacting or isolating.
</Recall>

<Recall q="Why prune tool output at the source rather than rely on context editing?">
Source pruning keeps the bulk out on every call. Context editing removes old results only after they have already consumed window space, and each clearing invalidates the cached prefix from that point.
</Recall>

<Recall q="After /compact in Claude Code, which instructions are guaranteed to come back, and which can be lost?">
The system prompt still applies and project-root CLAUDE.md, unscoped rules and auto memory are re-injected from disk. Instructions given only in the conversation are summarized with everything else and can be lost.
</Recall>

<Recall q="Why does subagent isolation beat pruning after the fact for broad exploration?">
The subagent's raw tool output never enters the parent's window; only its summary returns. Pruning after the fact still lets the full output into the parent once, where it costs attention and tokens.
</Recall>
