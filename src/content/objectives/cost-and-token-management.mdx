## Concept

The guide opens this objective with **token budgeting**, then lists usage tracking, cost modeling, prompt caching and cache checkpointing. Read it as one loop: decide what a call or task may spend before you send it, read exactly what it did spend from `usage`, turn that into cost per completed task, then pull the cheapest lever that moves the number.

Items test levers and ratios, not prices: output costs 5x input, a cache read is a tenth of input on most models, a 5 minute write costs 1.25x. Dollar figures drift; ratios do not.

**Scope boundary.** Choosing a model tier on capability grounds is <ObjLink id="model-selection-and-tradeoffs" />. Batch request shape, `custom_id` joins and result polling are <ObjLink id="claude-api-mechanics" />; here batch is only a lever that halves price and stacks with caching. Keeping the window useful (pruning, compaction, isolation) is <ObjLink id="context-engineering" />; here those matter only because fewer tokens cost less. What a token is belongs to <ObjLink id="llm-fundamentals" />.

Not this:
- Picking Opus versus Sonnet for reasoning quality
- Batch API polling, result ordering or request limits
- Designing compaction summaries for recall

<Callout type="key" title="The order that wins points">
Measure first, then cut in this order: **send fewer tokens, cache the stable prefix, batch what can wait, step effort down, and change the model last.** Only the last lever changes behaviour, so only the last one forces you to re-run evals.
</Callout>

### Token budgeting

<SubskillAnchor id="cost.budgeting" />

Budgets exist at three scopes, and each has a different enforcement mechanism.

| Scope | Mechanism | Enforced? |
|---|---|---|
| One request, output side | `max_tokens` (thinking counts inside it) | Yes, hard cap; truncates with `stop_reason: "max_tokens"` |
| One request, input side | `count_tokens` pre-check in your code | Yes, if your code refuses or trims |
| One agentic loop | `output_config.task_budget` (beta) | No, advisory; `max_tokens` stays the hard cap |
| Per user, per tenant, per month | Your ledger summing `usage`; Console workspace spend limits | Yes, in your code or at the workspace limit |

**Sizing `max_tokens`.** Size it to the longest legitimate answer plus thinking headroom, not to the average. Billing counts tokens generated, not the cap, and the rate limits page states that `max_tokens` does not factor into OTPM [Certain]. A tight cap therefore saves nothing on a normal response and wastes a whole call on a long one. Thinking tokens are a subset of `max_tokens` [Certain], so a high-effort call needs more room than its visible answer suggests.

**Pre-checking with `count_tokens`.** The endpoint takes the same system, tools, messages, images and PDFs as a real request and returns `input_tokens`. It is free, has its own rate limit separate from message creation, returns an estimate, and applies no caching logic [Certain]. It rejects server tools (other than the advisor tool), the MCP connector and URL or file sources [Certain]. Use it to refuse an oversize request, trim retrieval, or route before an expensive call.

**Per-task and per-user budgets.** Keep a ledger keyed by user or tenant, priced from `usage`, and check it before each call. A spend limit you set in the Console stops requests with a 400 `invalid_request_error`, distinct from the tier cap's 429 [Certain]. Workspaces can carry their own spend and rate limits [Certain]. Per-user limits remain your code's job.

**Task budgets for agent loops.** `output_config.task_budget` with `{"type": "tokens", "total": N}` tells the model how many tokens the whole loop may spend, including thinking, tool calls, tool results and output. The model sees a countdown and paces itself; responses carry no remaining-budget field [Certain]. It is advisory: the model may overrun to finish an action, so `max_tokens` stays the per-request ceiling. The minimum total is 20,000, a budget far too small can cause refusal-like early stops, and changing `remaining` per request breaks the cache [Certain]. The beta header is `task-budgets-2026-03-13`, which suggests it predates the guide, but it is beta and unsupported on Haiku 4.5 and Sonnet 4.6 [Likely low exam weight].

**Exam angle:** "cap", "ceiling", "before sending", "estimate" point here. The usual distractor is lowering `max_tokens` as a cost fix, which saves nothing and truncates.

### Token usage tracking

<SubskillAnchor id="cost.tracking" />

`usage` on every response is the billing truth. Read every field.

| Field | Meaning | Price multiplier on base input |
|---|---|---|
| `input_tokens` | Tokens **after the last cache breakpoint** only | 1x |
| `cache_creation_input_tokens` | Tokens written to cache this request | 1.25x (5m) or 2x (1h) |
| `cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` | Split of the write by TTL | as above |
| `cache_read_input_tokens` | Tokens served from cache | 0.1x on most models |
| `output_tokens` | Everything generated, **including thinking** | output rate |
| `server_tool_use.web_search_requests` | Server tool calls billed per use | $10 per 1,000 searches [Certain] |
| `iterations` (compaction) | Per-iteration usage when server compaction runs | sum them; top level excludes compaction |

Total input is `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` [Certain]. Thinking is billed as output at full length even when `display` is `"omitted"` or summarized, so billed `output_tokens` will not match the text you see [Certain]. The thinking cost page documents a breakdown, `usage.output_tokens_details.thinking_tokens`, which is always at most `output_tokens`; when streaming it appears only on the final `message_delta` [Certain, likely post-guide]. Use it for dashboards, but the exam-safe fact is that thinking is inside `output_tokens` at the output rate.

Log every field per request, tagged with feature, tenant, model and effort, and alert on **cache hit ratio** (reads over total input) and **cost per completed task**. A silent cache regression shows up as `cache_read_input_tokens` dropping to zero. Cached reads also do not count toward ITPM on most models [Certain], so a cache regression can surface as 429s before it shows on the invoice.

**Exam angle:** cues are "dashboard", "attribute", "reconcile with the invoice". The trap is treating `input_tokens` as total input or thinking as free.

### Cost modeling

<SubskillAnchor id="cost.modeling" />

```
cost = input_tokens x in
     + cache_write_5m x in x 1.25
     + cache_write_1h x in x 2.0
     + cache_read x in x 0.1        # 0.05 on Opus 5.5, 0.025 on Fable 5.1
     + output_tokens x out          # thinking included
     then x 0.5 if batched, x 1.1 if inference_geo "us" (4.6+ models)
```

**Worked arithmetic, Sonnet 5.5** ($2 input, $10 output per million [Certain]; 5 minute write $2.50, read $0.20). An analytics assistant sends a 24,000-token stable prefix (tools, system, schema notes), a 400-token question, and gets 900 output tokens including thinking.

| Call | Calculation | Cost |
|---|---|---|
| Uncached | 24,400 x $2/M + 900 x $10/M | $0.0578 |
| First call, cache write | 24,000 x $2.50/M + 400 x $2/M + 900 x $10/M | $0.0698 |
| Later call, cache hit | 24,000 x $0.20/M + 400 x $2/M + 900 x $10/M | $0.0146 |
| Five-question session, cached | $0.0698 + 4 x $0.0146 | $0.1282 vs $0.289 uncached |

Caching cut the session by about 56%. After caching, output is $0.009 of the $0.0146 hit, so the **next** lever is output (effort step-down, tighter format), not a model change.

**Cost per completed task, not per request.** Divide all spend (retries, failed tool calls, abandoned sessions, extra agent turns) by tasks that succeeded. Haiku 4.5 prices the same cached call at about $0.0073; if it needs two attempts per accepted answer, it costs $0.0146 per completed task, the same as Sonnet 5.5 at one attempt, before counting the user's time. Token counts also differ by tokenizer: models from Claude 4.7 on produce roughly 30% more tokens for the same text [Certain], so recount before comparing.

Modifiers stack multiplicatively: batch halves input and output, caching multipliers apply on top, and US-only inference adds 1.1x on 4.6 and later models [Certain]. 1M-token context on 4.6 and later models bills at standard rates with no long-context premium [Certain].

**Exam angle:** cues are "forecast", "per ticket", "which costs more". The distractor compares per-request price and ignores attempts per success.

### Prompt caching for cost

<SubskillAnchor id="cost.prompt-caching" />

Caching trades a write premium for a read discount on a repeated prefix.

| | 5 minute TTL (default) | 1 hour TTL |
|---|---|---|
| Syntax | `{"type": "ephemeral"}` | `{"type": "ephemeral", "ttl": "1h"}` |
| Write cost | 1.25x base input | 2x base input |
| Break-even | after 1 read | after 2 reads |
| Choose when | requests arrive within minutes | gaps of 5 to 60 minutes (human think time, long tool runs) |

Each hit refreshes the TTL at no extra cost, and the lifetime is measured from the **start** of the request, so a long stream eats into it [Certain]. Prefixes below the model's minimum are processed uncached with no error: 512 tokens on Opus 5.5 and Sonnet 5.5, 1,024 on Opus 4.8, Sonnet 5 and Sonnet 4.6, 4,096 on Haiku 4.5 [Certain]. Caches are isolated per workspace on the Claude API [Certain]. Cached tokens still occupy the context window; caching changes the price, not the size [Certain].

<PostGuide since="2026-08">
Cache reads are no longer a flat 0.1x on every model: Opus 5.5 reads cost 0.05x and Fable 5.1 reads cost 0.025x of base input, per the current pricing page [Certain]. Use 0.1x as the general rule for exam reasoning.
</PostGuide>

**Exam angle:** cues are "same large prefix", "repeated", "steady traffic". The distractor caches unique per-request content or picks 5 minutes when the stem describes gaps longer than 5 minutes.

### Cache checkpointing

<SubskillAnchor id="cost.checkpointing" />

A checkpoint is a `cache_control` marker. The prefix renders as **tools, then system, then messages**, and a write stores a hash of everything up to the marker. A read checks for an exact prefix match, looking back at most **20 blocks** per breakpoint for an earlier write [Certain]. You get **up to 4 breakpoints** per request [Certain]. Top-level automatic caching (one `cache_control` on the request) places the breakpoint on the last cacheable block and moves it forward as the conversation grows [Certain].

**Placement.** Put a checkpoint where stability changes: after tools and system (changes on deploy), after a large reference document (changes daily), and at the end of the conversation (moves every turn). When mixing TTLs, longer TTLs must come before shorter ones [Certain].

| Change | Tools cache | System cache | Messages cache |
|---|---|---|---|
| Tool definitions | invalidated | invalidated | invalidated |
| Web search, citations or fast-mode toggle | kept | invalidated | invalidated |
| `tool_choice`, adding or removing images | kept | kept | invalidated |
| Thinking config or effort | model-specific | model-specific | invalidated |

Source: prompt caching page [Certain]. Also invalidating: any byte change upstream (a timestamp or request ID in the system prompt, non-deterministic JSON key order), tool result clearing by context editing, and a changing task budget `remaining` value [Certain].

**Exam angle:** cues are "cache_read is 0", "hits stopped after turn 20", "only the latest turn changes". The distractor is a bigger TTL when the real fault is a volatile byte upstream of the breakpoint.

## Decision table

| If the stem says... | Choose | Why the runner-up loses |
|---|---|---|
| Cost spiked; prompt has a large unchanging prefix; team proposes a cheaper model | Add a cache checkpoint after the stable prefix | Model downgrade changes behaviour and invalidates evals; caching keeps outputs identical |
| `cache_read_input_tokens` is 0 on back-to-back identical requests | Find the volatile byte upstream (timestamp, ID, unsorted JSON, tool list) | Switching to the 1 hour TTL cannot help when the prefix differs each time |
| Users reply every 10 to 30 minutes against the same long context | 1 hour TTL on the stable block | The 5 minute cache expires between turns, so every turn pays a fresh 1.25x write |
| Each request carries a unique document read once | Do not cache that document; trim or retrieve less | A write premium with no later read costs more than no caching |
| Must reject requests that would exceed a per-request input budget before spending anything | `count_tokens` pre-check, then refuse or trim | Reading `usage` afterward is too late; the tokens are already billed |
| Agent loop should wind down gracefully near a token target | Task budget (advisory) plus a sane `max_tokens` (hard cap) | `max_tokens` alone truncates mid-action; a task budget alone is not enforced |
| Team wants to know how much reasoning costs | Read `usage.output_tokens_details.thinking_tokens` (inside `output_tokens`, billed at the output rate) per feature and effort level | There is no cheaper thinking rate to report separately |
| Cached answers are cheap now but output dominates each call | Step effort down or tighten the answer format | Model downgrade comes last; effort keeps the same model |

## Worked walkthrough

<Walkthrough title="Scenario: code review assistant that never hits its cache">

<Step title="Read the scenario">
A pull-request review assistant on Sonnet 5.5 sends 30,000 tokens of repository conventions as a cached system block, then the reviewer's comment. Reviewers usually reply 10 to 20 minutes after the previous answer. `usage` shows `cache_creation_input_tokens` near 30,000 on every call and `cache_read_input_tokens` at 0. Options: (A) move to Haiku 4.5, (B) set the conventions block to the 1 hour TTL, (C) route reviews through the Batch API, (D) cut `max_tokens` from 4,000 to 1,000.
</Step>

<Step title="Find the constraint">
Two facts together: a write on every call, and a gap of 10 to 20 minutes between calls. The prefix is stable (the write size is constant), so the cache is not being invalidated; it is **expiring**. The default TTL is 5 minutes.
</Step>

<Step title="Eliminate the distractors">
(A) Haiku is model change, the last lever; it changes review quality and does nothing about expiry. (C) Batch is asynchronous with up to 24 hours to complete, which breaks an interactive review thread. (D) Billing counts generated tokens, not the cap, so a lower cap only truncates longer reviews.
</Step>

<Step title="Choose and check the arithmetic">
(B). Over four turns in an hour, 5 minute caching rewrites every turn: 4 x 30,000 x $2.50/M = $0.30. With the 1 hour TTL: one write at 30,000 x $4/M = $0.12, then three reads at 30,000 x $0.20/M = $0.018. About $0.14 instead of $0.30, with identical outputs.
</Step>

<Step title="The deciding cue">
"Reply 10 to 20 minutes later" plus "cache write on every call". A constant write size means a stable prefix that expires, which points to TTL. A varying write size or a zero read on back-to-back calls would instead point to a volatile byte in the prefix.
</Step>

</Walkthrough>

## Code

**Budget before, cost after.** Pre-check input with `count_tokens`, enforce a per-user ledger, cap output with `max_tokens`, then price the real call from every `usage` field.

```python
import anthropic

client = anthropic.Anthropic()

MODEL = "claude-sonnet-5-5"
PRICE = {"in": 2.00, "out": 10.00}  # USD per million tokens (src/data/facts.json)
MULT = {"write_5m": 1.25, "write_1h": 2.0, "read": 0.1}
ledger: dict[str, float] = {}  # user_id -> USD spent this month


def text_of(resp) -> str:
    return "".join(b.text for b in resp.content if b.type == "text")


def cost_usd(u) -> float:
    cc = getattr(u, "cache_creation", None)
    w1h = (getattr(cc, "ephemeral_1h_input_tokens", 0) or 0) if cc else 0
    w5m = (u.cache_creation_input_tokens or 0) - w1h
    read = u.cache_read_input_tokens or 0
    per_million = (
        u.input_tokens * PRICE["in"]
        + w5m * PRICE["in"] * MULT["write_5m"]
        + w1h * PRICE["in"] * MULT["write_1h"]
        + read * PRICE["in"] * MULT["read"]
        + u.output_tokens * PRICE["out"]  # thinking is already inside output_tokens
    )
    return per_million / 1_000_000


def ask(user_id: str, system: str, messages: list, max_input=40_000, max_out=2_000, cap_usd=25.0):
    if ledger.get(user_id, 0.0) >= cap_usd:
        raise RuntimeError(f"{user_id} is over the monthly cap")
    n = client.messages.count_tokens(model=MODEL, system=system, messages=messages).input_tokens
    if n > max_input:
        raise ValueError(f"{n} input tokens exceeds budget {max_input}: trim or retrieve less")
    resp = client.messages.create(model=MODEL, max_tokens=max_out, system=system, messages=messages)
    spent = cost_usd(resp.usage)
    ledger[user_id] = ledger.get(user_id, 0.0) + spent
    if resp.stop_reason == "max_tokens":
        print("truncated: cap too tight, and those tokens were still billed")
    return text_of(resp), spent


answer, usd = ask("u-417", "You answer questions about our warehouse schema.",
                  [{"role": "user", "content": "Which table holds late-arriving events?"}])
print(f"${usd:.5f}", answer[:80])
```

```typescript
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const MODEL = "claude-sonnet-5-5";
const PRICE = { in: 2.0, out: 10.0 }; // USD per million tokens (src/data/facts.json)
const MULT = { write5m: 1.25, write1h: 2.0, read: 0.1 };
const ledger = new Map<string, number>(); // userId -> USD spent this month

function textOf(resp: Anthropic.Message): string {
  return resp.content.filter((b): b is Anthropic.TextBlock => b.type === "text").map((b) => b.text).join("");
}

function costUsd(u: Anthropic.Usage): number {
  const w1h = u.cache_creation?.ephemeral_1h_input_tokens ?? 0;
  const w5m = (u.cache_creation_input_tokens ?? 0) - w1h;
  const read = u.cache_read_input_tokens ?? 0;
  const perMillion =
    u.input_tokens * PRICE.in +
    w5m * PRICE.in * MULT.write5m +
    w1h * PRICE.in * MULT.write1h +
    read * PRICE.in * MULT.read +
    u.output_tokens * PRICE.out; // thinking is already inside output_tokens
  return perMillion / 1_000_000;
}

async function ask(userId: string, system: string, messages: Anthropic.MessageParam[],
                   maxInput = 40_000, maxOut = 2_000, capUsd = 25) {
  if ((ledger.get(userId) ?? 0) >= capUsd) throw new Error(`${userId} is over the monthly cap`);
  const { input_tokens } = await client.messages.countTokens({ model: MODEL, system, messages });
  if (input_tokens > maxInput) throw new Error(`${input_tokens} input tokens exceeds budget ${maxInput}`);
  const resp = await client.messages.create({ model: MODEL, max_tokens: maxOut, system, messages });
  const spent = costUsd(resp.usage);
  ledger.set(userId, (ledger.get(userId) ?? 0) + spent);
  if (resp.stop_reason === "max_tokens") console.warn("truncated: cap too tight, still billed");
  return { answer: textOf(resp), spent };
}

const { answer, spent } = await ask("u-417", "You answer questions about our warehouse schema.",
  [{ role: "user", content: "Which table holds late-arriving events?" }]);
console.log(`$${spent.toFixed(5)}`, answer.slice(0, 80));
```

**Two checkpoints with mixed TTLs.** The slow-changing reference block gets the 1 hour TTL and comes first; the moving conversation tail gets the default 5 minutes. Longer TTLs must precede shorter ones.

```python
import anthropic

client = anthropic.Anthropic()

REFERENCE = open("conventions.md").read()  # large, changes weekly
TOOLS = [{
    "name": "get_file",
    "description": "Return one file from the pull request by path.",
    "input_schema": {"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]},
}]
history = [
    {"role": "user", "content": "Review the retry logic in loader.py."},
    {"role": "assistant", "content": "The backoff never caps; see line 42."},
]
question = "Would a jittered cap of 30 seconds fix it?"

resp = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=2_000,
    tools=TOOLS,  # rendered first; any change here invalidates everything
    system=[{"type": "text", "text": REFERENCE,
             "cache_control": {"type": "ephemeral", "ttl": "1h"}}],  # checkpoint 1
    messages=history + [{"role": "user", "content": [
        {"type": "text", "text": question,
         "cache_control": {"type": "ephemeral"}}]}],  # checkpoint 2, moves each turn
)
u = resp.usage
print("read", u.cache_read_input_tokens, "write", u.cache_creation_input_tokens, "uncached", u.input_tokens)
```

```typescript
import Anthropic from "@anthropic-ai/sdk";
import { readFileSync } from "node:fs";

const client = new Anthropic();

const REFERENCE = readFileSync("conventions.md", "utf8"); // large, changes weekly
const TOOLS: Anthropic.Tool[] = [{
  name: "get_file",
  description: "Return one file from the pull request by path.",
  input_schema: { type: "object", properties: { path: { type: "string" } }, required: ["path"] },
}];
const history: Anthropic.MessageParam[] = [
  { role: "user", content: "Review the retry logic in loader.py." },
  { role: "assistant", content: "The backoff never caps; see line 42." },
];
const question = "Would a jittered cap of 30 seconds fix it?";

const resp = await client.messages.create({
  model: "claude-sonnet-5-5",
  max_tokens: 2_000,
  tools: TOOLS, // rendered first; any change here invalidates everything
  system: [{ type: "text", text: REFERENCE, cache_control: { type: "ephemeral", ttl: "1h" } }], // checkpoint 1
  messages: [...history, { role: "user", content: [
    { type: "text", text: question, cache_control: { type: "ephemeral" } }] }], // checkpoint 2
});
const u = resp.usage;
```

## Recall checks

<Recall q="Why is lowering max_tokens a poor cost fix for responses that are already short?">
Billing counts tokens actually generated, so a lower cap saves nothing on short answers. On long answers it truncates with stop_reason max_tokens, and the retry costs more than one complete call.
</Recall>

<Recall q="A dashboard sums input_tokens and shows input spend falling 80% after caching shipped, but the invoice barely moved. What is wrong?">
input_tokens counts only tokens after the last cache breakpoint. The cached prefix moved into cache_read_input_tokens and cache_creation_input_tokens, which must be added at 0.1x and 1.25x or 2x of the base input price.
</Recall>

<Recall q="After caching, output is 60% of each call's cost. Which lever comes next, and why not a smaller model?">
Step effort down or tighten the output format, because both keep the same model and validated behaviour. A model change is last since it changes outputs and forces a full eval re-run.
</Recall>

<Recall q="Why model cost per completed task instead of per request?">
Retries, failed tool calls and extra agent turns are real spend. A model that is half the price per call but needs two attempts per accepted answer costs the same per task, and more once user time is counted.
</Recall>

<Recall q="When does the 1 hour TTL beat the default 5 minute TTL?">
When the same prefix is reused with gaps longer than 5 minutes but under an hour. A 1 hour write costs 2x once and breaks even after two reads, while a 5 minute cache would pay a fresh 1.25x write after every gap.
</Recall>

<Recall q="Changing tool_choice between requests drops cache hits. Which cached segments survive?">
The tools and system segments stay cached; only the messages segment is invalidated. Changing tool definitions, by contrast, invalidates all three because tools render first.
</Recall>

<Recall q="A task budget is set to 60,000 tokens. Can the loop spend more?">
Yes. Task budgets are advisory: the model sees a countdown and paces itself but may finish an action past the budget. max_tokens is the enforced per-request ceiling.
</Recall>
